# 音声をサーバーで中継し、面接ごとのDOで状態を管理する

個人用の面接練習に加えて、本番運用を想定した接続・記録・利用制限の設計を成果物として説明したいため、ブラウザとGPT-Liveの間にCloudflare側の音声中継を置きます。再接続や別タブからの引き継ぎでも同じ面接の状態と送信権を管理するため、面接ごとにDurable Objectを割り当てます。単純な中継より増える費用と障害処理を引き受け、サーバー側で制御する責務を明確にします。

## 2026年10月30日の採用サービス変更

音声対話をGemini LiveからGPT-Liveへ変更します。音声のみの要件に対応する接続方式と文字起こしが公式資料にあり、ProのAPIクレジットを利用できることが変更の理由です。サーバー側で状態と送信権を管理する目的は変わらないため、DO中継を維持します。クレジットの継続や実環境での品質・互換性は保証済みとは扱いません。

再開には保存済みテキストを使います。OpenAI側に録音を保存して再開する方式もありますが、再開のための音声保存を避ける方針から採用しません。音声に含まれる情報を完全には復元できないこと、履歴の入力上限に合わせた文脈選択と欠落時の処理が必要になることを受け入れます。具体的な検証事項は[MVP仕様書の補足事項](../spec/mvp.md#補足事項)に集約します。

## 検討した選択肢

- ブラウザ直結：短命トークンにより長期キーを隠し、中継の遅延と実装負担を減らせます。本番で成立しない方式だから除外したのではなく、今回のサーバー側制御と学習目的から中継を選びました。
- 通常Workerだけの中継：通信は実現できますが、再接続先が変わる場合の状態・所有権・競合管理が別途必要です。
- 面接ごとのDO：面接IDによる状態と接続の管理をまとめられるため採用しました。

## 影響

外向きWebSocketの保持中はDOの休止による節約を前提にしません。DOも通信やメモリを永続的に維持するわけではないため、再開情報と未保存テキストの復旧設計が必要です。GPT-Liveの録音保存は無効にし、D1に保存したテキストと面接状態から新しい接続を開始します。面接IDは維持します。再開用の文脈を選択・要約しても、評価の根拠となる原文は変更しません。OpenAI側の不正利用監視等による保持と、アプリ側の音声非保存は区別します。

現在の動作は[MVP仕様書](../spec/mvp.md)、根拠と未検証事項は[技術調査](../research/platform-integration.md)を参照してください。
