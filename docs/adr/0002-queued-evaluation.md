# 評価をQueuesとDLQで音声面接から分離する

終了受付後は画面を閉じても評価を進め、失敗時には再実行できるようにするため、評価をCloudflare QueuesのConsumerで実行します。既存DOのAlarmだけで評価する案も検討しましたが、本番運用を想定して音声面接と評価の障害・実行時間・同時実行制御を分ける判断からQueuesを選びました。失敗したジョブを失わないようDLQも明示的に設定します。

## 検討した選択肢

- DO Alarmで評価：サービス追加を抑えられますが、評価の実行管理を面接DO側に持つ構成になるため採用しません。
- Queues：評価処理の独立した実行と再配送を採用理由とします。
- Workflows：複数段階の永続的な処理管理は、現時点の評価工程では採用しません。

## 影響

送信待ち記録による配送漏れ対策、重複配送時の実行権管理、DLQとD1状態の照合が必要です。初期案ではDOのAlarmによる配送確認も候補でしたが、2026年11月2日にEvaluation Workerの定期回復へ集約しました。再試行の回数、手動再実行の条件、削除との競合は[MVP仕様書](../spec/mvp.md)を正とします。

QueueやDBの重複防止だけでは外部AIへの呼び出しを厳密に一度にできません。生成後の通信断などでは再呼び出しと追加料金が発生し得ます。

## 2026年11月2日の配送・回復規則の具体化

[ADR 0010](0010-queue-contracts-and-job-control.md)により、Queue契約の原本、D1の状態・実行権、評価と配送の再試行の分離を定めました。アプリが判断できる失敗はD1へ先に保存し、送信待ち記録からDLQへ退避します。DLQ到着だけでは失敗と判定しません。回復はEvaluation Workerが担当し、面接DOで評価を実行しない判断は維持します。
