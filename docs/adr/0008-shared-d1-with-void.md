# D1を共有し、Void経由のDrizzleで一元管理する

2026年11月2日合意。同じ環境の3 WorkersでD1を1つ共有し、スキーマとマイグレーションの原本を`packages/database`に集約します。DrizzleをVoid経由で使用し、生成・適用もVoid CLIにまとめます。面接記録と評価の共通データを扱いながら、DB定義と適用履歴の重複を避けるためです。

## 検討した選択肢

- WorkerごとのDB：保存と配置を独立させやすい反面、面接・評価・削除状態の同期が必要になります。現在の個人用MVPでは採用しません。
- 各Workerでスキーマ・適用を管理：変更の入口が増え、定義や適用状態がずれるため採用しません。
- Drizzle KitとCloudflare CLIを直接運用：可能ですが、利用者がWranglerの直接操作を避けたい意向と、Void内蔵Drizzleを利用する方針から、日常操作をVoidへ集約します。

## 影響

HTTP契約はTypeSpec、DBの保存形式はDrizzleを原本とし、業務モデルやAPI応答との変換をサーバーで扱います。DB管理パッケージは追加Workerとして配置しません。接続は各Workerで作り、全業務処理を共有DBパッケージへ集めません。

共有DBはWorker間の結合点です。旧版・新版が共存できる変更順序が必要で、DO・D1・Queueをまたぐ原子性も得られません。DBアクセスを分けても、バインディングだけでテーブル単位の権限制限を保証しません。独立した保存権限や運用が必要になった場合は共有範囲を見直します。

Void 1.4.0の静的確認と実動作の確認を区別します。DB専用パッケージからの適用、共有ローカルD1、Workerデプロイ時の意図しない適用防止は未検証です。[調査記録](../research/void-drizzle.md)と[MVP仕様書](../spec/mvp.md#共有d1とマイグレーション)を参照してください。
