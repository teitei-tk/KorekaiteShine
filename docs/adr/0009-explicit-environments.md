# 環境名からWorkerとリソースの対応を一元化する

2026年11月2日合意。`development`・`test`・`production`を独自の`APP_ENV`で選び、3 Workers、D1、DO、Queueの対応を共通設定で管理します。開発データを保持しながら自動テストを独立させ、環境をまたぐ誤接続を防ぐためです。

## 検討した選択肢

- DB名だけを分ける：DO状態やQueue配送が混ざるため不十分です。
- Voidの環境別CLIやdotenvファイルに任せる：確認した固定版に共通の`--env`はなく、環境別dotenvも前提にできません。
- 共通環境設定を用意する：設定コードの保守は増えますが、同じ環境名から全接続先を決められるため採用します。`NODE_ENV`、配置基盤、remote bindingとは区別します。

## 影響

通常の開発とテストはローカル、本番はCloudflareです。テストでは実行・並列単位ごとにリソース識別子、状態保存先、生成設定・ビルド出力を分けます。固定の架空データを使い、開発DBのリセットは明示操作にします。

単一開発ランタイムの`auxiliaryWorkers`を第一候補としますが、保存先の共有だけではWorker間通信やQueue配送は成立しません。Voidの生成情報・lockとDB専用CLIの保存先まで対応を検証します。配置環境を追加する場合や起動方式が成立しない場合は、環境の対応表と実行方式を見直します。

命名・配置・未検証事項は[MVP仕様書](../spec/mvp.md#環境と検証データ)、固定版の根拠は[調査記録](../research/void-environments.md)を参照してください。文書の合意はクラウド変更や秘密値の登録の承認を意味しません。
