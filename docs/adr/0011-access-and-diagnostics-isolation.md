# Accessで入口を保護し、診断機能を本番成果物から除外する

2026年11月2日合意。本番Webの入口をCloudflare Accessで本人限定にし、診断用の画面・API・失敗注入処理は本番成果物に含めません。認証処理や環境判定の書き忘れだけに保護を依存させず、入口の認可と配置する機能の分離を組み合わせるためです。

## 検討した選択肢

- 各APIで環境を判定する：単純ですが、判定の漏れや設定ミスで本番に診断機能が残るため、唯一の防御にはしません。
- Accessだけで保護する：本人以外の利用は制限できますが、認証済み本人による本番の診断・失敗注入は防げません。
- Accessと成果物分離を併用する：開発・テスト用エントリと本番用エントリの保守、ビルド結果の検査が増えますが、診断機能を実行する経路自体を本番から除くため採用します。

## 影響

3 Workersの分割は維持します。診断モジュールは開発・テスト用エントリだけから読み込み、本番の各Workerと配信アセットへの混入をCIで検査します。単なる文字列検索や環境変数の判定だけで、非包含を保証したとは扱いません。

WebSocketを使うため、Webの独自ホスト名をAccessで保護します。確認時点の[Cloudflare公式資料](https://developers.cloudflare.com/workers/configuration/cloudflare-access/)ではWorker単位のAccessはWebSocketに未対応で、ホスト名単位が案内されています。不要なworkers.dev・プレビュー入口を配置設定で無効にし、残す入口も同等に保護します。Interview・Evaluationには公開HTTP入口を設けません。

Accessの本人情報は内部Workerへ自動伝播するとは扱いません。認証手段、内部呼び出しの権限、接続中の失効は別途設計します。保護と成果物分離は未検証であり、クラウド操作は対象・操作の承認後に行います。

正式な要件と検証項目は[MVP仕様書](../spec/mvp.md#アクセスと秘密情報)を参照してください。将来クラウド上の診断環境を設ける場合は、本人限定Accessに加えて本番リソースからの分離を設計し直します。本番へ診断機能を戻すことを暗黙に許可しません。
