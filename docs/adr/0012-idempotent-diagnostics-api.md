# 診断APIの受付をD1で冪等化し、型付きエラーを返す

2026年11月2日合意。検証用開始APIに必須の冪等キーを設け、キーと入力の対応・ジョブ・後続処理のoutboxをD1へ一体で保存してから受付を返します。通信切断や同時要求でも一つの受付を参照でき、受付直後の停止から回復できるようにするためです。HTTPエラーは機械判定用の識別子と説明を分け、TypeSpecで管理します。

## 検討した選択肢

- 画面の連打防止だけで対応する：通信結果が不明な再送や複数の呼び出し元を制御できないため採用しません。
- 先にDOを初期化し、最後に受付を保存する：DOへの書き込み後に停止すると受付との対応が失われるため、先にD1へ受付と後続処理を保存します。
- キーの存在確認後に別々に保存する：同時要求で競合するため、一意制約と同一トランザクションで保証します。
- HTTPステータスと説明文だけを返す：文言の変更でクライアントの分岐が壊れるため、文字列の`code`を必須にします。
- エラー分類や自由形式の詳細を増やす：初期構成ではHTTPステータスと`code`で分岐できるため、`type`は設けず、入力検証の詳細も型付きに限定します。

## 影響

同じキー・同じ入力には、処理の進行にかかわらず同じ受付結果を返します。異なる入力は競合とし、意図的な再実行は別のキーで行います。冪等キーは要求の再送、ジョブIDは評価実行、要求ごとの`requestId`はログの追跡を識別します。最小骨格ではキーを自動失効させず、保存量が増える負担を引き受けます。明示的なDBリセットで保証は終了します。

D1・DO・Queue間の原子性や外部副作用の厳密な一回実行は保証しません。DOの初期化もジョブ単位で冪等化し、後続処理の回復とConsumerの実行権は[ADR 0010](0010-queue-contracts-and-job-control.md)の方針を維持します。正常完了と、意図的な失敗による業務再試行・DLQ受信を別々に観測します。

エラーは`error`で包み、`code`・`message`・`requestId`を必須にします。入力検証時だけ型付きの`details`を追加し、内部例外や受信した秘密値は返しません。参照した「有名OSS・SDKのAPIエラー形式を調査」（チャットID：`01a19ae4-c02f-7ad2-a9e9-414811930f2e`）の比較を踏まえ、外形を参考にしつつ、他サービスで異なる`code`の意味や必須性をそのまま持ち込みません。外部SDKの例外形式とアプリのHTTP契約も分けます。

[ADR 0006](0006-typespec-api-contracts.md)に従い、HTTPヘッダー・本文・応答をTypeSpec原本から生成します。[ADR 0011](0011-access-and-diagnostics-isolation.md)の本番成果物からの除外は維持します。入出力、保存順序、受入条件の正式な定義は[MVP仕様書](../spec/mvp.md#検証用apiの契約)に集約します。文書化はAPIや回復処理の実装・実動作検証の完了を意味しません。
