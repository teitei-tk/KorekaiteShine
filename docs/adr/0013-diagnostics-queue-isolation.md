# D1とジョブ制御を共有し、診断のQueue・DLQを分ける

2026年11月2日合意。開発・テスト環境の診断データは共有D1内で正式データと区別し、配送には診断専用のQueue・DLQを使います。状態遷移・実行権・回復などの処理を検証しつつ、意図的な失敗による配送・滞留・DLQ受信を通常の評価と区別するためです。環境ごとの3 Workers・D1一つという構成は維持します。

## 検討した選択肢

- D1・Queue・DLQを共有し、用途で区別する：設定が少なく正式処理に近い経路を通せますが、意図的な失敗と通常の配送が混在し、観測や再実行で用途の絞り込みが必要になります。
- D1を共有し、Queue・DLQを診断専用にする：配送設定は増えますが、診断の滞留やDLQを独立して確認でき、3 Workersと共通のジョブ制御を維持できるため採用します。
- 診断用のWorkers・D1・DO・Queueを一式独立させる：破棄や負荷試験に向きますが、日常診断のために常設すると管理対象と構成差が増えます。実行ごとの独立テスト環境でこの役割を担います。

## 影響

ジョブ・実行権・outboxは共通のテーブルと処理を使い、用途を区別します。シナリオと確認結果は診断専用の関連テーブルに保存し、正式な一覧・集計へ混ぜません。スキーマとマイグレーションは[ADR 0008](0008-shared-d1-with-void.md)に従って一元管理します。

同じEvaluation Workerに用途別の配送入口を設け、AI呼び出し部分を診断用の固定スタブに差し替えます。ジョブ制御を複製しません。Queue本文は既定の2項目のままとし、受信QueueとD1の用途を照合します。定期回復やDLQ送信でも配送先の用途を維持します。DOは診断用の識別範囲を設け、正式な面接と同じインスタンスを使いません。

D1・Worker・本人全体の評価枠は共有するため、リソース競合や障害を完全には隔離しません。競合や大量投入は[ADR 0009](0009-explicit-environments.md)の独立テスト環境で確認します。診断経路の成功は正式Queueの接続設定の検証を代替しません。

[ADR 0011](0011-access-and-diagnostics-isolation.md)に従い、本番には診断入口・失敗注入・診断Queueバインディングを含めず、診断Queue・DLQも作成しません。空の診断用テーブルの存在と、診断コードの本番への組み込みは区別します。

複数Queueを同じConsumer Workerで受信する構成は[Cloudflareの公式資料](https://developers.cloudflare.com/queues/reference/how-queues-works/)にありますが、固定版Voidでの設定・起動は未検証です。正式な分離規則・受入条件は[MVP仕様書](../spec/mvp.md#診断データと配送経路の分離)へ集約します。用途不一致や存在しないジョブの通知は、[ADR 0014](0014-quarantine-invalid-job-notifications.md)に従ってD1へ隔離記録を保存してackします。
