# 不在・用途不一致の通知をD1に隔離してackする

2026年11月2日合意。存在しないジョブや用途不一致のQueue通知は、D1に配送異常の記録を保存してackします。判断または保存できないときだけretryします。時間を置いても回復しない異常と基盤の一時障害を区別し、異常な通知からAI実行やジョブ変更が起きることを防ぐためです。

## 検討した選択肢

- ログだけを残してackする：簡潔ですが、調査根拠と対応状況の永続的な管理が弱くなるため採用しません。
- 常に上限までretryしてDLQへ送る：標準の配送機能を使えますが、用途不一致など待っても直らない異常の発見が遅れ、無駄な配送が増えます。
- D1に隔離記録を保存してackする：記録の保守は増えますが、調査根拠を保持し、再試行を判断・保存不能時に限定できるため採用します。
- ジョブの自動復元や正しいQueueへの自動転送：原因となった設定不備を隠し、失われた入力の推測や用途境界を越える処理につながるため採用しません。

## 影響

[ADR 0012](0012-idempotent-diagnostics-api.md)ではジョブとoutboxを通知前に保存します。この順序を前提に、受付済みの書き込みを確認できる読み取りで不在を判定します。D1照会失敗は不在と扱わず、削除済み識別情報がある場合は遅延通知として処理し、復元しません。

[ADR 0013](0013-diagnostics-queue-isolation.md)の用途境界は受信時にも検証します。不一致では既存ジョブの状態・実行権・試行回数を変更せず、AIを呼びません。異常記録はジョブの存在に依存させず、受信QueueとメッセージIDで重複管理します。既存ジョブの正しい回復経路は維持します。

通常QueueとDLQで同じ分類を使い、新しい隔離QueueやDLQへの転送連鎖は設けません。隔離記録は自動回復の対象から外し、原因修正後にD1の状態を確認して必要な通知だけを再発行します。DLQ自身の保存失敗・再試行枯渇の運用は別途設計します。

分類・記録項目・ack条件・受入条件は[MVP仕様書](../spec/mvp.md#配送異常の記録と隔離)を正とします。これは配送規則の決定であり、実装や実動作検証の完了を意味しません。
