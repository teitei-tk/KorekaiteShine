# AIレビューの固定容量制限の監査

2026年10月27日、main `68dff9cd3062f510f8269edeb5dd02896f646391` を調査した。実装変更前の記録であり、以下の制限はまだ残っている。利用者の要求は「実行ごとの$1予算と処理時間による制御」である。

## 結論

300KBだけの問題ではない。入力作成、実行、結果検証に固定容量の拒否条件が分散している。入力側だけを変更すると、課金済みの結果を保存・投稿する段階で再び拒否される。現行コードの数値をAPIの公式上限として扱ってはいけない。

[費用設計](../superpowers/specs/2026-10-25-ai-review-dollar-budget-design.md#既存の容量時間制限との区別)にも「1回の資料容量、索引・Artifact・応答サイズを維持する」と記載していた。実装だけでなく設計段階で固定容量制限を残していたことが原因である。文書に記載があることは、利用者の最新指示への適合や数値の妥当性の根拠にならない。

## 入力と分割に残る制限

値は10進バイト。異なる場所で同じ値を検査する箇所も列挙する。

## 応答と投稿

| 場所                                                  | 制限                                                                     | 影響                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------- |
| `output-size.ts:2`、`review.ts:122`                   | モデル出力30,000バイト                                                   | usage精算後、JSON解析より前に拒否。費用内でも失敗する    |
| `output-size.ts:3`、`partition.ts:48`                 | 履歴応答の見積もり28,000バイト                                           | 30KB上限から2KBを引いた内製値で履歴作業を分割            |
| `task-schema.ts:52–60`、`partition-review.ts:161–163` | 履歴要約300文字、不確実性3件×150文字、根拠500文字                        | 応答契約。バイト数・トークン数とは別の制限               |
| `policy.ts`                                           | 要約1,500文字、指摘各項目1,000文字、不確実性5件×500文字、修正根拠500文字 | 読みやすさと結果形式の契約。入力資料の上限ではない       |
| `publish.ts:127`                                      | コメント60,000（JavaScript文字列長）                                     | 投稿直前の拒否。公式GitHub上限と同一だとは確認していない |

文字列長はUTF-16コード単位であり、バイト数・モデルのトークン数と同一ではない。モデルの出力8,000トークンという要求設定も30KBを根拠付けるものではない。

## バイト数以外の隠れた停止条件

同じ問題を残さないため、件数制限も併せて確認した。変更パス5,000、索引エントリ・資料ファイル5,000、確認対象5,000、境界の組合せ2,000、作業あたり確認対象200、過去指摘30がある。指摘の採用は最大3件である。これらは料金そのものの判定ではなく、削除・維持・置換を用途ごとに決める必要がある。

`budget.ts`には入力922,000トークン、usage各項目2,000,000、出力8,000の検証がある。これらはバイト上限ではないが、モデル制約と内製の値を区別して確認する。今回、外部サービスの最新上限の再確認は実施していない。

## 再現した事実と修正時の受け入れ条件

[PR #32](https://github.com/teitei-tk/KorekaiteShine/pull/32)では修正版の実行コードを照合した上で収集が失敗した。`partition.ts`の主資料2件と補助資料34件、本文312,353バイトが300,000バイト制限を超えた。PR #30の元の順方向差分でも同じ停止をローカルで再現した。

次の修正では、以下を一体で検証する。まだ実装・テスト追加は行っていない。

1. 元PR #30の固定base/headを使い、収集から投稿用Artifactの再検証まで通す。逆差分だけで代用しない。
2. 250KB・300KB・400KB・500KBを超えても、実トークン数と費用が許容範囲ならバイト数だけで拒否しないことを検証する。
3. 小さな入力でも残予算を超えれば生成せず、予算超過のPRコメントを投稿する。
4. 同じ料金条件でASCII・日本語・JSONエスケープを変え、バイト数による隠れた拒否を検出する。
5. 入力だけでなく、応答・IPC・plan・metadata・execution・最終結果・費用台帳・投稿側の読み直しまで通す。
6. 残す技術制限には用途・値の根拠・単位・超過時の処理・テストを記録する。費用超過と混同しない。
7. 実装中の新たな容量検査をこの一覧と照合し、実データでの同規模レビュー成功まで完了扱いしない。

調査対象は自前の `tools/ai-review` と関連Workflow、および設計書。依存SDK内部やGitHub/OpenAI側の制限まで網羅した監査ではない。Resolve操作、API課金を伴う追加実行、PRのマージは行っていない。
