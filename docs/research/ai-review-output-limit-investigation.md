# AIレビューが出力上限で停止した原因調査

2026年10月27日。対象実装は `c7aab2e2af70d7f34bee12a8d8f76d42896e8383`。調査のみで、修正・追加の有料レビュー・Resolve操作は実施していない。

## 結論

入力を送信できることと、担当範囲の確認を終えて回答を返せることを分けて設計・検証していなかった。固定バイト制限の修正では入力側だけを適応分割し、出力不足は回復不能な失敗として残した。これはモデルだけの問題ではなく、設計と検証の不足である。

「200件だから必ず8,000トークンを超える」とは証明していない。推論と可視出力の内訳を保存しておらず、今回どちらが何トークンを使ったかは復元できない。上限に達した事実と、その後停止する実装は確認できた。

## 原因となった判断

1. PR #25で導入した `MAX_OUTPUT = 8000` を、PR #33で入力側の制限を廃止した際に再評価しなかった。
2. PR #33の仕様に「料金不足・生成後の失敗は自動再試行しない」と明記した。無制限の再試行を避ける判断を、精算済みの出力不足への適応処理まで禁止する設計にしてしまった。
3. PR #34は直前の指摘位置不正と入力重複を修正したが、それで新たに一度に実行できるようになる担当量と出力需要を検証しなかった。
4. 実資料を使うモックテストを、実モデルの完走を裏付ける材料として強く扱いすぎた。テストが証明するのは形式・接続・保存・投稿であり、モデルの推論完了や実費用ではない。
5. 中断応答を安全に拒否する単体テストはあったが、中断後も同一実行内で予算を守って完走できるかという受け入れ試験がなかった。

[公式の推論ガイド](https://developers.openai.com/api/docs/guides/reasoning#allocating-space-for-reasoning)は、出力枠が推論にも使われ、可視回答が出る前に上限へ達し得ると説明している。今回保存したusageは合計のみで、この内訳を落としている。公式の初期余裕量を別の固定値としてコピーするだけでは、担当範囲との不整合は解決しない。

## 再発防止の受け入れ条件

次の設計・実装では以下を一組として扱い、上限値だけ変更して再度本番で試す手順を避ける。

1. 担当範囲・必須資料・推論を含む出力枠・残予算・残時間を要求ごとに決定する。固定バイト数を料金の代理にしない。
2. 出力不足のusageを先に精算し、次の要求が予算・期限内で処理を進められる場合だけ担当の再編成を許す。usage不明、権限、拒否、内容フィルターを一律に再試行しない。
3. 再編成しても資料が減らない場合、単一担当、候補整理、過去指摘確認を含む終了条件を決める。担当の欠落・重複や部分成功を許さない。
4. 安全な診断に要求出力枠、入力・出力・推論トークン数（取得できた場合）、経過時間、担当件数、再編成理由を保存する。生出力は保存しない。取得できない値を推定で埋めない。
5. 実API終了形式の中断応答を使い、精算→再編成→完了→Artifact保存・再読込→投稿までの回帰試験を追加する。回復不能時の$1超過防止・時間終了・日本語通知も同じ境界で試験する。
6. PR #30の元方向の固定資料とPR #32の同規模以上の実レビューを分けて検証する。コードSHA、head/base、全作業、総費用、保存、投稿を確認するまで完了と報告しない。

再発ゼロを調査だけで保証することはできない。今回の同じ見逃しを繰り返さないため、修正前にこれらの失敗経路を再現し、修正後に同じ試験で回復または意図した終了を確認する。

## 改善案への敵対的検証

同日、上記の受け入れ条件を現実装に適用した場合の反例を検証した。結論は「方針には賛成できるが、そのまま実装に移れる詳細設計ではない」。以下は新実装の不具合認定ではなく、案がまだ防いでいない失敗経路である。

### 1. 予算が残っているだけでは再試行の根拠にならない

今回と同じ入力390,911・出力8,000・cache write390,908を返し続ける敵対的応答を、実際の `BudgetLedger` へ順番に精算した。9回で$0.9335484を消費し、10回目の予約は `COST_BUDGET_EXCEEDED` になった。$1の保護は働くが、担当が一件も完了しないまま予算を消費し得る。この試験は将来の実API料金やキャッシュ命中の予測ではない。

案には「次の要求で処理が進む」の判定が欠けている。同一要求・同一出力枠の再送を回復策とせず、担当範囲、必須文脈、出力枠のどれを変更するかを明示する。子要求と後続作業の負担も比較し、親を失敗させてから考えるだけの方式を避ける。ただし未来の実費用や成功率を確定値として扱わない。

### 2. 単一担当・履歴確認は二分割できない

履歴は既に1件単位であり、単一の契約確認もこれ以上IDを二分できない。出力不足時に分割だけを選べば、同じ未完了で停止する。逆に必須原文を削ると確認の品質を落とす。

単一担当では、残予算・モデルのコンテキスト制約・残時間に収まる出力枠の調整を許すか、別の担当定義へ再編成するかを決める必要がある。どちらも不可能なら、原因を説明して未完了で終了する。「同規模なら必ず成功」とは約束できない。

### 3. 候補整理の分割は重複判定を壊し得る

既存の「再分割した候補整理では別の子作業にしか渡していない原文を引用できない」テストを再実行した。1件成功、26件スキップ。これは候補整理の成功を示すテストではなく、相手の原文がない重複判断を正しく拒否するテストである。

反例は候補AとBを別の子作業へ分け、AをBの重複と判断する場合。各子には全候補の本文が渡るが、原文は担当候補側に限定されるため、根拠検証が拒否する。逆に全原文を毎回戻せば分割効果が失われる。

候補IDの単純二分ではなく、比較対象の関係と必要原文を同じ作業に割り当てる設計が必要。別バッチの重複、重複の循環、重複先がrejectされた場合も、正しい採否へ到達する回帰試験を要する。検証を緩めて通す方法は採らない。

### 4. 出力枠・費用台帳・実行記録は一緒に変えないと整合しない

APIの出力枠だけを16,000へ変更した想定で、8,001出力トークンのusageを現行の `validUsage` に渡すとfalseになった。成果物にもcalls×8,000の条件が残る。一方、再試行を追加するだけなら費用台帳には失敗分が入るが、実行記録のusageには成功分しか入らない。

要求ごとに出力予約枠と結果を記録し、計数のみ・生成開始・usage精算済み・usage不明・担当完了を区別する必要がある。失敗親と成功子を含めた総課金usageの正本を費用台帳に定め、Artifactにも同じ意味で反映する。台帳形式を変える場合は旧Artifactの扱いも明記する。

### 5. タイムアウト後の安易な再試行は費用不明の要求を増やす

出力枠を増やしても生成150秒・子プロセス200秒のままなら、応答前に時間切れとなり得る。クライアントの中断だけでサーバー側の課金終了を断定してはいけない。usage不明の予約を保持して追加生成を停止する既存方針を維持する。

残時間が計数・認証・生成を賄えない時点では開始せず、全体期限から子処理の期限を導く。期限直前の精算、応答と中断の競合、worker終了後の通知を試験する。単にタイムアウトを延ばして次のCI上限へぶつけない。

### 検証の合格条件への追加

- 最初の生成だけでなく、失敗した親、成功した片方の子、失敗したもう片方の子、候補整理失敗、保存失敗、投稿途中失敗を区別する。
- 最後の子が未完了なら親は完了にしない。途中で生成した候補や修正確認は投稿しない。
- 意味上の重複を分割境界越しに正しく整理できるケースを、拒否テストだけでなく成功テストでも確認する。
- $1未満で終了することとレビュー完走を別々にassertする。費用不足を正しく通知できても完走成功とは扱わない。
- PR #30固定実資料の成功モックは配線検証として維持し、中断から回復する試験と実レビューの証拠で補う。

実装・有料APIの再実行・Resolve操作は行っていない。
