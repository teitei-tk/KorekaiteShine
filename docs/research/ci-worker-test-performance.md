## 検査範囲と設定

Vitestの実際の列挙結果では、変更前は境界23ファイルと結合8ファイルの交差集合が`http-contract.test.ts`でした。結合コマンドから同ファイルを外すと、境界23・結合7ファイル、交差集合なし、変更前と同じ和集合30ファイルとなりました。環境共有のために追加する回帰テストはこの既存範囲と分けて扱います。

mainのBranch protection APIは未設定を返し、有効なruleset `26424032`にはPR必須・削除禁止・force push禁止のみがあり、旧ジョブ名を必須とするルールはありませんでした。2ジョブ分割後もActionsロックは更新不要で、`gh actions-lock --verify`が成功しました。

中央値は89.93秒から46.47秒へ約48%短縮しました。ケース間清掃8回を加えたためDBコマンドは21回から29回へ増えましたが、起動を8回から1回へ減らした効果が上回りました。これはローカルのファイル単位の比較であり、CI全体の短縮率ではありません。共有マシンの負荷のばらつきも含むため、秒数は固定の性能保証ではありません。

残る負荷はDB CLIの呼び出しです。部分失敗ケースは投入3回と照合6回があり、投入の一括化と送信前後ごとの照合の一括化が候補です。本変更では既存の業務条件の検査を維持し、任意SQLのHTTP入口追加や他ファイルへの共有化は行っていません。

通常検査は`pnpm test --maxWorkers=2`で530件成功しました。既定並列度での一度の実行は、他worktreeのWorker検証と重なり、12件が起動45秒またはテスト60・120秒の上限で失敗しました。既存の時間上限を伸ばさず、ローカル検証の並列度を抑えて確認しています。CIの並列度は変更していません。

逆順実行は8件成功（49.08秒）、単独実行は1件成功（12.63秒）。別プロセスでの同時実行は両方8件成功し、異なるD1識別子と各1回の起動を確認しました。計測用の一時コードは削除しました。

状態混入の回帰テストは、清掃なしでは次ケースに2件の古い通知が現れて失敗し、清掃後は成功しました。起動・検査・清掃・停止の失敗、起動中の停止、清掃中の停止・タイムアウトも回帰テストで確認しています。独立レビューで指摘された「清掃完了後に停止状態から復帰する競合」は、2ケースのRed/Greenで修正しました。

一時計測コードを除いた最終状態で`pnpm check`が成功しました（ローカル同時実行数4、通常530件・文書67件、Node.js設定・Lint・整形・型検査も成功）。`pnpm prepare:integration`の後の`pnpm test:integration`は7ファイル・15件が640.27秒で成功し、実時間の再試行・停止後回復と開発DBの保持を確認しました。

GitHub CIの実測は実装PRの本文に、対象head SHA・実行URL・各ジョブの開始終了時刻とともに記録します。ローカルの48%短縮と、CIのジョブ並列化による短縮を区別します。
