# 公式CodexでPRコードの実行を禁止できるか

2026年10月27日。対象は、公式Codex ActionとCLIでリポジトリ探索を維持しながら、PR由来コードの実行を厳密に禁止する構成である。実装・設定変更・モデル呼び出しは行っていない。

## 結論

調査後の判断: 利用者は2026年10月27日、公式`unprivileged-user`で資格情報を隔離した読み取り専用環境内のPRコード実行を許容した。[現行の設計案](../superpowers/specs/2026-10-27-existing-review-wif-design.md)では厳密な非実行を要件から外している。以下はその判断前の調査記録であり、非実行を理由とする保留条件は現在の方針ではない。

**現在の設計候補である読み取り専用設定と非対話実行だけでは、PRコードの実行は禁止できない。公式機能だけで探索と厳密な実行禁止を両立する具体的な設定は、今回の調査でも確認できなかった。** 公式機能で絶対に不可能と証明したわけではないが、導入可能と断定する根拠は不足している。

固定版0.164.0のソースと設定Schemaを確認した。禁止するコマンドを個別に列挙する方法を、任意のPRコードの実行禁止と同一視しない。また、危険性の判定やプロンプトで「実行しない」と頼むことも、厳密な強制とは区別する。

## 公式機能で確認できたこと

| 機能                        | 確認結果                                                                                       | 今回の要件との関係                                                           |
| --------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 読み取り専用プロファイル    | ファイル書き込み等を制限する                                                                   | ファイルを読むだけのPR内Python・シェル等を実行することとは別                 |
| 承認ポリシー`never`         | 規則に一致せず危険コマンドとも判定されなかったコマンドは、サンドボックスに保護を任せて許可する | 未登録コマンドをすべて拒否する設定ではない                                   |
| `prefix_rule`の`forbidden`  | 一致したコマンドを拒否する                                                                     | インタープリター、別名、シェル経由等を有限の列挙で完全に覆う根拠にはならない |
| `prefix_rule`の`allow`      | 明示許可によりサンドボックス外で実行する経路がある                                             | 調査コマンドだけを安全に許す設定として安易に使わない                         |
| `features.shell_tool=false` | シェルツールの登録を止められる                                                                 | ユーザーの既存実装のプロンプトが使う`git diff`やファイル探索も止まる         |
| `requirements.toml`の規則   | 管理側からprompt/forbiddenを強制できる。allowは受け付けない                                    | これだけで「指定した読取操作以外はすべて拒否」になるわけではない             |

根拠: [未一致コマンドの処理][exec-policy]、[シェルツールの登録][spec-plan]、[管理側ルール][requirements]、[設定Schema][schema]、[公式Rules説明][rules]。

固定版のツール登録で、shellを無効にした場合にユーザーの既存実装のローカルGit・原文探索をそのまま置換する専用の読取ツールは確認できなかった。MCPリソース読取機能はあるが、別の提供元が必要である。独自読取MCPや実行代理を新設することは、今回の「独自実装を最小限にする」設計に含めない。

プロジェクトをuntrustedとして扱う設定も調査対象とした。内部には未登録コマンドで承認を求める経路があるが、無人実行で必要な探索だけを継続させる構成としては検証できていない。対話承認を必要とする方式を、そのまま自動レビューの解決策にはしない。[未一致コマンドの処理][exec-policy]

## 反例と必要な検証

PR内に、何も書き換えず計算結果だけを標準出力へ出すスクリプトがあるとする。Codexがインタープリターを通じて実行しても、読み取り専用という制限には必ずしも反しない。サンドボックスの外へ出る要求をしなくても実行できるため、昇格だけを禁止しても「PRコード非実行」の証明にならない。

今後、両立する公式設定が見つかった場合は、少なくとも次を無害なfixtureで検証する。

- Git差分と必要なファイルを読める。
- PR内スクリプトの直接実行、インタープリター経由、シェル経由の実行を拒否する。
- PR側の設定・MCP・フック・実行ファイルの別名を使って制限を回避できない。
- 許可した調査コマンドに実行オプションや別プログラムの呼び出しを付けても、任意実行に変わらない。
- Actionの保護設定が、その設定の指定方法を拒否したり上書きしたりしない。

今回は固定版CLIの実行検証を行っていない。上記はソースから導いた反例と検証条件であり、資格情報流出や実サービスへの攻撃を実証したものではない。

## 設計への反映

「公式機能を設定すればPRコード非実行が実現する」という前提を外し、実装開始を妨げる未解決条件として明記する。資格情報を隔離したサンドボックス内でPRコードの実行を許容する案は別の要件であり、利用者の承認なしに置き換えない。独自サンドボックスやコマンド代理を追加して解決することもしない。

独自実装を増やさず進めるための候補は、公式機能での両立を検証するか、別途利用者が「隔離環境内の実行は許容する」と判断することである。本調査では後者を選択していない。
