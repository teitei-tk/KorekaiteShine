# 履歴改訂検知と投稿再開の再検証

2026年10月28日。[更新後の設計](../superpowers/specs/2026-10-27-existing-review-wif-design.md)を、履歴の改訂検知、途中投稿の再開、独自実装の範囲に絞って検証した。設計本文・実装・Workflowは変更していない。

検証後の対応: 2026年10月28日、利用者の指示により、再開保証の前提と手動削除時の扱いを[設計案](../superpowers/specs/2026-10-27-existing-review-wif-design.md)へ反映した。独自DB・監視基盤は追加しない。以下は変更前の検証結果であり、実装による検証は未実施である。

## 結論

通常の部分失敗からの再開について、改訂検知と操作照合の順序に矛盾は見つからなかった。前回指摘した固定ページ数の廃止と、履歴読取・改訂検知の責務分離も反映されている。

新たなP2は1件。固定Artifactと現在のGitHubコメントだけでは検知できない削除があり、外部変更時の停止と投稿再開の保証範囲を明確にする必要がある。独自DBやイベント監視を増やすことは推奨しない。現在の構成で観測できる状態に保証を限定し、限界を運用へ明示する方が、独自実装を最小限にする方針に合う。

## P2: 応答喪失後に削除された返信と、未投稿を区別できない

対象は設計の「保存と投稿」、特に再開契約の3〜5と、外部の履歴変更で停止する条件である。

反例は次の順序になる。

1. Artifactには元指摘の履歴と返信操作Aが固定されている。
2. GitHubでAの投稿は成功するが、投稿ジョブは応答を受け取れず終了する。
3. 再試行までに、権限を持つ利用者がその返信を削除する。
4. 再試行では操作Aのマーカーが見つからず、元指摘の本文・返信・Resolve状態は生成時と同じに見える。
5. 設計の手順ではAを未投稿として再作成できてしまう。

GitHubはレビューコメントの削除APIを提供している。[公式仕様](https://docs.github.com/en/rest/pulls/comments#delete-a-review-comment-for-a-pull-request)

この場合、固定Artifactと比較対象の現在の履歴は「Aを一度も投稿していない場合」と一致する。操作IDや本文ハッシュを増やしても、消えたコメント自体を照合できない。生成時から存在した元コメントの削除とは異なり、削除された返信IDも生成時のArtifactにはない。人間が取り除いた返信を再作成する可能性があるため、外部変更を必ず検知して停止できるという広い保証とは両立しない。

**最小限の修正提案:** 再開保証の前提として、操作マーカー付きコメントが保持され、読取可能であることを明記する。改訂検知は取得時点で観測できる差異を対象とし、取得の間に追加・削除されて消えた変更の検知は保証しない。途中投稿を手動削除した場合は同じArtifactの再試行を避ける運用と、誤って再試行した場合に再作成され得る限界を記載する。これは現行設計への提案であり、保証範囲の変更を採用済みとは扱わない。

手動削除後も自動的に停止する保証が必要なら、現在の構成では満たせない。成功応答後だけ保存する台帳では、応答喪失の窓は埋まらない。独自の投稿台帳や監視基盤を安易に追加せず、要件と負担を再判断する必要がある。

## 矛盾がないと判断した手順

以下は設計の契約を静的に追った結果であり、未実装のTypeScriptや実GitHubでの成功を示すものではない。

| 状況                                          | 設計から導かれる動作                               | 判定                                       |
| --------------------------------------------- | -------------------------------------------------- | ------------------------------------------ |
| A返信成功、B返信失敗、Aは保持されている       | Aを操作照合後に比較から除外し、Bだけ投稿           | 整合                                       |
| A成功の応答だけ喪失、Aは保持されている        | 操作ID・投稿者・対象・本文からAを確認して省略      | 整合                                       |
| 自分の返信後、人間の追記が残っている          | 自分の返信だけ除外し、人間の追記による不一致で停止 | 整合                                       |
| 元コメント編集、Resolve状態の変更が残っている | 生成時スナップショットとの不一致で停止             | 整合                                       |
| 同じbotの別実行が返信する                     | 当該Artifactの操作として認めず停止                 | 整合                                       |
| マーカー一致、本文不一致                      | 投稿済みと認めず停止                               | 整合                                       |
| APIの取得順だけが変化                         | 同じID集合を同じ順序へ整えて比較                   | 整合                                       |
| 初回投稿で複数操作を実施                      | 各書き込み前の再確認でも同じ操作照合を使う         | 整合。開始時の履歴へ単純比較してはいけない |

新規指摘スレッドを識別して比較から除く場合も、スレッド全体を無条件に捨ててはいけない。確認済みの自分の投稿だけを除き、そこへの人間の返信やResolve変更は残す必要がある。現設計は「確認済み書き込みだけ」「Resolve変更が残れば停止」としているため、追加の矛盾とは数えない。

書き込み直前の検査とGitHubへの投稿は別リクエストであり、検査後の人間の変更まで原子的に排除する構成ではない。返信APIの公開パラメーターには履歴改訂値との比較更新条件は記載されていない。PR単位の投稿直列化も、人間の操作をロックする意味ではない。この競合窓は実運用上の限界として区別する。[返信API](https://docs.github.com/en/rest/pulls/comments#create-a-reply-for-a-review-comment)

## 独自実装の最小化

再利用範囲は前回より明確になっている。既存の通信、旧マーカー解析、表示、認可、状態通知を再利用し、追加部分を共通スナップショットと固定操作の照合に集約する方針は妥当である。別の履歴エンジン、再開専用エンジン、旧分割・費用台帳の互換層は不要と明記されている。

この要件を保つ限り、外部変更の判定と投稿済み操作の識別は省けない。さらに保証を強めるための新DB・監視・汎用実行基盤を追加するより、P2で示した観測限界を明示することを推奨する。「最小」であることを実装量で証明したわけではなく、設計上不要な仕組みを増やしていないという評価である。
