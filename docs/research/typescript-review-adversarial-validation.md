# TypeScript版AIレビュー設計の敵対的検証

2026年10月28日。[設計案](../superpowers/specs/2026-10-27-existing-review-wif-design.md)のTypeScript変更後を、現在のコードと照合した。読者は設計の採否を判断する利用者と実装担当者。実装・Workflow・認証設定は変更していない。

検証後の対応: 2026年10月28日、P2のページ数上限廃止と、履歴改訂・投稿再開の再利用境界を[設計案](../superpowers/specs/2026-10-27-existing-review-wif-design.md)へ反映した。以下は変更前に確認した結果であり、実装による解消は未検証である。

## 結論

新たな指摘はP2が1件。TypeScriptの再利用元に残る独自のページ数上限を、設計の廃止対象へ追加する必要がある。前回の2件への対応方針は設計に残っており、TypeScript変更によって取り消されてはいない。

独自実装を減らす方向は妥当である。認証・探索・モデル実行を公式側へ任せ、Goの実行環境も増やさない。ただし、履歴の改訂検知と投稿再開は独自処理として残る。「既存TypeScriptの接続変更だけで済む」とは評価できない。実装量の最小化は、下記の責務分離を守れることを条件とする。

## P2: 再利用元の10ページ上限で、30指摘以内でも取得を拒否する

設計の「保存と投稿」「独自実装を残す範囲」は既存TypeScriptのGitHub通信を再利用し、「レビューと出力」は履歴の独自上限を廃止する。一方、廃止対象は参照元の20返信・16KiB・128KiBに限られ、現在のTypeScriptにある別の上限が抜けている。

[github.ts](../../tools/ai-review/github.ts)の`pages`（60〜68行）は100件ずつ最大10ページを取得し、10ページ目が100件ならエラーにする。通常コメントとレビューコメントの両方に適用され、自システムの指摘を選別する前に動く。AI指摘が30件以内でも、他のコメントを含めて1,000件あるPRは拒否される。これはAPIのエラーやジョブ期限ではなく、独自の固定上限である。

**再現:** 現行の`comments`を直接呼び、各ページ100件を正常に返すモックAPIを渡した。10回の取得後に`コメント取得上限を超えました`で停止した。11ページ目が空で取得完了になるケースにも到達できない。ネットワーク通信は行っていない。

**修正提案:** このページ数上限も引き継がないと明記する。取得終了を確認するまでページを読み、実際のAPI失敗や期限超過なら未完了とする。固定値の引き上げ、古いコメントの切捨て、独自の分割基盤の追加は不要。受け入れ条件には、30指摘以内で総コメントが1,000件・1,001件の場合を追加する。

これは将来の実装に既に不具合が存在するという指摘ではなく、既存通信処理の再利用に伴う設計上の取りこぼしである。

## 再利用できる範囲と追加実装が必要な範囲

### 指摘の読取と、履歴の改訂検知は別の責務

[history.ts](../../tools/ai-review/history.ts)の`reviewHistory`が返すのは元指摘であり、返信本文やResolve状態を含むスナップショットではない。`readInlineHistory`は返信を除外する。[github.ts](../../tools/ai-review/github.ts)のコメント型にもResolve状態はない。

**再現:** 元のAI指摘1件だけの場合と、それに人間の返信を追加した場合で`reviewHistory`の戻り値を比較した。両者は同じだった。現行の[publish.ts](../../tools/ai-review/publish.ts)もこの戻り値同士を比較しているため、この比較をそのまま新設計の履歴改訂検査に使えない。

設計自体は返信・Resolve変更での停止を既に要求しているため、これは新たな設計違反として数えない。ただし、旧マーカーの読取を再利用することと、履歴改訂の検査を再利用することは区別する必要がある。取得した原文とスレッド状態から作るスナップショットを生成・投稿で共用し、操作IDで照合した自分の書き込みだけを除外する契約が必要である。Go側とTypeScript側の履歴エンジンを二つ残す構成は不要。

### 準備・投稿・Artifactを丸ごと再利用しない

[prepare.ts](../../tools/ai-review/prepare.ts)は分割の事前検査と資料収集に依存する。[artifact.ts](../../tools/ai-review/artifact.ts)は分割計画・完了タスク・課金情報を検証し、[publish.ts](../../tools/ai-review/publish.ts)にも予算処理が結び付いている。これらは新方式へそのまま接続できない。

設計には既に切り離す方針があり、ここも新たな指摘ではない。既存検証器を通すための仮の分割計画・利用量・課金台帳を作ると、公式側へ任せた処理が互換層として残ってしまう。新しいArtifactの入口で対象・生成元・結果・履歴を一度検証し、旧方式の型や台帳へ変換しないことが重要である。

| 領域                                             | 最小化する方針                                                         |
| ------------------------------------------------ | ---------------------------------------------------------------------- |
| WIF交換・更新、モデル実行・探索                  | 公式プロキシ・Action・CLIへ委ねる既定方針を維持                        |
| PRの認可、旧マーカー、返信状態、本文の安全な表示 | 現行TypeScriptから要件に合う処理とテストを再利用                       |
| 履歴取得・改訂検知                               | 原文と状態の取得を一か所へ集約。元指摘の読取結果を改訂値の代用にしない |
| 結果保存・投稿再開                               | 新形式のArtifactと一つの投稿処理に限定。旧方式との二重検証や新DBは不要 |
| 状態表示・失敗通知                               | 既存の状態形式との接続を一か所に限定                                   |
| 分割・横断確認・候補統合・費用台帳・独自WIF交換  | 新方式の実行経路から外す。互換目的のダミー入力を作らない               |

独自処理の残量が大きいのは、言語ではなく、過去指摘の互換・状態変更時だけの返信・途中投稿の再開という要件による。これらを維持したまま公式のモデル実行機能だけで全て代替できるとは確認していない。削減のために合意済み要件を落とす提案はしない。
