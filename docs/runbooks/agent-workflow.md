# エージェントの調査とレビュー引き継ぎ

認証設定を確認するとき、大きなツール結果を扱うとき、レビューを委譲するとき、PRを作成・更新した作業を終了するときに参照します。

## 認証設定の確認

AIレビューのRepository Variablesは、ルートから`pnpm check:ai-settings`で確認します。取得値を含む`gh variable list --json name,value`等の直接出力は使わず、[初期設定手順](ai-review.md#登録値を表示せず確認する)に従います。取得失敗は認証切れと断定せず、接続・権限を確認します。ネットワーク制限のあるサンドボックスでは最初から外で実行します。

## ツール出力の絞り込み

- 検索は`rg`で候補を絞り、必要な範囲を読みます。同じ内容は保持済みの結果を再利用し、ファイル・リビジョンが変わったときに読み直します。
- 大きなツール応答は変数やセッション内ストアに保持し、状態・件数・次の判断に必要な証拠だけを表示します。JSON全体を`text(result)`で繰り返し出力しません。エラーは成功扱いせず、機密値を除いた原因を確認します。
- 原本の保存が必要なスキャンでは、プラグイン指定の成果物保存・取得機構を使います。表示の省略によって、必須の確認範囲や証拠を省略しません。
- 認証値を含む応答はファイルや共有ストアへ保存せず、専用コマンド内で判定します。エラーや未知のフィールドも機密値を含み得るものとして扱います。
- 進捗は状態が変わるまで待ち、同じ巨大な結果をポーリングしません。検査は変更後とcommit・push時の必要な実行にとどめ、成功後は変更や未解決の懸念がない限り追加で繰り返しません。

## Actionsの状態確認

`pnpm check:ai-run <AIレビュー実行ID>`で単発確認し、完了まで待つ場合は`--watch`を付けます。対象はこのリポジトリに固定しています。GitHubへの接続はネットワーク制限のあるサンドボックス外で実行します。

修正版の検証では`--expect-commit <40桁SHA>`を指定します。例：`pnpm check:ai-run <AIレビュー実行ID> --expect-commit <mainに入った修正SHA> --watch`。実行コードSHAと、元CIに記録されたレビュー対象のhead/base SHAを分けて表示し、期待コミットが実行コードの履歴に含まれるか照合します。squashマージでは元ブランチのSHAではなく、mainへ取り込まれたコミットSHAを指定します。包含確認は実装の存在の確認であり、動作成功の証明ではありません。

`--expect-commit`指定時に、期待コミットを含まない場合、AIレビュー以外の実行IDの場合、元CIからレビュー対象を特定できない場合は「修正版の検証対象外」と表示して終了コード3にします。取得・解析失敗は2です。期待コミットを省略した場合は「包含は未確認」と表示し、修正版の検証済みとは扱いません。クローズ済みPRなどで元CIのPR情報が空の場合も、実行版の包含判定は表示しますが、レビュー対象は特定不能として扱います。期待コミット省略時は従来どおり状態監視を続けます。現在のPRのSHAを過去の実行へ代入しません。実行コードSHAは、このリポジトリのAIレビューWorkflowが`github.sha`をcheckoutする構成に対応します。

監視は15秒間隔、最大40回です。状態が変化したときだけ出力します。固定したジョブ・ステップ名以外は位置番号で示し、未知の名前・生ログ・外部エラー本文は出力しません。`GH_DEBUG`も無効にします。原因の詳細が必要なら、表示された実行URLで該当ステップを確認します。このコマンドはログ取得、実行の開始・再実行・停止、Variablesの変更を行いません。

終了コードは完了成功が0、完了失敗・キャンセル・スキップ等が1、取得失敗・不正入力・監視上限が2です。単発確認で進行中の場合も0を返すため、成功の判断には表示の`completed / success`と必要なステップの成功を確認します。監視上限になってもGitHub側の実行は継続します。既存の認証設定確認と同様、管理者用の読み取り専用コマンドであり、通常CIやLefthookからは呼びません。

## レビュー担当へ渡す情報

委譲が許可され、独立したレビューが必要な場合は、新しいコンテキスト（対応ツールでは`fork_turns: "none"`）を基本にします。全会話のコピーに代えて、次を渡します。

1. リポジトリの絶対パス、比較元・比較先のSHA。未コミット変更では未追跡を含む対象一覧と、レビュー中に変更しない前提。
2. ユーザーが求めた仕様・受け入れ条件と、確認に必要な仕様書・ADR・規約のパス。
3. 担当するファイル・観点、他の担当との境界、必要時に読める関連コード。
4. 読み取り専用などの制約、実行済み検査、未検証事項。認証値や会話全体は含めません。
5. 戻り値は指摘・根拠の位置・確認済み範囲・未解決事項に限定し、ソース全文やツール応答の再掲を求めません。

仕様の補足や修正が届いたら、影響する担当へ要点を追加します。固定した差分が変わった場合はその事実と新しいSHAを伝え、古いレビューを最新のものとして扱いません。主担当は必要な証拠を確認し、未確認の範囲を明示します。

## PRを扱った作業の完了条件

作業を終了する前に、今回作成・更新したPRについて次を確認し、最終報告に残す。別チャットが担当するPRは今回の整理対象から外す。

1. 各PRのURL、最終head、検査結果と最終状態（マージ済み・未マージでクローズ・オープン）を確認する。
2. オープンで残すPRには、残す理由と次の対応を明記する。検証用・不要になった案・取り込み待ちを区別する。
3. 検証用PRを閉じる前に、残すべき回帰テストを確認する。移管する場合は移管先PRと検証結果を元PRへ記載する。移管先が未マージなら、その状態も報告する。
4. マージ・クローズは利用者が承認した範囲内で行う。クローズの承認がないPRは、閉じる理由を提示してオープンで残す。不要なPRの自動クローズや、他のPRへの承認の流用は行わない。
5. コメント・検証履歴を保持し、PR整理に伴ってレビュースレッドのResolve状態を変更しない。

「実装・検証が成功した」だけでは整理完了としない。残るPRの理由とテストの移管先まで確認できたことを完了条件とする。
