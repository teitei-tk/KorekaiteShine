# AIレビューの分割と横断確認の設計

2026年10月25日作成。利用者が選択した「関連単位で分割レビュー＋横断確認」を具体化し、利用者の承認を受けた設計です。実装と回帰テストを追加しました。有料の実PR検証とmainへの反映は未実施です。上限引き上げの[PR #13](https://github.com/teitei-tk/KorekaiteShine/pull/13)はマージしません。

以下の数値、分割規則、失敗時の投稿方針を実装の初期値とします。[コメントと修正確認の要件](ai-review.md)と併せて参照してください。[設計基準](mvp.md#設計基準)に従い、責務・費用・再試行を明確にします。アプリの評価処理に関する[根拠固定のADR](../adr/0003-immutable-evaluation-evidence.md)は変更せず、AIレビューでも入力を固定する既存方針を維持します。

## 解決する問題

現行の収集処理は差分に加え、対象拡張子のファイルをbaseとheadから広く収集します。変更と無関係なファイルも容量を消費し、リポジトリの成長によって小さなPRでも失敗します。PR #12の調査では差分46,145バイト、スナップショット330,108バイト、合計376,253バイトとなり、300,000バイトの収集上限を超えました。

上限を引き上げるだけでは再発します。変更に必要な資料を選び、有限の大きさの確認作業へ分割します。分割による境界の見落としを補う横断確認と、確認対象の台帳を組み合わせます。「全コードを読んだ」「不具合がない」という保証ではなく、指定した確認対象を処理し終えたかを明示します。

## 比較した方式

| 方式                            | 利点                                          | 負担・限界                                 | 判断                     |
| ------------------------------- | --------------------------------------------- | ------------------------------------------ | ------------------------ |
| 差分と関連資料を選んで1回で確認 | 小さな変更で安価、構成が単純                  | 関連変更が増えると1回の上限に再び達する    | 資料選択の考え方だけ採用 |
| 関連単位で分割し、境界も確認    | 1回の容量を抑え、変更量に応じて処理を増やせる | 呼び出し回数、統合、確認範囲の管理が必要   | 利用者が選択             |
| モデルが必要な資料を追加取得    | 必要箇所を柔軟に追える                        | ツール権限、終了条件、費用管理が複雑になる | 初期実装では採用しない   |

新しいクラウドサービスや永続DBは追加しません。既存のGitHub Actions、固定モデル、構造化出力、Artifactを利用します。PR内コードの実行、モデルへのツール付与、自動Resolve・再オープンは行いません。

## 処理の流れと責務

1. 信頼済みコードがPR番号、base/head、起点CI、履歴を確認し、対象を固定する。
2. Gitから変更一覧と参照関係を読み、確認対象の台帳と資料を作る。
3. 関連単位ごとに新規指摘候補を生成する。
4. 単位をまたぐ契約・呼び出し・設定・仕様の整合性を、原文付きで横断確認する。
5. 過去の指摘を別枠で確認する。手順3・4の指摘件数には依存しない。
6. 信頼済みコードが対象の網羅、根拠、重複、容量を検証し、投稿内容を固定する。
7. 投稿専用ジョブが現在のPRと履歴を再確認し、該当行への指摘、元スレッドへの返信、完了概要の順に投稿する。

初期実装は逐次実行とし、並列制御やモデルによる自由な探索は追加しません。各段階の結果を次へ渡す前に形式検証します。モデルの自己申告だけでは確認対象の充足を判定しません。

## 資料選択と関連単位

### 確認対象の台帳

台帳には対象SHA、収集・プロンプト・スキーマの版、変更ファイルと差分範囲、参照関係、関連単位、横断確認対象、過去指摘IDを記録します。各資料はリビジョン、パス、行範囲、内容ハッシュで識別します。各対象には担当する作業IDと完了状態を持たせます。

追加だけでなく削除、改名相当の削除・追加、変更された設定・文書も列挙します。除外対象は理由を残します。既存の秘密情報・ロックファイル・バイナリ等の除外方針を維持し、対象コードの確認に必須の資料が除外される場合は未確認として扱います。除外ファイルの内容を外部送信して解決しません。

### 初期実装の関連付け

変更差分を起点に、信頼済み収集処理で次を静的に関連付けます。PRのスクリプトや設定を実行して解決しません。

- TypeScript・JavaScriptのリポジトリ内import/export、import型、import-equalsと逆参照。変更された公開契約の利用側、関連テストを含める。
- Workflowから起動するスクリプト、package scripts、設定ファイルの明示的な参照。
- Markdownのローカルリンクと、信頼済み設定で指定する領域別の仕様・ADR・規約。

初期対応は相対参照と静的に解決できる設定に限定します。動的参照や解決できないaliasを検出した場合は未解決の関係として記録します。任意の動的依存を完全に検出できるとは扱いません。検出した未解決関係が変更の評価に必要なら、その確認は未完了にします。

変更箇所と直接の参照先・利用側から作業単位を作ります。関連ファイル全体の連結成分を一つの入力にする方法は採りません。巨大な共通モジュールに全変更が連結しても、容量に応じて分けられるようにします。分割順はパス・差分位置で安定させ、境界を横断確認の台帳へ登録します。

各入力には差分、変更を含む関数・型・Markdown節、必要な利用側とテスト・仕様を原文で入れます。base/headで同一の内容は重複を避け、削除前の挙動はbaseを参照します。必須部分が収まらなければ関数・節・差分範囲ごとに分割します。分割して意味が失われる単一対象は未完了にし、機械的な末尾切り捨てや要約だけで代替しません。

全リポジトリの本文を一つのJSONに保持する処理は廃止します。ファイル一覧・参照索引と、必要時に読み出す原文を分離します。索引作成にも読み取り件数・バイト数・時間の制限を設け、超過を通知します。リポジトリ全体の160ファイル制限をレビュー可能範囲の定義として使い続けません。

## 横断確認

横断確認には、単位ごとの結果に加えて、分割境界の両側の原文、公開型・入出力、利用側、設定・仕様を渡します。候補指摘の要約だけでは契約の不一致を判断しません。例として、API応答型と利用側、履歴形式と読み取り処理、Workflowの入力とCLI引数を同じ確認対象にします。

単位間の依存辺だけでなく、変更領域に指定した共通契約・仕様との対応も台帳に登録します。横断資料も容量を超えたら契約ごとに分割し、同じ境界に関する両側の根拠を一緒に渡します。すべてを最後の巨大なプロンプトに戻す処理は設けません。全体にまたがる不変条件を分割できず収まらない場合は未完了です。

## 過去指摘と結果の統合

過去指摘は最大30件を別枠で扱い、指摘本文、元の位置・コミット、現在の関連原文を使って全IDを確認します。変更差分に現れない指摘も省略しません。各IDに修正済み・未修正・判断不能のいずれかと根拠を要求し、行の移動やResolve状態だけで修正済みにしません。

単位レビュー・横断確認の候補には根拠となる資料IDと行を付けます。候補は各呼び出し最大3件、最終投稿も従来どおり最大3件です。候補数の上限はレビュー範囲の省略を許可する意味ではありません。投稿候補の優先順はP1、P2、パス、行の順とし、候補総数と採用数を概要に残します。

同じファイル・発生条件の重複判定と、履歴の形式検証を分離する既存方針を維持します。既存指摘との対応IDを各モデルへ要求し、意味が近い候補や判定が衝突する候補は根拠付きの横断確認で整理します。履歴判定とその根拠も候補整理へ渡します。同じ問題の再発候補を既存指摘へ対応付けたのに、履歴が修正済みと判定されている場合は停止します。原文によって候補自体を誤りと判断できる場合だけ棄却を許し、解消できない矛盾は統合失敗とします。新規指摘は現在の差分の投稿可能行を検証し、削除だけの問題などで有効な位置を決められない場合、無関係な行には投稿せず未完了理由に含めます。

## 容量・費用・認証の制限案

上限をなくす設計ではありません。1回の上限と実行全体の予算を分け、どの段階で何が不足したかを示します。以下を初期値とし、実運用で妥当性を確認します。

| 対象                        | 提案する制限                                             |
| --------------------------- | -------------------------------------------------------- |
| 1回の原文資料               | 300,000バイト                                            |
| 1回のJSON資料               | 400,000バイト                                            |
| 指示・履歴等を含む1回の入力 | 500,000バイト                                            |
| モデル呼び出し              | 固定回数上限なし、自動再試行なし                         |
| 全呼び出しの入力合計        | 合計バイト制限なし。共有資料の再送もトークン・費用へ計上 |
| 出力                        | 各回最大8,000トークン、合計は費用と時間で制御            |
| モデル要求時間              | 各回150秒、生成ジョブ全体40分                            |

生成run/attemptごとに$1の予算を持ち、各要求の入力トークンを計数して最大出力費用とともに確保します。応答後に実測usageで精算し、次の要求が残額に収まらなければ送信しません。固定の2MB・1MBの配分や合計3MBの判定は廃止します。必須作業・候補整理の固定回数上限は廃止し、認証・計数・生成・統合を含む30分の期限で処理時間を制御します。詳細は[費用制御設計](../superpowers/specs/2026-10-25-ai-review-dollar-budget-design.md)を参照してください。

既存の1回用8分ジョブ・3分ステップをそのまま流用しません。各要求の直前に信頼済み処理でWIF交換し、既存の残存240秒以上の確認を行います。モデル実行には交換済みトークンだけを渡し、OIDC取得権限を持つ環境変数は渡しません。トークンはログ・資料・Artifactに保存しません。交換失敗や期限不足は未完了にします。

収集・生成と書き込み専用ジョブの権限分離、main上の信頼済みコードによる実行、PRコードの非実行を維持します。モデルに渡すソース・文書は指示として扱いません。利用者が変更できるPR側の設定から上限や許可パスを緩めることも認めません。

## 完了・失敗・再実行

必須の単位、横断対象、過去指摘IDがすべて処理され、出力が検証できた場合だけ投稿へ進みます。資料を読んだうえでの判断不能は理由を残した結果として許容しますが、必須資料の欠落、モデル失敗、出力破損、予算超過は処理未完了です。費用予算の超過はPRコメントで通知し、通知成功ならCIは正常終了します。

生成の一部が失敗した場合は、成功した部分だけの指摘や修正確認返信を投稿しません。Actionsの概要に完了件数、未完了対象、理由を残します。修正確認を実行できなかった指摘へ「修正が確認できません」を機械的に返信しません。

生成完了時に台帳と最終結果を同じ実行・試行のArtifactへ固定します。投稿の再試行は同じArtifactを使用し、モデルを再実行しません。入力と結果のハッシュ、対象SHA、スキーマ版、信頼済み生成元を検証します。Artifact期限切れ時は新規生成になりますが、同じhead/baseへ投稿済みの内容と一致しなければ、従来どおり未完了で停止します。過去試行の部分生成結果を引き継ぐキャッシュは初期実装では作りません。

投稿途中の失敗は、既存の投稿済み照合と返信マーカーで再開します。各書き込み直前にhead/baseと対象条件を再確認します。新規指摘は該当行のレビュースレッド、修正確認は元スレッドへの返信とし、旧形式の通常コメントは既存の互換処理を維持します。AIはResolve・再オープンを一切操作しません。

## 検証と移行

実装は資料選択・台帳、分割レビュー、横断確認と履歴確認、Workflowと投稿連携の順に進めます。正式仕様・運用手順・必要なADRは実装時に更新します。PR #13の上限引き上げを先行マージする移行は行いません。mainで動く収集処理の切り替えには、実装PRの検査と別途マージ判断が必要です。

受け入れ時には次を確認します。

1. 無関係なファイルを増やしてもモデルへの資料は増えず、索引の制限超過は明示される。
2. 全体で300,000バイトを超える関連変更を、各回の上限内で分割して確認できる。
3. 大きな共通ファイル、巨大な関数、循環参照、削除・改名、動的参照を黙って欠落させない。
4. 別単位に分けた型・利用側の不整合を横断確認の原文資料に含め、台帳の必須対象漏れを検証で拒否する。
5. 単位が増えても過去指摘を全件扱い、旧形式の複数指摘の固定fixtureを維持する。
6. 後半の失敗・予算超過・トークン期限不足では完了扱いや修正確認返信が発生しない。
7. 投稿再試行でモデルを呼ばず、投稿済み内容との不一致、途中のPR更新、Artifactの不整合を拒否する。
8. CI後の検証用PRで行スレッドの投稿と元スレッドへの修正確認返信を確認し、Resolve状態を操作しない。

単体・結合テストは資料選択と確認漏れの検出を保証するもので、モデルが必ず不具合を発見する保証ではありません。有料の実PR検証では検出結果と見落としも記録します。

## 実装時の具体化

- 静的解析には`typescript-parser`という別名でTypeScript 5.9.3を固定する。型検査用のTypeScript 7.0.2には従来の解析APIがないため、型検査のバージョンを変更せず解析だけ分離した。PR側のtsconfigやプラグインを実行しない。
- 索引は最大5,000ファイル、本文20,000,000バイト、読み取り・解析120秒を目安に停止する。Gitコマンドにも個別の60秒制限がある。除外文書へのリンクと参照先の欠落を区別し、前者は除外一覧をモデルへ提示する。
- 宣言・節を壊さない範囲で80,000バイトまで原文をまとめ、1作業の確認対象は最大200件とする。巨大な差分hunkも原文の宣言境界へ対応させる。
- 横断確認はJSON資料250,000バイトまでで組み、先行候補が1回のJSON上限へ収まるよう150,000バイトの余地を取る。この値を費用へ換算・合算しない。候補追加後もJSON400,000バイト・入力500,000バイトを実測して検査する。
- 台帳を含むArtifactは6,000,000バイト、metadataは400,000バイト、最終結果は100,000バイトまで。最終結果には複数回分の履歴判定を含むため、1回のモデル応答30,000バイトとは別の上限とする。
- 投稿のみ再実行する場合は、生成ジョブが出力したArtifact名と生成試行番号を引き継ぐ。新しい試行番号から存在しないArtifact名を組み立てない。

再レビュー対応として、Markdownは文書検査と同じmarkdown-it 15.0.3で解析し、参照形式・省略形のリンクも対象にする。コード例や未使用のリンク定義は依存として扱わない。候補の重複棄却には、相手候補または過去指摘の確認根拠となった原文を同じ作業へ含め、双方を引用することを必須にする。容量のため同時に渡せなければ未完了で停止する。失敗時の概要には、安全な作業IDと固定の理由コードを残す。
