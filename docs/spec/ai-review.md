# AIレビューのコメントと修正確認

`tools/ai-review`がGitHubのPRへ投稿する指摘と、その修正確認の要件です。2026年10月25日に追加しました。既存の実行条件と権限分離は[導入設計](../research/ai-code-review.md)に従います。

該当行への指摘投稿と元スレッドへの修正確認返信を実装しています。自動テストで検査し、実PRでの行コメント投稿はmain反映後に確認します。旧方式の集約コメントは[検証用PR #11](https://github.com/teitei-tk/KorekaiteShine/pull/11)で検証済みです。

## 指摘の投稿

- AIレビューで採用した指摘ごとに、対象PRの「Files changed」にある該当ファイル・行へインラインレビューコメントを投稿し、レビュースレッドを作成する。
- 各指摘には対象箇所、発生条件、影響、修正方針を含め、どのコミットをレビューした結果か分かるようにする。
- 再レビューでも元の指摘を残し、修正確認の結果を元のレビュースレッドへ返信する。同じ指摘を新規の指摘として重複投稿しない。

## 修正確認

PR更新後、通常CIの成功を受けて再レビューするときに、過去の指摘についても対象コミットのコード・文書を確認する。

| 判定                                 | 追加する文言             |
| ------------------------------------ | ------------------------ |
| 指摘した問題の修正を確認できた       | `☑️: 修正を確認しました` |
| 指摘した問題の修正を確認できなかった | `修正が確認できません`   |

確認結果は元のレビュースレッドへの返信として追加し、対象コミットと判断の根拠を添える。行番号の移動や差分の更新で元のコメントが古くなっても、元スレッドとの対応を保持する。資料不足などで判断できない場合も「修正が確認できません」とし、未修正を確認した場合と区別できる理由を書く。新しいレビューで指摘が出なかったことや、通常CIが成功したことだけでは修正済みと判定しない。

モデル呼び出しの失敗などで修正確認自体を実行できなかった場合は、修正判定を追加せず、実行を未完了として扱う。投稿直前に対象コミットが変わっていた場合も、古い確認結果を投稿しない。同じ対象コミットに対する同じ指摘の確認結果は、再実行しても重複投稿しない。

スレッドの「Resolve conversation」は人間が行う。AIは修正を確認しても自動でResolveせず、人間がResolveしたスレッドを自動で再オープンしない。Resolveの状態だけでは修正済みと判定しない。

## PRのチェック表示

対象PRのheadコミットに`AI review`というCheck Runを登録する。通常CI成功後にAIレビューが開始すると実行中になり、詳細リンクから該当実行・試行番号のActionsログを開ける。

| 状況                                                        | チェックの結論 |
| ----------------------------------------------------------- | -------------- |
| レビューと投稿が完了、または同じhead/baseへの投稿済みを確認 | `success`      |
| 収集・事前検証・認証・生成・成果物検証・投稿に失敗          | `failure`      |
| 対象変更や実行条件の再確認で処理を省略                      | `neutral`      |
| 元Workflowがキャンセルされた                                | `cancelled`    |
| 元Workflowが時間切れになった                                | `timed_out`    |

成功は処理と投稿の完了を意味し、指摘がないことや修正済み・Resolve済みを意味しない。失敗時はタイトルと概要に対象ID・固定理由コードを表示する。外部エラー本文やモデルの生出力は渡さない。記録前の障害には`EXECUTION_FAILED`等の固定理由を使い、投稿完了の記録が欠けていれば`REPORT_MISSING`として成功にしない。

通知は`AI review`の開始・完了を受ける独立Workflowで行う。元Workflowのキャンセル後も終了を通知し、モデル実行側には`checks: write`を付与しない。実行ID・試行番号・対象SHAを照合し、遅延した開始通知や古い試行の通知で新しい結果を上書きしない。新規登録には既存の本人・同一リポジトリ・main向けPR条件を適用する。対象PRが更新・終了した後でも、登録済みの旧SHAのチェックは終了できる。

通知Workflow自体の障害では表示が更新されないことがある。その場合はActionsの`AI review check`を確認して再実行する。main向けでない依存PRや`claims`モードはチェック作成の対象外とする。マージ必須チェックへの登録は別の運用判断とし、この変更では行わない。

## 受け入れ条件

1. AIレビューの各指摘を対象PRの該当ファイル・行のレビュースレッドで確認できる。
2. 指摘への修正を含むPR更新後、元のレビュースレッドに「☑️: 修正を確認しました」と確認根拠が返信される。
3. 修正を確認できないPR更新後、元のレビュースレッドに「修正が確認できません」と理由が返信される。
4. 再レビュー後も元の指摘と過去の確認結果が残り、どのコミットに対する判定か分かる。
5. 再実行、資料不足、モデル失敗、投稿前のPR更新によって、重複投稿や誤った修正済みの表示が生じない。
6. 行番号の変更後も確認結果は元スレッドへ返信され、AIによってスレッドのResolve・再オープンは行われない。
7. 対象PRのチェック一覧でAIレビューの実行中・終了状態と失敗理由を確認できる。再実行、キャンセル、通知の順序逆転で誤った成功や状態の巻き戻りが生じない。

既存形式の集約コメントも修正確認の対象にする。旧コメントには行スレッドがないため、その指摘に限り元コメントへのリンク付きの通常コメントで確認結果を追加する。新規指摘は行スレッドへ投稿する。過去の指摘は最大30件まで扱い、超過・破損・取得失敗は未完了として停止する。新規指摘の最大3件とは別枠で全件を確認する。

新規指摘は一つのレビューとして一括投稿する。修正確認の返信は指摘IDと対象head/baseの組で重複を防ぎ、途中失敗後は投稿済みの処理を省略する。同じhead/baseで新規指摘が投稿済みの場合、再生成結果の優先度・ファイル・行・発生条件・影響・修正方針と件数を照合する。順序だけの違いは許容するが、内容が不一致なら返信や完了概要を追加せず、未完了として停止する。すべての投稿後に、指摘本文を含まない完了概要を通常コメントへ残す。各書き込みの直前にPRの対象を再確認する。

資料は[分割と横断確認の設計](ai-review-partitioning.md)に従い、関連単位・境界・履歴確認へ分割する。1回の原文300KB、JSON資料400KB、プロンプト500KBを維持し、実行全体は最大12回・入力合計3MBとする。履歴を含むmetadataは400KBまで、統合した最終結果は100KBまでとする。容量超過時は未完了で停止し、過去の指摘を黙って省略しない。

全必須作業と候補整理が完了した場合だけ投稿する。部分失敗時は成功した部分の指摘・修正確認を投稿しない。十分な資料を読んでも判断がつかない結果と、必須資料の欠落・モデル失敗を区別する。前者は確認不能の理由を返信し、後者はActionsに未完了を記録する。

重複はモデルに既存指摘との意味上の対応付けを指示し、根拠付きの候補整理で確認する。同じファイル・発生条件の指摘は投稿前の検証でも拒否する。成果物の生成元、固定入力・結果のハッシュ、全作業の完了を投稿前に照合する。
