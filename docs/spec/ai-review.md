# AIレビューのコメントと修正確認

投稿ジョブに進んだ実行の失敗・キャンセル・時間切れは、PRチェック・状態Artifact・Actionsで通知し、通常コメントは追加しない。通知自身による履歴改訂で投稿再開を妨げないためである。生成前・生成中の失敗通知コメントは維持する。

`tools/ai-review`がGitHubのPRへ投稿する指摘と、その修正確認の要件です。2026年10月25日に追加しました。既存の実行条件と権限分離は[導入設計](../research/ai-code-review.md)に従います。

該当行への指摘投稿と元スレッドへの修正確認返信を実装しています。自動テストで検査し、実PRでの行コメント投稿はmain反映後に確認します。旧方式の集約コメントは[検証用PR #11](https://github.com/teitei-tk/KorekaiteShine/pull/11)で検証済みです。

## 指摘の投稿

- AIレビューで採用した指摘ごとに、対象PRの「Files changed」にある該当ファイル・行へインラインレビューコメントを投稿し、レビュースレッドを作成する。
- 各指摘には対象箇所、発生条件、影響、修正方針を含め、どのコミットをレビューした結果か分かるようにする。
- 再レビューでも元の指摘を残し、修正確認の結果を元のレビュースレッドへ返信する。同じ指摘を新規の指摘として重複投稿しない。

## 修正確認

PR更新後、通常CIの成功を受けて再レビューするときに、過去の指摘についても対象コミットのコード・文書を確認する。

| 判定                                 | 追加する文言             |
| ------------------------------------ | ------------------------ |
| 指摘した問題の修正を確認できた       | `☑️: 修正を確認しました` |
| 指摘した問題の修正を確認できなかった | `修正が確認できません`   |

確認結果は元のレビュースレッドへの返信として追加し、対象コミットと判断の根拠を添える。行番号の移動や差分の更新で元のコメントが古くなっても、元スレッドとの対応を保持する。資料不足などで判断できない場合も「修正が確認できません」とし、未修正を確認した場合と区別できる理由を書く。新しいレビューで指摘が出なかったことや、通常CIが成功したことだけでは修正済みと判定しない。

モデル呼び出しの失敗などで修正確認自体を実行できなかった場合は、修正判定を追加せず、実行を未完了として扱う。投稿直前に対象コミットが変わっていた場合も、古い確認結果を投稿しない。同じ指摘への確認結果は、最新の通知から判定状態が変わった場合だけ返信する。head/baseや根拠文だけが変わっても、修正済み・未修正・確認不能の状態が同じなら返信を増やさない。再発や再修正など状態が変われば通知する。修正確認自体は毎回実施する。

スレッドの「Resolve conversation」は人間が行う。AIは修正を確認しても自動でResolveせず、人間がResolveしたスレッドを自動で再オープンしない。Resolveの状態だけでは修正済みと判定しない。

## PRのチェック表示

`pull_request`で起動する専用Workflowにより、PRのチェック一覧へ`AI review / Review result`を表示する。`Documentation checks`とは異なるCheck Suiteに所属する。通常CIとmain上のAIレビューを待つ間は実行中になり、詳細から監視結果と元のAI実行ログを確認できる。

| 状況                                                          | 表示ジョブの結論            |
| ------------------------------------------------------------- | --------------------------- |
| レビューと投稿が完了、または同じhead/baseへの投稿済みを確認   | `success`                   |
| 起点CI・収集・事前検証・認証・生成・成果物検証・投稿に失敗    | `failure`                   |
| 監視開始後の対象変更、元実行のキャンセル・時間切れ            | `failure`（固定理由で区別） |
| 監視ジョブ自身をキャンセル、または新しいPR更新で置換          | `cancelled`                 |
| 本人・同一リポジトリ・main向け・非Draft・reviewモードの条件外 | `skipped`                   |

成功は処理と投稿の完了を意味し、指摘がないことや修正済み・Resolve済みを意味しない。失敗時はジョブのエラー注釈と概要に対象ID・固定理由コードを表示する。外部エラー本文やモデルの生出力は渡さない。記録前の障害には`EXECUTION_FAILED`等の固定理由を使い、投稿完了の記録が欠けていれば`REPORT_MISSING`として成功にしない。

表示側はPRのbase SHAから信頼済みコードをcheckoutし、読み取り権限だけで実行する。OIDCを持つ生成ジョブと投稿権限を持つジョブは、main上の`workflow_run`に残す。いずれにも`checks: write`を与えず、Resolve APIを操作しない。PR番号・head/base、今回のPRイベント以降に開始した起点CIの実行ID・最新試行、AI実行ID・最新試行を照合し、成果物取得後にも再確認する。通常CIと表示の両WorkflowをDraft解除時にも起動する。

監視は15秒間隔・最大50分で打ち切る。対象実行の検索は最大1,000件とし、取得上限や接続障害で成功を推測しない。監視にはActions実行時間を使う。通常CIとAI実行が終わる前に監視を終了した場合は、表示側を再実行する。AI実行を再試行した場合も表示側の再実行が必要になる。マージ必須チェックへの登録は別の運用判断とし、この変更では行わない。

## 受け入れ条件

1. AIレビューの各指摘を対象PRの該当ファイル・行のレビュースレッドで確認できる。
2. 指摘への修正を含むPR更新後、元のレビュースレッドに「☑️: 修正を確認しました」と確認根拠が返信される。
3. 修正を確認できないPR更新後、元のレビュースレッドに「修正が確認できません」と理由が返信される。
4. 再レビュー後も元の指摘と過去の確認結果が残り、どのコミットに対する判定か分かる。
5. 再実行、資料不足、モデル失敗、投稿前のPR更新によって、重複投稿や誤った修正済みの表示が生じない。
6. 行番号の変更後も確認結果は元スレッドへ返信され、AIによってスレッドのResolve・再オープンは行われない。
7. 対象PRのチェック一覧でAIレビューの実行中・終了状態と失敗理由を確認できる。再実行、キャンセル、古い試行の結果で誤った成功が生じない。

既存形式の集約コメントも修正確認の対象にする。旧コメントには行スレッドがないため、その指摘に限り元コメントへのリンク付きの通常コメントで確認結果を追加する。新規指摘は行スレッドへ投稿する。過去の指摘は最大30件まで扱い、超過・破損・取得失敗は未完了として停止する。新規指摘の最大3件とは別枠で全件を確認する。

新規指摘、状態が変わった修正確認返信、完了概要の順に、一件ずつ投稿する。元の指摘を初期状態「未修正」とし、状態不変では返信しない。旧形式返信の解析とリンク付き旧集約コメントの互換性を維持する。

## 公式Actionによる生成

公式Codex Action v1.13、Codex 0.164.0、gpt-6-luna、mediumを使う。信頼済みmainから用意したプロンプトとSchemaをファイルで渡し、PR headのcheckout、baseとmerge-base、差分行、PR本文と全履歴を読み取り専用で参照する。PR内の指示・設定を信頼せず、公式unprivileged-userとsandboxの内側だけでPRコード実行を許容する。ルート所有の設定・文脈と、OIDCを保持する公式プロキシ・runnerの資格情報を専用UIDから隔離する。生成前後に境界を検査し、失敗時は成果物を公開しない。

静的分割・独自SDK実行・候補整理・費用予約・自動再生成は使わない。任意の規模の完走や全ファイル閲覧は保証しない。Actionが成功し、全過去指摘への判定と差分内の新規指摘をSchemaと既存検証器で確認できた場合だけ投稿する。モデル実行は15分、生成ジョブは25分までとする。未完了は部分投稿に変換しない。

## 履歴の改訂と投稿再開

準備と投稿で同じスナップショット取得器を使う。通常コメント・全行コメントと返信はRESTの全ページ、スレッドのID・元コメントID・Resolve状態はGraphQLの全ページを取得する。末尾の取得失敗や対応不整合では停止する。本文、投稿者、更新時刻、対象位置・コミット、返信関係、Resolve状態を正規化して改訂値を作る。旧返信件数・バイト数・ページ数上限は設けない。

成果物`review-v2.json`は生成run/attempt・実行コードSHA、対象PR/head/base、元CI、差分行、履歴スナップショットと改訂値、固定結果、投稿操作と本文ハッシュを保持する。投稿前に再構築して一致を検査する。旧形式Artifactは投稿しない。

各操作直前に対象と最新履歴を確認する。同じ生成の操作IDを持ち、bot・本文・投稿先・コミットが完全一致する自己投稿だけを履歴比較から除外する。新規スレッドへの外部返信やResolve変更は除外しない。残りが生成時の履歴と異なれば停止する。同じ対象への別生成の途中投稿も停止する。最後に完了概要を追加する。各書込みはトランザクションではなく、確認と書込みの間の外部変更を原子的に排除する保証はない。

PR単位で投稿を直列化する。同じArtifactの保持期間7日以内に投稿ジョブだけを再実行した場合、成功応答が失われても保持されたコメントを照合し、残った操作だけを実行する。新規生成は行わない。保証には対象SHAの一致、外部改訂のない履歴、自己投稿の保持・読取可能性が必要である。

手動削除後は同じArtifactを再試行しない。応答喪失直後に削除された自己投稿は未投稿と区別できず、再作成され得る。削除を独自DBや監視で補わない。手動削除・Artifact失効・履歴改訂時はPRの履歴を人が確認し、新しいheadを起点に通常レビューを実行する。

## 未完了の安全な診断

既存の状態Artifact、PRチェック表示、失敗通知を再利用する。準備・履歴・生成・投稿の固定理由を保存し、外部エラー本文や認証値を通知へ含めない。旧診断の読取互換性は維持するが、旧分割台帳や作業別の診断は新規生成しない。公式Actionの実行ログはActionsで確認する。

## 実行ごとの費用制御

$1の厳密上限・トークン事前計数・費用予約は廃止する。公式Actionの探索は複数モデル要求になり得る。自動再生成をせず、実行期限で停止する。料金や利用量が取得できない場合は`null`（不明）で保持し、ゼロとしない。現在のArtifactでは利用量・料金とも不明とし、必要時は公式実行ログ・請求画面で別途確認する。投稿ジョブだけの再実行はモデルを呼ばない。

## 各段階の失敗通知

対象確認・履歴取得・資料収集・隔離検証・認証・生成・成果物検証・投稿の失敗をPRの通常コメントで通知する。修正確認を実施できなかった失敗通知を、元スレッドの修正判定とは区別する。既に投稿済みの指摘・返信は変更しない。

AIレビュー実行の終了を受ける専用Workflowが、信頼済みmainのコードで状態Artifactを検証し、日本語で「何が起きたか」「次に何を確認すべきか」を説明し、実行と試行のリンクを投稿する。対象段階・失敗理由・サブコード・head/baseの固定診断は「調査用の詳細」に折りたたむ。説明文は固定理由に対応する信頼済みの定型文から選び、原因を確定できない場合は断定しない。モデル生出力、外部エラー本文、秘密値、未検証の任意文字列は含めない。診断記録が欠ける場合はジョブ状態からEXECUTION_FAILEDまたはPUBLISH_FAILED、不正な記録ならREPORT_INVALIDとする。タイムアウト・キャンセルも現在の対象に限り通知する。

通知ジョブはActions・contentsの読み取りとPR書き込みだけを持ち、OIDC・モデル実行・PRコードの実行は行わない。元CIとAI実行のリポジトリ・Workflow・試行、本人の非Draft PR、現在のhead/baseを投稿直前にも検証する。対象を特定できない場合、対象外PR、更新済みのhead/base、旧試行には投稿しない。通知自体が失敗した場合は専用Workflowを失敗にし、固定理由FAILURE_NOTIFICATION_FAILEDを残す。GitHubの権限不足・障害などで投稿できない場合にコメント成功を保証しない。

同じAI実行ID・試行・PR・head/baseでは、GitHub Actions botの識別情報と専用マーカーで重複を防ぐ。生成の新しい試行は別通知とする。予算通知済み・レビュー成功・対象外では失敗コメントを追加しない。元実行が成功していれば、Artifactの取得障害や保存期限切れをレビュー失敗とみなさない。失敗通知の成功で元のレビュー失敗を成功へ変更しない。予算超過時の既存の通知・CI正常終了方針は維持する。Resolve・再オープンは操作しない。
