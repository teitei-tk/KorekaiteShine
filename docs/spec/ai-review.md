# AIレビューのコメントと修正確認

`tools/ai-review`がGitHubのPRへ投稿する指摘と、その修正確認の要件です。2026年10月25日に追加しました。既存の実行条件と権限分離は[導入設計](../research/ai-code-review.md)に従います。

該当行への指摘投稿と元スレッドへの修正確認返信を実装しています。自動テストで検査し、実PRでの行コメント投稿はmain反映後に確認します。旧方式の集約コメントは[検証用PR #11](https://github.com/teitei-tk/KorekaiteShine/pull/11)で検証済みです。

## 指摘の投稿

- AIレビューで採用した指摘ごとに、対象PRの「Files changed」にある該当ファイル・行へインラインレビューコメントを投稿し、レビュースレッドを作成する。
- 各指摘には対象箇所、発生条件、影響、修正方針を含め、どのコミットをレビューした結果か分かるようにする。
- 再レビューでも元の指摘を残し、修正確認の結果を元のレビュースレッドへ返信する。同じ指摘を新規の指摘として重複投稿しない。

## 修正確認

PR更新後、通常CIの成功を受けて再レビューするときに、過去の指摘についても対象コミットのコード・文書を確認する。

| 判定                                 | 追加する文言             |
| ------------------------------------ | ------------------------ |
| 指摘した問題の修正を確認できた       | `☑️: 修正を確認しました` |
| 指摘した問題の修正を確認できなかった | `修正が確認できません`   |

確認結果は元のレビュースレッドへの返信として追加し、対象コミットと判断の根拠を添える。行番号の移動や差分の更新で元のコメントが古くなっても、元スレッドとの対応を保持する。資料不足などで判断できない場合も「修正が確認できません」とし、未修正を確認した場合と区別できる理由を書く。新しいレビューで指摘が出なかったことや、通常CIが成功したことだけでは修正済みと判定しない。

モデル呼び出しの失敗などで修正確認自体を実行できなかった場合は、修正判定を追加せず、実行を未完了として扱う。投稿直前に対象コミットが変わっていた場合も、古い確認結果を投稿しない。同じ対象コミットに対する同じ指摘の確認結果は、再実行しても重複投稿しない。

スレッドの「Resolve conversation」は人間が行う。AIは修正を確認しても自動でResolveせず、人間がResolveしたスレッドを自動で再オープンしない。Resolveの状態だけでは修正済みと判定しない。

## PRのチェック表示

`pull_request`で起動する専用Workflowにより、PRのチェック一覧へ`AI review / Review result`を表示する。`Documentation checks`とは異なるCheck Suiteに所属する。通常CIとmain上のAIレビューを待つ間は実行中になり、詳細から監視結果と元のAI実行ログを確認できる。

| 状況                                                          | 表示ジョブの結論            |
| ------------------------------------------------------------- | --------------------------- |
| レビューと投稿が完了、または同じhead/baseへの投稿済みを確認   | `success`                   |
| 起点CI・収集・事前検証・認証・生成・成果物検証・投稿に失敗    | `failure`                   |
| 監視開始後の対象変更、元実行のキャンセル・時間切れ            | `failure`（固定理由で区別） |
| 監視ジョブ自身をキャンセル、または新しいPR更新で置換          | `cancelled`                 |
| 本人・同一リポジトリ・main向け・非Draft・reviewモードの条件外 | `skipped`                   |

成功は処理と投稿の完了を意味し、指摘がないことや修正済み・Resolve済みを意味しない。失敗時はジョブのエラー注釈と概要に対象ID・固定理由コードを表示する。外部エラー本文やモデルの生出力は渡さない。記録前の障害には`EXECUTION_FAILED`等の固定理由を使い、投稿完了の記録が欠けていれば`REPORT_MISSING`として成功にしない。

表示側はPRのbase SHAから信頼済みコードをcheckoutし、読み取り権限だけで実行する。OIDCを持つ生成ジョブと投稿権限を持つジョブは、main上の`workflow_run`に残す。いずれにも`checks: write`を与えず、Resolve APIを操作しない。PR番号・head/base、今回のPRイベント以降に開始した起点CIの実行ID・最新試行、AI実行ID・最新試行を照合し、成果物取得後にも再確認する。通常CIと表示の両WorkflowをDraft解除時にも起動する。

監視は15秒間隔・最大50分で打ち切る。対象実行の検索は最大1,000件とし、取得上限や接続障害で成功を推測しない。監視にはActions実行時間を使う。通常CIとAI実行が終わる前に監視を終了した場合は、表示側を再実行する。AI実行を再試行した場合も表示側の再実行が必要になる。マージ必須チェックへの登録は別の運用判断とし、この変更では行わない。

## 受け入れ条件

1. AIレビューの各指摘を対象PRの該当ファイル・行のレビュースレッドで確認できる。
2. 指摘への修正を含むPR更新後、元のレビュースレッドに「☑️: 修正を確認しました」と確認根拠が返信される。
3. 修正を確認できないPR更新後、元のレビュースレッドに「修正が確認できません」と理由が返信される。
4. 再レビュー後も元の指摘と過去の確認結果が残り、どのコミットに対する判定か分かる。
5. 再実行、資料不足、モデル失敗、投稿前のPR更新によって、重複投稿や誤った修正済みの表示が生じない。
6. 行番号の変更後も確認結果は元スレッドへ返信され、AIによってスレッドのResolve・再オープンは行われない。
7. 対象PRのチェック一覧でAIレビューの実行中・終了状態と失敗理由を確認できる。再実行、キャンセル、古い試行の結果で誤った成功が生じない。

既存形式の集約コメントも修正確認の対象にする。旧コメントには行スレッドがないため、その指摘に限り元コメントへのリンク付きの通常コメントで確認結果を追加する。新規指摘は行スレッドへ投稿する。過去の指摘は最大30件まで扱い、超過・破損・取得失敗は未完了として停止する。新規指摘の最大3件とは別枠で全件を確認する。

新規指摘は一つのレビューとして一括投稿する。修正確認の返信は指摘IDと対象head/baseの組で重複を防ぎ、途中失敗後は投稿済みの処理を省略する。同じhead/baseで新規指摘が投稿済みの場合、再生成結果の優先度・ファイル・行・発生条件・影響・修正方針と件数を照合する。順序だけの違いは許容するが、内容が不一致なら返信や完了概要を追加せず、未完了として停止する。すべての投稿後に、指摘本文を含まない完了概要を通常コメントへ残す。各書き込みの直前にPRの対象を再確認する。

資料は[分割と横断確認の設計](ai-review-partitioning.md)に従い、関連単位・境界・履歴確認へ分割する。1回の原文300KB、JSON資料400KB、プロンプト500KBを維持し、実行全体は最大12回とし、生成run/attemptごとのAPI費用を$1以内に制御する。合計バイト数を費用上限として使わない。履歴を含むmetadataは400KBまで、統合した最終結果は100KBまでとする。容量超過時は未完了で停止し、過去の指摘を黙って省略しない。

全必須作業と候補整理が完了した場合だけ投稿する。部分失敗時は成功した部分の指摘・修正確認を投稿しない。十分な資料を読んでも判断がつかない結果と、必須資料の欠落・モデル失敗を区別する。前者は確認不能の理由を返信し、後者はActionsに未完了を記録する。

重複はモデルに既存指摘との意味上の対応付けを指示し、根拠付きの候補整理で確認する。同じファイル・発生条件の指摘は投稿前の検証でも拒否する。成果物の生成元、固定入力・結果のハッシュ、全作業の完了を投稿前に照合する。

## 未完了の安全な診断

既存の理由コード（`INCOMPLETE`・`OUTPUT_INVALID`等）に固定サブコードを追加する。API生成中断は`TOKEN_LIMIT`・`CONTENT_FILTER`・`API_INCOMPLETE`、空・過大出力は`EMPTY_OUTPUT`・`OUTPUT_LIMIT`、形式や根拠の不正は`INVALID_JSON`・`INVALID_RESULT`・`COVERAGE_MISMATCH`・`EVIDENCE_MISMATCH`等で区別する。

モデルは未完了時に`MISSING_CONTEXT`・`NO_REVIEWABLE_LINE`・`UNRESOLVED_CONFLICT`・`MODEL_UNSPECIFIED`のいずれかを申告する。不足情報は`IMPLEMENTATION`・`CALLER`・`CONTRACT`・`SPECIFICATION`・`PRIOR_EVIDENCE`・`REVIEWABLE_LINE`から選ぶ。モデルの申告は原因の確定とは区別し、診断だけを根拠に自動再試行や資料の追加取得は行わない。旧形式など分類できない失敗は`UNCLASSIFIED`を使う。

親プロセスが検証済み台帳から作業種別、資料ID・行範囲・base/head/ancestorの別、確認対象IDと全件数を記録する。各一覧は最大8件とし、表示件数と全件数を併記する。台帳検証前の失敗では範囲を推測して記録しない。ファイルパス、本文、認証値、外部エラー本文、モデルのsummary・uncertaintiesなどの自由文は診断へ含めない。

診断は生成ジョブのActions概要と、既存の4KB状態Artifactに保存する。独立したPRチェックは検証した診断だけを概要へ表示し、エラー注釈には対象・理由・サブコードを表示する。未知の分類・余分な項目・不正なIDや範囲を拒否する。診断を持たない旧形式の状態Artifactも読み取り可能とし、未完了を成功や部分投稿へ変換しない。

## 実行ごとの費用制御

生成実行ごとに$1の予算を設ける。同じhead/baseでも生成の再実行は新しい予算、投稿だけの再試行は追加生成なしとする。公式APIで入力トークン数を計数し、入力の最大単価と最大出力費用を各呼び出し前に確保する。応答usageを結果検証前に精算し、未精算・料金区分不一致では追加生成を止める。通常入力、キャッシュ読み取り・書き込み、推論を含む出力を区別する。

費用は親プロセスのメモリと一時JSONで管理し、予約・精算ごとに原子的に保存する。DBは追加しない。終了時に費用記録をArtifactへ保存し、強制終了等で記録が残らなければ使用量を不明とする。料金設定版、run/attempt、対象SHA、要求ハッシュ、使用量と金額だけを記録し、秘密値とモデル生出力は含めない。

予算不足は「予算上限（$1）を超える見込みのため、AIレビューを中止しました。PRを分割してください。」とPRの会話欄に通知する。レビュー未完了を明記し、部分指摘・修正確認は投稿しない。botのIDと生成run/attempt・対象SHAのマーカーで同じ通知の再投稿を防ぐ。通知済みならCIは正常終了するが、レビュー完了とは区別する。通知失敗は技術的失敗として扱う。Resolve状態は変更しない。

[詳細設計](../superpowers/specs/2026-10-25-ai-review-dollar-budget-design.md)に料金条件、状態管理、Artifactの検証と境界テストを記載する。実APIのWIF接続・計数料金・請求整合はmain反映前の確認事項として残る。
