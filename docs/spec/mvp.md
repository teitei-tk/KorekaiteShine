# 模擬技術面接アプリのMVP仕様

2026年10月24日作成。2026年11月2日までの設計相談で合意した要件を記録します。2026年11月3日、面接一覧APIの移行と診断ジョブによる3 Workers・共有D1・Queueのローカル接続を検証しました。正式な面接・実AI・認可・クラウド配置は未実装・未検証です。[用語集](../../GLOSSARY.md)の意味で用語を使います。実施済みの検証と後続の計画を区別し、未確定事項は末尾にまとめます。

## 課題

ソフトウェアエンジニア・開発リーダーの転職面接では、設計や技術を選んだ理由、制約の中での優先順位、意思決定と合意形成の説明が求められます。本人のコードや経験について、回答を深掘りされても、当時の根拠とトレードオフを自分の言葉で説明する練習が必要です。

技術知識の暗記や模範解答の生成が目的ではありません。コードだけでは当時の制約や本人の権限が分からず、業務コードは持ち込めません。毎回長い事前資料を書く負担も避けたいと考えています。

## 解決方針

本人専用のWebアプリで、一つの意思決定を15分程度、AIと音声で深掘りします。「公開GitHubのコードだけ」と「外部の経験Markdownだけ」のどちらからでも開始できます。両方を混ぜる面接はMVPに含めません。

送信内容を確認した後、AIが材料から面接テーマを提示し、本人が一つ選びます。短い事前補足と対話で背景を補い、終了後に点数と根拠付きの振り返りを残します。履歴から発言の一貫性と説明不足を確認できます。

自分のPCで使える状態から始め、Cloudflareへの配置を前提に構築します。このアプリ自体も、設計・実装の成果物として面接で紹介できるものを目指します。

### 設計基準

判断の基準は「自分に役立つ小さなMVP」と「本番運用を想定した設計を、自分の判断として説明できること」の両立です。サービス数や実装量の少なさだけを最適化しません。

- 面接練習としての価値を優先し、対象利用者・材料・機能範囲を限定します。
- 接続・記録・認可・再試行・削除の責務を明確にし、障害時の動作と費用上のトレードオフを説明できる構成を選びます。
- 技術を追加する時は、満たす要件、代替案、増える運用負担を示します。「本番向け」という名称だけを選定理由にしません。
- 新しい提案とレビューでは既存ADRの理由を確認します。採用済みの構成を見直す場合は、変わった前提と影響を明示します。
- フレームワークの互換性など構成を左右する未検証事項を、細かな操作仕様や設定値より先に確認します。

## ユーザーストーリー

### 材料の準備

1. 利用者として、公開GitHubのURLとコミットを指定したい。面接で参照するコードを固定するため。
2. 利用者として、外部送信するファイルと分量を分析前に確認したい。許可した内容だけをAIへ渡すため。
3. 利用者として、コードを読んだAIからテーマ候補を受け取りたい。アーキテクチャや設計判断、ライブラリ選定などの練習対象を選ぶため。
4. 利用者として、リポジトリ外の自由書式の経験Markdownを選びたい。業務コードを持ち込まず、意思決定を練習するため。
5. 利用者として、一つのMarkdownに複数の意思決定を記載したい。既存の記録を繰り返し使うため。
6. 利用者として、経験Markdownの送信内容を確認し、提示されたテーマを一つ選びたい。今回扱う判断に集中するため。
7. 利用者として、背景・担当・権限を短く補足したい。長い事前資料を毎回作らずに済ませるため。

### 面接

8. 利用者として、一問ずつ回答に応じた追加質問を受けたい。固定質問の消化ではなく、自分の説明を深めるため。
9. 利用者として、設計判断とリーダーとしての行動を同じ面接で扱いたい。一つの意思決定を技術と人の両面から説明するため。
10. 利用者として、コードの事実とAIの推測を区別してほしい。意図や貢献を勝手に決め付けられないため。
11. 利用者として、本人の権限と他者の判断を区別してほしい。チームの成果や組織上の制約を適切に説明するため。
12. 利用者として、現在の質問を文字で確認し、必要なら言い換えてもらいたい。質問の意味を理解して回答するため。
13. 利用者として、質問を見送りたい。回答を強制されず、同じ判断の別の観点へ進むため。
14. 利用者として、一時停止・再開したい。考える時間や休憩を取るため。
15. 利用者として、通信切断後に同じ面接へ戻りたい。途中までの練習を失わないため。
16. 利用者として、途中でも終了したい。その時点までの説明を振り返るため。
17. 利用者として、別タブでも進行中の面接を表示したい。面接を重複して作らず、必要なら操作を引き継ぐため。

### 評価と振り返り

18. 利用者として、五つの評価軸を1〜5点で採点してほしい。説明の充足度を継続して確認するため。
19. 利用者として、点数の理由と根拠となる発言を確認したい。具体的な改善対象を把握するため。
20. 利用者として、未確認・対象外と低得点を区別してほしい。話していないことを能力不足と扱われないため。
21. 利用者として、説明できた点、不足した点、未確認事項、次に練習する問いを確認したい。次回の練習につなげるため。
22. 利用者として、同じ面接内の矛盾候補を確認したい。自分の発言の一貫性を振り返るため。
23. 利用者として、終了受付後は画面を閉じても評価を進めてほしい。結果を待って画面を開き続けずに済むため。
24. 利用者として、評価の一時的な失敗を自動で再試行してほしい。自分で何度も操作しなくて済むため。
25. 利用者として、自動再試行で解消しない失敗を同じ条件で手動再実行したい。面接をやり直さず評価を得るため。

### 履歴と管理

26. 利用者として、文字起こし全文を保存したい。質問と回答の前後関係を確認するため。
27. 利用者として、面接単位の一覧と評価軸ごとの推移を見たい。繰り返し不足する説明を把握するため。
28. 利用者として、評価の根拠から該当発言と前後の会話へ移動したい。指摘が妥当か確かめるため。
29. 利用者として、矛盾候補の発言を並べて確認したい。前提の違いや訂正を含めて判断するため。
30. 利用者として、原文を保ったまま追記メモを付けたい。誤変換や後からの気付きを面接中の発言と分けるため。
31. 利用者として、面接詳細で評価の状態・失敗理由・実行履歴を確認したい。処理の状況と必要な対応を把握するため。
32. 利用者として、自分が削除するまで記録を保持したい。後から振り返りを蓄積して分析するため。
33. 利用者として、面接単位で関連記録を削除したい。不要な会話や評価をまとめて消すため。
34. 利用者として、削除後に遅れた評価ジョブが記録を復活させないでほしい。削除の意思を維持するため。
35. 利用者として、本人以外の閲覧や有料API実行を防ぎたい。面接内容と利用費を管理するため。

## 実装上の決定事項

### 構成と責務

| 部分                           | 責務                                                             |
| ------------------------------ | ---------------------------------------------------------------- |
| React・shadcn/ui               | 画面、面接操作、文字起こしと評価の比較                           |
| TypeSpec                       | 通常のHTTP APIの契約の原本、OpenAPI・型・検証コードの生成起点    |
| TanStack Start                 | 画面遷移、通常のサーバー処理                                     |
| Void                           | Cloudflareとの連携、ビルド・配置                                 |
| 通常Worker                     | 認可、接続の振り分け、材料整理、履歴・管理API                    |
| 面接ごとのDurable Object（DO） | GPT-Liveへの音声中継、面接状態、接続の引き継ぎ、再開・終了の制御 |
| Queues・評価Consumer・DLQ      | 音声接続から独立した評価、再試行、失敗ジョブの退避               |
| D1                             | 文字起こし、材料の参照・抜粋、評価、追記メモ、実行履歴           |
| Cloudflare Access              | Cloudflare配置時の本人限定アクセス                               |

Web・Interview・Evaluationを独立した3 Workersとして配置します。WebはTanStack Start、InterviewはCloudflare標準の面接DOを公開し、Evaluationは評価QueueとDLQを受信します。WebのDOバインディングは同じ環境のInterview Workerを参照します。Webは手動再実行など、Interviewは面接終了時の評価依頼を同じQueueへ送ります。アプリ全体をnative Voidへ置き換える方針ではなく、各バックエンドWorkerのエントリ方式は検証で確定します。通常のHTTP APIに加え、検証専用入口でWebからInterview DOへの呼び出し、3 Workersの共有D1、Evaluationのscheduledイベントをローカル検証済みです。診断ジョブのQueue配送・再試行・DLQと停止後回復もローカルで検証済みです。固定版のQueue永続性の制約は[検証記録](../research/local-worker-integration.md#ローカル検証の限界)に記載します。分割理由は[ADR 0007](../adr/0007-three-workers.md)に記録します。

音声はブラウザからDOを経由してGPT-Liveへ送信します。アプリでは音声を永続保存せず、中継に必要な短いメモリ内バッファだけを使います。GPT-Liveの録音保存は無効にし、保存録音からの再開は使いません。再開にはD1の文字起こしと面接状態を使います。OpenAI側の不正利用監視等による保持は、アプリの音声非保存や録音保存の無効化とは区別します。外部保持の条件と検証状況は[技術調査](../research/platform-integration.md#websocket再開外部保持)を参照してください。

ローカルではブラウザを閉じても開発サーバーとPCの稼働が必要です。PCが停止してもバックグラウンド処理が続く構成はCloudflare配置後に実現します。

### 配置と業務モデル

今後育てる最小骨格として、次の配置を採用します。以下は実装先の合意であり、ディレクトリやコマンドが作成済みであることを意味しません。

| 配置                      | 責務                                                                                            |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| `apps/web`                | React・TanStack Start、HTTP API、認可、接続振り分け                                             |
| `apps/interview`          | 面接DO、音声中継、面接状態と再開・終了の制御                                                    |
| `apps/evaluation`         | 評価Consumer、再試行、DLQからの失敗反映                                                         |
| `packages/api-contracts`  | HTTP・QueueのTypeSpec原本、OpenAPI・JSON Schema・型・Ajv検証コードの生成。生成物はGit管理対象外 |
| `packages/database`       | 共有するDrizzleスキーマ、D1マイグレーション、検証データ                                         |
| `packages/runtime-config` | 環境選択とWorker・リソース対応の共通設定                                                        |

各アプリの`src/domain`に業務モデル・状態遷移、`src/application`に処理の組み立て、`src/server/repositories`にDBアクセスを置きます。業務モデルはReact・Void・Drizzleに依存させません。必要な処理から設け、単純な取得に一律の層やクラスを増やしません。複数Workerで同じ業務ルールを使う場合に限り`packages/domain`へ切り出します。画面固有の状態はWeb側に置きます。

依存方向はアプリから共有パッケージへ向け、共有パッケージからアプリを参照しません。HTTP契約、DBレコード、業務モデルを同じ型として扱わず、必要な境界で変換します。`database`に全Workerの業務処理を集めません。

既存試作から契約・生成処理・画面・API・回帰テストを移行しました。移行先で契約生成、型検査、テスト、開発サーバー、ビルド済みWorker、ブラウザ表示を確認し、旧試作を削除しています。互換性制約と回帰ケースの移管先は[検証記録](../research/local-worker-integration.md)に残します。試作の一覧APIを正式な履歴APIとして確定しません。

### 共有D1とマイグレーション

同じ環境の3 WorkersでD1を1つ共有します。DrizzleはVoid経由で使用し、全パッケージのVoid版を揃えます。DBスキーマの原本は`packages/database/db/schema.ts`と`db/schema/`、SQLと生成メタデータは同パッケージの`db/migrations/`に集約してGit管理します。接続済みインスタンスは共有せず、各WorkerのD1バインディングから取得します。

マイグレーションはリポジトリルートの操作入口から、`packages/database`のスキーマとSQLを参照する環境別の作業ディレクトリで、Void CLIの生成・適用を実行します。固定版Voidが作業ディレクトリへ生成設定・lock・DB保存先情報を書き込むため、並列テストと開発の管理情報も分離します。原本は`packages/database`に維持し、作業先に別のDB定義を設けません。SQLをレビューしてから適用し、DB管理パッケージを4つ目のWorkerとして配置しません。各Workerのデプロイから意図せず適用されないことも検証します。DOクラスのマイグレーションはD1のSQLと別で、Interview Workerが管理します。

共有D1のため、Workerを独立配置してもDB変更には互換性が必要です。旧版・新版が共存できる追加変更を先に行い、列削除などは利用側の移行後に行います。採用理由と負担は[ADR 0008](../adr/0008-shared-d1-with-void.md)、固定版の確認範囲は[Drizzle連携調査](../research/void-drizzle.md)を参照してください。

### 環境と検証データ

環境は`development`・`test`・`production`に分けます。Void標準の環境選択に依存せず、独自の`APP_ENV`を共通設定で検証し、未指定や誤記では停止します。`NODE_ENV`とは別に扱い、起動・テストの操作入口が必要な値を渡します。実行時の環境識別にも同じ値を渡します。環境名は秘密値ではなく、秘密値の供給方法は既存の方針に従います。

| 対象       | development                 | test                                            | production                  |
| ---------- | --------------------------- | ----------------------------------------------- | --------------------------- |
| 実行先     | ローカル                    | ローカル                                        | Cloudflare                  |
| Worker名   | `korekaite-{役割}-dev`      | `korekaite-{役割}-test-{識別子}`                | `korekaite-{役割}-prod`     |
| D1名       | `korekaite_development`     | `korekaite_test_{識別子}`                       | `korekaite_prod`            |
| 評価Queue  | `korekaite-evaluation-dev`  | `korekaite-evaluation-test-{識別子}`            | `korekaite-evaluation-prod` |
| DLQ        | 評価Queue名に`-dlq`を付加   | 同左                                            | 同左                        |
| 診断Queue  | `korekaite-diagnostics-dev` | `korekaite-diagnostics-test-{識別子}`           | 作成・接続しない            |
| 診断DLQ    | 診断Queue名に`-dlq`を付加   | 同左                                            | 作成・接続しない            |
| 状態保存先 | `.local/development/`で保持 | `.local/tests/{実行ID}/{並列番号}/`で分離・破棄 | Cloudflareの各リソース      |

役割は`web`・`interview`・`evaluation`です。テスト識別子は命名上限を満たす短い一意値とします。各環境の3 Workersは同じD1識別子を使い、環境間では分離します。WebからDOを参照するときは同じ環境のInterviewの`script_name`を明示します。DO namespaceとQueueも分離し、環境名やDB名の変更だけで分離済みとは扱いません。ローカル状態と生成設定・ビルド出力はGit管理対象外とし、並列テストで共有しません。

ローカルは`auxiliaryWorkers`による単一開発ランタイムを第一候補とします。状態保存先だけでなくWorker間通信・Queue配送を接続します。`packages/database`のCLIにも同じD1の保存先と識別子を対応させます。設定・生成物・`void.lock.json`に残る別環境の情報を流用しない方式は実装検証で確定します。[ADR 0009](../adr/0009-explicit-environments.md)と[環境調査](../research/void-environments.md)を参照してください。

共有する架空の固定データは`packages/database/fixtures`、投入入口は`db/seed.ts`、テストDB準備とfactoryは`testing/`に置きます。HTTP不正入力、接続イベント、AI応答などの個別データは各アプリの`tests/fixtures`に置きます。ID・日時を固定し、実データや秘密値は入れません。

開発DBは通常起動・マイグレーションで保持し、リセットとseedは明示操作にします。Voidのseedはリセットを伴うため、操作入口でもその意味を示します。自動テストは空DBへ同じマイグレーションを適用し、必要なデータだけ投入します。純粋な業務ルールのテストはDBを起動しません。テスト内の3 Workersは同じテスト環境を使い、別実行・並列単位と開発環境には接続しません。

### HTTP APIの契約管理

通常のHTTP APIの契約管理にTypeSpecを正式採用します。入力・応答・HTTPステータスをTypeSpecで定義し、OpenAPI 3.1、TypeScriptのAPI型、実行時検証コードを生成します。生成物を手編集せず、同じ契約を別のスキーマへ手書きしません。選定理由は[ADR 0006](../adr/0006-typespec-api-contracts.md)に記録します。

TanStack StartのServer RoutesでHTTP APIを実装し、Reactから生成型とopenapi-fetchを使って呼び出します。同じAPIの契約をServer Functions側に重複定義しません。VoidはCloudflare連携・ビルド・配置を担い、既存のDO・Queues・D1の責務は維持します。

APIの入力と受信した応答は境界で検証します。Ajvの検証コードはES Modulesとして事前生成し、Workers上でスキーマをコンパイルしません。型生成だけでは実データの正しさを保証できないため、実装したAPIの応答が契約に合うこともテストします。認可、状態遷移、重複防止、削除との競合などの振る舞いは、スキーマとは別に実装・テストします。

契約変更時は再生成・型検査・契約に対するテストを行います。TypeSpecの採用は、試作の面接一覧の項目や件数上限を正式な履歴APIの仕様として確定するものではありません。DBスキーマはDrizzleを原本とし、HTTP契約とは分けます。Queueは[評価ジョブの契約](#queueの契約)で定めます。WebSocket・AI出力への適用は、[補足事項](#未確定事項実装前の確認)で別途判断します。

### 依存バージョンの制約

2026年10月30日の初回ローカル検証はVoid 1.3.0、2026年11月2日以降の移行・3 Workers・DB操作はVoid 1.4.0で検証しました。現行の依存宣言はVoid 1.6.2へ更新しています。TypeSpec 1.17.0、React 19.3.1、TanStack Start 1.169.4、Vite 8.3.5、openapi-typescript 7.13.0を使用しています。現行の[依存宣言](../../apps/web/package.json)と[共有ロックファイル](../../pnpm-lock.yaml)、確認範囲と履歴を分けた[検証記録](../research/local-worker-integration.md)を参照してください。

| 対象                      | 維持する制約と根拠                                                                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| TypeScript                | openapi-typescript 7.13.0は5系のCompiler APIを使用するため、型生成専用のtools/api-codegenで5.9.3に固定する。アプリの型検査と文書・レビューツールは7.0.2を使う                  |

### 材料の取り込み

コード面接ではURLとコミットの対応を確認してファイル一覧を取得し、分析対象・除外対象・分量を表示します。利用者の確認後にAIが読み、根拠の参照箇所を伴うテーマ候補を提示します。対象コードは実行しません。

依存ライブラリ、生成物、バイナリ、秘密情報や機密情報を含む可能性があるファイルを除外します。入力上限を超える場合は黙って切り捨てず、範囲を絞るよう案内します。面接中の自由な追加取得は行わず、選択範囲外は未確認と扱います。参照はコミット・ファイル・行番号で固定します。

経験Markdownはブラウザで選び、送信内容を確認してからAIが意思決定を抽出します。自由書式とし、推奨テンプレートと架空の記入例を用意します。外部の原本をアプリのリポジトリへコピーせず、選んだテーマの根拠の抜粋と見出し等の参照をD1に保存します。原本は変更しません。

材料と音声による補足には、外部AIへ送信してよい情報だけを使います。業務経験はあらかじめ匿名化・抽象化し、学習に利用されても差し支えない内容に限定します。未加工の業務情報をAIへ送って匿名化させる流れは設けません。

README、コードコメント、取り込んだ文書内の指示は分析対象のデータとして扱います。アプリや開発エージェントへの命令として実行しません。

### 面接官の振る舞い

一問ずつ回答の不足や曖昧さを確認し、一つの判断を十分に深掘りします。事前に説明された背景や役割を繰り返し尋ねず、必要な部分だけを補います。

- 設計について、課題、要求、当時の制約、選択肢、非採用理由、利点・欠点、品質・運用・性能・納期・コストの優先順位、見直す条件、結果と改善点を確認します。
- リーダーとしての行動について、責任・権限、当時の情報と不確実性、関係者の意見や利害、本人の判断と委任、説明・合意形成・反対への対応、判断後の行動と学びを確認します。
- コードの事実、本人の説明、AIの推測を区別し、意図・本人の貢献・未発言の実績を補いません。
- チームの成果と本人の行動を分け、組織や他者の判断まで本人の責任としません。結果だけで判断の良し悪しを決めません。
- 圧迫・侮辱、過剰な称賛、模範解答への誘導を避け、改善の助言は原則として終了後に行います。

### 時間、操作、接続

| 項目                   | 合意済みの動作                                                                   |
| ---------------------- | -------------------------------------------------------------------------------- |
| 面接時間               | 15分程度を目安とし、終了が近づいたら論点を広げず区切りで終える                   |
| 一時停止               | 最大5分。録音・送信・AI音声再生と面接時間の計測を止める                          |
| 自動再接続             | 最大1分。切断中は面接時間に含めず、同じ面接へ戻る                                |
| 待機上限               | 面接を終了し、保存済みの会話から評価する                                         |
| 回答がない場合         | 点数を付けず「評価対象の回答なし」として履歴に残す                               |
| 質問の再表示・言い換え | 現在の質問を文字で確認でき、論点を保って言い換えられる。回答例・ヒントは出さない |
| 質問の見送り           | 回答を強制せず、同じ意思決定の別の観点へ移る                                     |
| 途中終了               | 利用者の操作で終了し、その時点までの会話を評価する                               |

一時停止・言い換え・見送り・通信切断・待機上限到達そのものは減点理由にしません。

ブラウザとDO間、DOとGPT-Live間の切断を分けて扱います。一時停止・ブラウザ不在時には録音・送信・再生と面接時間の計測を止め、上流接続を閉じます。マイクのミュートだけで停止完了とは扱いません。再開時は保存済みテキストと面接状態を渡して新しいGPT-Live接続を開始し、同じ面接IDへ紐づけます。API接続の終了・更新と、面接の終了は区別します。

再開用の文脈には選択テーマ、材料の必要な抜粋、本人の背景・権限、直前の質問と回答、未確認事項を含めます。入力上限を超える場合の選択・要約は再開用に限定し、評価の根拠となる文字起こし原文を変更しません。受信できなかった発言や聞けなかった質問は補完せず、必要なら話し直してもらいます。必要な文脈を復元できない場合や待機上限に達した場合は、保存済みの会話から振り返ります。

音声面接は本人につき同時1件で、一時停止・再接続待ちも含みます。別タブでは進行中の面接と同じ文字起こし・進行状態を表示します。音声の送受信は一つのタブが担当し、明示的に引き継いだ時に古いタブの録音・再生と送信権を無効にします。

評価処理も同時1件とします。追加の評価はQueueで待機し、評価中でも次の音声面接は開始できます。

### 採点と一貫性

| 評価軸               | 確認する説明                                 |
| -------------------- | -------------------------------------------- |
| 課題・制約           | 解決したかった課題、要求、受けていた制約     |
| 選択肢・トレードオフ | 代替案、採用・非採用理由、優先・断念したこと |
| 判断の根拠           | 当時の情報と不確実性から判断へ至る理由       |
| 本人の行動・合意形成 | 権限内での判断・行動、委任、他者との調整     |
| 結果・学び           | 結果の捉え方、改善点、判断を変える条件       |

| 点数 | 基準                                                                             |
| ---- | -------------------------------------------------------------------------------- |
| 1    | 質問・確認をしても判断や行動の具体的な説明が得られなかった                       |
| 2    | 結論や行動は説明できたが、理由・制約とのつながりが不明確だった                   |
| 3    | 判断や行動を当時の理由・制約と結び付け、筋道を説明できた                         |
| 4    | 具体的な根拠を示し、代替案や不確実性など、その軸の重要な論点まで説明できた       |
| 5    | 深掘りにも前提と根拠を整理し、その軸に即した判断の限界・見直す条件まで説明できた |

各軸に理由と発言の根拠を付けます。未質問、時間不足、通信欠落は「未確認」、当てはまらない軸は「対象外」とし、0点に置き換えません。質問されたが説明できなかった場合とは区別します。流暢さ、話の長さ、成果の大きさだけでは加点しません。

一貫性は同じ面接内に限定します。矛盾候補は双方の発言を引用し、前提・時点・権限の違いや説明の訂正を確認します。面接中には中立的に一問ずつ確認し、解消しなければ「要確認」とします。推測だけで減点しません。

振り返りには「説明できていた点」「説明が不足していた点」「未確認事項」「次に練習する問い」を示し、発言や材料の参照箇所を付けます。未発言の成果を加えて回答を美化しません。

### 評価ジョブと再実行

終了受付時に会話と評価依頼を永続化し、受付完了後はブラウザに依存せず処理を進めます。音声接続の終了と評価完了は別の状態です。D1をジョブ状態の正本、Queueを処理開始の通知として扱います。2026年11月2日に、以下の契約・実行権・配送判断と初期値を合意しました。2026年11月3日に共有ジョブ制御を診断スタブとローカルD1で検証しました。正式な面接終了処理と実AIの連携は未検証です。

#### Queueの契約

Queueの契約もTypeSpecを原本とし、JSON Schema・TypeScript型・Ajv検証コードを生成します。HTTP用OpenAPIは経由させず、`packages/api-contracts/messages/`で定義し、生成物は`generated/messages/`に置いてGit管理対象外にします。検証コードは事前生成し、送信前・Consumer受信後・DLQ受信後の境界で使います。型やSchemaを手書きで二重管理しません。

メッセージ本文は次の2項目に限定します。

```json
{
  "schemaVersion": 1,
  "jobId": "7e318b72-f255-4f17-845b-714d487ae621"
}
```

`schemaVersion`は整数の1です。`jobId`は一回の評価実行を識別する不変・再利用不可のIDとし、Queueの配送IDとは区別します。自動再試行は同じID、手動再実行は新しいIDです。IDはサーバー生成のUUID v4とし、小文字・ハイフンありの36文字に統一します。v1は未定義フィールドを拒否し、型の自動変換・既定値補完・余分な項目の削除は行いません。

会話・材料・モデル指定・採点基準・評価用の指示はD1に固定して紐づけ、本文に含めません。検証時の失敗注入も開発・テスト専用ジョブで管理します。不正形式と未対応版を区別し、検証に失敗した本文のIDだけで既存ジョブを変更しません。生の本文をそのままログへ出しません。

破壊的変更では契約版を上げ、Consumerを新旧両対応にしてから送信側を更新します。旧版のQueue・DLQメッセージとロールバックを考慮し、旧版対応を廃止する時期を決めます。TypeSpecのJSON Schema emitterと型・Ajv生成の固定版互換性は検証対象です。理由は[ADR 0010](../adr/0010-queue-contracts-and-job-control.md)を参照してください。

#### 状態遷移と実行権

| 状態         | 意味                   | 次の状態                                         |
| ------------ | ---------------------- | ------------------------------------------------ |
| `pending`    | 受付済み・実行待ち     | `running`、取消時は`cancelled`                   |
| `running`    | 実行権を取得して処理中 | `completed`・`retry_wait`・`failed`・`cancelled` |
| `retry_wait` | 次回実行時刻まで待機   | `running`、取消時は`cancelled`                   |
| `completed`  | 結果保存が完了         | 終端。遅延配送で変更しない                       |
| `failed`     | 自動処理を終了         | 終端。手動再実行は新しいジョブ                   |
| `cancelled`  | 削除などにより取消     | 終端。再開しない                                 |

配送障害からの回復で、未完了ジョブを失敗へ確定する場合は、現在の実行者・次回通知・削除状態を条件付きで再確認します。未送信・DLQ送信待ちはジョブ状態と別の送信待ち記録で管理します。削除は未完了ジョブを取り消し、原文等を削除して最小限の削除済み識別情報を残します。完了・失敗の終端状態も、データの保持を強制するものではありません。

ジョブ単位の重複実行と、本人全体で評価が同時に複数動くことを防ぎます。実行権には所有者トークン・世代・有効期限を持たせ、本人の評価枠とジョブをD1内で一体として条件付き更新します。空き状態の読み取りと無条件の更新を分離しません。結果保存時も所有者・世代・有効期限・`running`状態・未削除を確認します。古いConsumerによる上書きや、失効した実行権の復活を認めません。

評価の試行回数はD1で管理し、実行権取得後、AI呼び出し開始直前に増やします。記録直後の停止で呼び出し成否が分からない場合も一回として数えます。Queue待機、実行権待ち、重複配送、D1接続失敗だけでは増やしません。SDK内部の自動再試行は無効にし、初回と最大3回の再試行をアプリで管理します。

評価済み結果の保存だけを回復できる場合はAIを呼び直しません。手動再実行は同じ会話・材料・採点基準・モデル指定・評価用の指示を引き継ぎ、追記メモは含めません。指定モデルが使えなければ設定上の失敗とし、別モデルへ黙って変更しません。同じ条件でも出力の完全一致は保証しません。

#### タイムアウトと回復の初期値

以下は終了後の評価用であり、音声面接の接続時間とは別です。設定を集約し、モデル・入力上限・実測値を踏まえて変更履歴と理由を残します。

| 項目              | 初期値             | 基準                                               |
| ----------------- | ------------------ | -------------------------------------------------- |
| AIタイムアウト    | 120秒              | リクエスト開始から応答本文の受信完了まで           |
| 1試行の上限       | 180秒              | 実行権取得からAI・検証・保存まで                   |
| 実行権の有効期間  | 180秒              | 最後の取得・更新時刻から。ただし試行の終了期限まで |
| 実行権更新        | 30秒間隔           | ジョブと本人全体の評価枠を一体で更新               |
| 引き継ぎ猶予      | 30秒               | 実行権失効後に待つ時間                             |
| 評価の再試行      | 30秒・120秒・300秒 | 各失敗を確定した時刻から。初回後の最大3回          |
| 回復処理          | 60秒周期           | Evaluation Workerの定期実行                        |
| Queue配送の再試行 | 30秒間隔・最大3回  | 判断・保存できない配送の再試行。評価回数とは別     |

試行の終了期限は取得時刻から180秒で固定します。実行権の期限は「更新時刻＋180秒」と「試行の終了期限」の早い方です。期限ちょうどから旧Consumerの更新・保存を認めず、引き継ぎは期限＋30秒以降に行います。更新しても一試行を無制限に延長しません。

AIが120秒で完了しなければ通信を中止し、実行権が有効なら`retry_wait`・失敗理由・次回時刻・送信待ち記録をまとめて保存します。180秒で更新と結果保存を打ち切ります。更新に失敗したConsumerは新しいAI呼び出しを開始せず、所有権喪失または期限切れでは処理を中止して結果を破棄します。

次回時刻より前には実行しません。外部APIの`Retry-After`が通常間隔より長い場合は、その指定より早く再試行せず、D1へ次回時刻を保存します。認証・設定不備は早期に失敗とします。正常な終了処理では状態・送信待ちの保存と実行権解放を整合させ、停止・結果不明時は期限と猶予による回復に委ねます。

Evaluation Workerが未送信通知、期限に達した再試行、期限切れ実行権、DLQへの未送信記録を回復します。送信済みでも処理されていない通常通知と、失敗状態の受信記録がないDLQ通知は、送信日時と予定日時から30秒の猶予を置いて再送待ちへ戻します。現世代・用途・削除状態を再確認し、DLQを通常Queueへ無条件に差し戻しません。4つ目のWorkerは追加せず、評価の回復を面接DOのAlarmへ依存させません。送信待ち作成直後にも送信を試み、定期実行は取りこぼしを補います。遅延付き通知を利用しても、実行可否の正本はD1です。

期限切れジョブは所有者・世代・期限を再確認し、再試行可能なら`retry_wait`、上限到達なら`failed`とします。回復処理の重複起動でも同じ状態を二重に進めません。失効から引き継ぎまでは通常30〜90秒程度と実行遅延を見込み、正確な時刻での再開は保証しません。時計を差し替えて直前・ちょうど・直後と競合をテストし、実タイマー・配送・定期実行は別途ローカル連携で確認します。

#### ack・retry・DLQ

ackは評価成功ではなく、この配送を繰り返す必要がなくなったことを示します。終端状態を確認できた場合、後続処理を永続化できた場合、または配送異常を隔離記録として永続化できた場合にackし、判断・保存できなければretryします。バッチ全体ではなくメッセージ単位で扱います。

| 状況                           | 処理                                                                 |
| ------------------------------ | -------------------------------------------------------------------- |
| 評価成功                       | 結果と`completed`を保存してack                                       |
| 完了・取消済みの重複           | 再実行せずack                                                        |
| 同じジョブを別Consumerが実行中 | 有効な実行権と回復対象であることを確認してack                        |
| 別ジョブが本人の評価枠を使用中 | 次回通知を永続化してack。評価回数は増やさない                        |
| 一時的なAIエラー               | `retry_wait`・次回時刻・送信待ちを保存してack                        |
| 評価上限到達・回復しないエラー | `failed`とDLQ送信待ちを保存してack                                   |
| D1に接続できず判断・保存不能   | 遅延付きretry                                                        |
| 不正形式・未対応版             | AIを呼ばず、配送側の異常と退避を永続化してack。保存できなければretry |

存在しないジョブと用途不一致は、[配送異常の記録と隔離](#配送異常の記録と隔離)に従います。契約・用途の検証は実行権の取得やジョブ状態の更新より先に行います。

D1状態・送信待ちは一体で保存しますが、D1・DO・Queue間の原子性は前提にしません。送信成功直後の停止による再送もあるため、受信側の重複防止を維持します。

DLQにはアプリが評価失敗を確定して退避した通知と、配送上限へ達した通知の両方が届きます。DLQ到着だけでジョブを失敗に上書きしません。

| DLQ照合時のD1状態             | 処理                                                                       |
| ----------------------------- | -------------------------------------------------------------------------- |
| `completed`・`cancelled`      | 状態を変えず、遅延・重複として記録してack                                  |
| `failed`                      | 退避を確認し、記録してack                                                  |
| 有効な`running`・次回通知あり | 失敗に上書きせず、現在の処理・回復経路を維持                               |
| 実行者も次回通知もない未完了  | 回復処理への引き継ぎを永続化し、条件付きで回復または配送障害として失敗確定 |
| 不正形式・未対応版            | 本文のIDだけでジョブを変更せず、配送側の異常として記録                     |

DLQから元Queueへ無条件に差し戻しません。DLQ処理自体の保存失敗もretryし、回復経路を残さずackしません。DLQ処理の再試行枯渇・通知・保持期限内の運用回復と、配送障害を業務失敗へ確定する具体条件は補足事項で詰めます。

外部AIの処理は通信中止後も続く可能性があります。実行権・引き継ぎ猶予でアプリ側の結果を保護しても、外部呼び出しや料金の重複は完全には防げません。保存済み結果の回復とAI再呼び出しを区別し、この限界を表示します。

#### 配送異常の記録と隔離

存在しないジョブや用途不一致の通知は、評価失敗とは別の配送異常としてD1に記録し、通常処理・自動回復の対象から外してackします。判断または保存ができない場合だけ、既定の配送再試行を行います。判断理由は[ADR 0014](../adr/0014-quarantine-invalid-job-notifications.md)に記録します。

| 状況                                                         | 処理                                                  |
| ------------------------------------------------------------ | ----------------------------------------------------- |
| D1への問い合わせが失敗                                       | 不在と判定せず、遅延付きretry                         |
| 有効な契約のIDで照会し、ジョブも削除済み識別情報も存在しない | `JOB_NOT_FOUND`として隔離記録を保存してack            |
| 削除済み識別情報がある                                       | 削除後の遅延通知として記録してack。ジョブを復元しない |
| 受信Queueの期待用途とジョブ用途が不一致                      | `JOB_PURPOSE_MISMATCH`として隔離記録を保存してack     |
| 隔離記録を保存できない                                       | ackせず、既定の配送retry                              |
| 同じ異常通知の再配送                                         | 保存済み記録を確認・更新してack。通常処理を起動しない |

通常QueueとDLQの両方で同じ分類を使います。用途不一致では、参照先ジョブの状態・評価試行回数・実行権を変更せず、AIを呼びません。別のQueueへの自動転送や、存在しないジョブの自動作成は行いません。不正形式・未対応版は既定の契約検証で処理し、本文から取り出したIDだけで存在確認やジョブ変更を進めません。

受付・ジョブ・outboxは通知より先にD1へ保存されるため、正常な経路で通知がジョブ作成を追い越すことは想定しません。不在の判定には受付済みの書き込みを確認できる読み取りを使います。将来読み取りレプリカなどを導入する場合も、古い読み取り結果だけで不在を確定しません。

隔離先は共有D1の専用テーブルとし、新しい隔離Queueは設けません。異常記録には次を保存します。

- 異常コード、受信Queue、その期待用途。
- メッセージID、検証済みの契約版と`jobId`、確認できたジョブ用途。
- 初回・最終検知日時、未対応／対応済み、対応内容。

ジョブが存在しなくても記録できるよう、ジョブへの必須の外部キーに依存させません。同じ配送の再受信は、受信QueueとメッセージIDを基準に一意に管理します。別メッセージIDで同じジョブの通知が届いた場合は別の配送記録として残します。隔離記録の保存後・ack前に停止しても、再配送時に重複した処理を起こさないようにします。受信本文や秘密値を無制限に保存しません。

DLQは配送上限到達や評価失敗通知の退避先、D1の異常記録は調査・対応状況の保存先です。異常と判断できた通知をDLQへ到達させるためだけにretryせず、DLQで同じ異常を検知した場合も記録してackします。隔離のために別のDLQへ送り続けません。保存不能時に配送上限へ達する場合は既定のDLQ経路を使います。DLQ自身の保存失敗と再試行枯渇時の運用回復は、引き続き補足事項で管理します。

隔離された通知を定期回復から自動再投入しません。原因を修正した後、D1の正しいジョブ状態・用途・既存の実行権と通知を確認し、必要な通知だけを再発行して対応内容を記録します。用途不一致の通知を隔離しても、正しいジョブの既存処理や回復経路は妨げません。削除済みのジョブは再発行の対象にしません。

受入条件は、存在しないジョブ・用途不一致・削除後通知の分類、D1照会失敗を不在と誤認しないこと、記録保存失敗時のretry、保存後・ack前の停止と重複受信、通常QueueとDLQでの同じ判断です。用途不一致でも元ジョブが変更されず、AIを呼ばず、自動転送しないことを確認します。これらは共有処理の単体テストとローカルD1境界テストで検証しました。実配送・停止境界との対応と限界は[検証記録](../research/local-worker-integration.md)に記載します。

### 履歴と保存

面接単位で一覧に表示し、再実行の履歴は面接詳細にまとめます。一覧は日時・テーマ・材料種別・面接時間・評価状態を表示し、完了後は五つの点数を示します。採点基準や評価できた軸が違う結果を、点数だけで単純比較しません。

| 状態           | 表示と操作                                     |
| -------------- | ---------------------------------------------- |
| 評価待ち       | 受付済みで開始待ち。面接記録を閲覧できる       |
| 評価中         | 評価処理中。面接記録を閲覧できる               |
| 自動再試行待ち | 再試行回数と次回予定を示す                     |
| 評価失敗       | 理由と必要な対応を示し、同じ条件で再実行できる |
| 評価完了       | 点数、振り返り、根拠を閲覧できる               |

最終更新時刻を表示し、根拠のない進捗率は出しません。更新が途絶えても画面だけで失敗を断定せず、サーバー側で確認します。失敗理由は通信・時間切れ、利用上限、認証・設定、結果形式、保存失敗を区別します。実際に保存できた範囲と次の操作を示し、秘密値や生の外部APIエラー本文は出しません。

再実行ボタンは実行中に無効化し、サーバー側でも連打・別タブからの重複依頼を防ぎます。以前の失敗理由と試行回数を保持し、AIの再呼び出しに追加料金が発生し得ることを表示します。

文字起こし全文には話者・発言順・経過時間を持たせ、切断による欠落を明示します。受信した文字起こしの断片と時刻を保持し、発言の区切りと同時発話の表示はアプリで管理します。再接続後の時刻は面接全体の経過時間と対応づけます。生成された質問と利用者に再生できた範囲を区別し、再生が確認できない部分を聞けたものと扱いません。評価の根拠から該当発言と直前の質問へ移動でき、矛盾候補は前後の文脈と解消状況を比較できます。原文を変更せず、誤変換や補足は追記メモとして保存し、採点には反映しません。

### 保持と削除

本人が削除するまで保持し、自動削除はしません。対象テーマを確認して面接単位で削除し、文字起こし、材料の抜粋、評価、実行履歴、追記メモをまとめて削除します。アプリ内のごみ箱は設けず、外部Markdownの原本は変更・削除しません。

評価中でも削除を優先し、可能な範囲で処理を中止します。削除状態はジョブ開始時と結果保存時の両方で確認し、遅れた結果を保存しません。削除済みの面接を評価処理から新規作成することも禁止します。

QueueやDLQの遅延ジョブ、手動再実行からも復活させません。会話を含まない最小限の削除済み識別情報を一定期間保持します。期間とバックアップ上の残存は未確定事項として扱います。アプリ内の削除がOpenAI側の保持を直ちに消すとは説明しません。

### アクセスと秘密情報

Cloudflare配置後も本人1人に限定し、Cloudflare Accessで画面・API・WebSocketを保護します。履歴の閲覧・削除だけでなく、面接開始と評価再実行にも認可を適用します。IDを知っているだけではアクセスできず、別URLによる迂回を防ぎます。独自のユーザー登録・共有機能は設けません。

本番Webの公開入口は独自ホスト名に集約し、ホスト名単位のAccessアプリケーションで本人限定にします。WebSocketを使うため、Worker単位のAccess保護を前提にしません。不要な`workers.dev`・プレビューURLは配置設定で無効化し、残す公開入口には同等の保護を付けます。Interview・Evaluationには公開HTTP入口を設けず、DOバインディング・Queue・定期実行を使います。Accessの本人情報が内部Workerへ自動伝播するとは扱わず、内部呼び出しの権限設計を別途行います。

診断用の画面・API・失敗注入処理は別モジュールに分離し、開発・テスト用エントリからだけ参照します。本番のWeb・Interview・Evaluationと配信アセットには含めません。`APP_ENV`の実行時条件で拒否するだけの方式は採用せず、本番ビルドのルート・依存関係・出力に診断機能が含まれないことをCIで検査します。Accessは本人以外の利用を防ぎ、成果物の分離は認証済み本人の誤操作による診断・失敗注入も防ぐための構成です。[ADR 0011](../adr/0011-access-and-diagnostics-isolation.md)に理由を記録します。

本番成果物への診断URLのアクセスで診断処理が実行されないことを確認します。Accessによる未認証・許可外利用者の拒否、WebSocket接続、別URLからの迂回防止は、承認後のクラウド配置で検証します。ローカルの認証模擬だけでAccessの保護を検証済みとは扱いません。

開発時は1Password Environments MCP Serverを第一候補にし、環境名・変数名などの非秘密情報だけを扱います。値の登録・承認は1Passwordの正規UIで行います。プロセス起動時の注入には1Password CLIを候補とし、開発用とデプロイ用の権限を分離します。

秘密値を環境ファイル、JSON、ソース、設定、一時ファイルへ保存しません。チャット、モデルのコンテキスト、ログ、シェル履歴、コマンドライン引数にも露出させません。値の表示、環境変数の全件ダンプ、マスキング無効化は行いません。仮想環境ファイルのマウントも未採用です。連携未設定時に平文ファイルへ退避しません。

OpenAIの長期APIキー、GitHubトークン、Cloudflare管理トークンをブラウザへ渡しません。本番の秘密値供給は開発時の1Password連携とは別途決定します。Workers Secrets等を使う場合は、1Password以外にコピーが保持されること、配置先、権限、更新・削除方法を説明して合意を得ます。

## テスト方針

架空データの面接一覧APIでは、契約生成、型検査、不正な入力・応答の拒否、開発サーバーとビルド済みWorkerのHTTP通信、ブラウザでの一覧表示・再取得を検証しました。診断ジョブでは実時間の再試行・DLQ・停止後回復、環境分離と本番成果物からの除外も検査しています。再実行は[ローカル開発手順](../runbooks/local-development.md)、固定版と限界は[検証記録](../research/local-worker-integration.md)を参照してください。今後のAPIも契約との一致を検証します。

以下の製品機能については検証計画案で、まだ実施していません。本番アプリは未実装です。内部関数の呼び出し順ではなく、画面・API・保存結果などから観測できる振る舞いを検証します。

| 対象         | 主な確認事項                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| 材料取り込み | 送信確認前にAI分析しない、コミット固定、除外と上限、文書内の命令を実行しない                                     |
| 面接状態     | 停止5分・再接続1分の境界、停止時間の除外、二重開始の防止、タブ引き継ぎ、欠落の明示                               |

### 最小骨格の接続確認と検証の拡張

検証用APIは開始を`POST /api/diagnostics/check-jobs`、状態取得を`GET /api/diagnostics/check-jobs/{jobId}`とします。パスは環境名ではなく接続確認の用途を表します。開発・テスト用エントリからだけ組み込み、本番成果物から除外します。`APP_ENV`は環境選択に使い、実行時の拒否条件だけには依存しません。パス名自体をアクセス制限とは扱いません。

最初に、正常に処理が一周する確認と、意図的なConsumer失敗による再試行・DLQ確認を実装します。外部AIは呼び出さず、架空の検証ジョブを使います。開発・テスト環境専用の操作とデータを用意し、正式な面接データと分離します。

- 正常系：画面から開始し、WebがD1へ受付・処理待ちジョブ・後続処理のoutboxを保存します。永続化した後続処理でInterviewのDOへの保存確認とQueue送信を行い、EvaluationがD1を完了へ更新します。画面からその結果を確認します。
- 失敗系：Consumer内のAIスタブを意図的に失敗させ、業務試行の再予約と通知を確認します。一時的な失敗からの成功と、全4回失敗した場合のD1への失敗確定・DLQへの退避を確認します。Queue配送自体の再試行とは区別します。

#### 診断データと配送経路の分離

開発・テスト環境では、D1を共有し、診断専用のQueue・DLQを用意します。Web・Interview・Evaluationの3 Workersと、環境ごとにD1を1つ持つ構成は維持します。通常開発のデータを保持しながら意図的な失敗とDLQ受信を観測するための分離です。[ADR 0013](../adr/0013-diagnostics-queue-isolation.md)に選択肢と判断理由を記録します。

| 対象           | 分離・共通化の方針                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------- |
| D1             | ジョブ・実行権・outboxは共通のテーブルと処理を使い、診断／正式の用途を明示的に区別する                  |
| 診断固有の情報 | `scenario`と確認結果は、ジョブに関連付けた専用テーブルへ保存する                                        |
| Queue・DLQ     | 開発・テストそれぞれに診断専用の組を設け、正式処理の配送と混在させない                                  |
| Evaluation     | 同じWorkerで受信し、正式・診断の入口を分ける。状態遷移・実行権・outbox・再試行・ack判断は共通処理を通す |
| AI呼び出し     | 診断の入口から固定スタブを組み込み、失敗注入を行う。共通のジョブ制御処理を診断用に複製しない            |
| DO             | 診断用の識別範囲を設け、正式な面接と同じインスタンスを使わない                                          |
| 本番           | 診断の入口・失敗注入・Queueバインディングを含めず、診断Queue・DLQも作成しない                           |

配送先とジョブの用途はサーバー側で決定し、開始APIへ用途指定を追加しません。Queue本文は`schemaVersion`と`jobId`の2項目を維持します。Consumerは受信Queueの用途とD1のジョブ用途を照合し、不一致ならジョブを実行しません。再試行・定期回復・DLQへの送信でも用途に対応する配送先を維持します。存在しないジョブや用途不一致の扱いは、[配送異常の記録と隔離](#配送異常の記録と隔離)に従います。

正式データの一覧・集計には診断ジョブを混ぜません。DBスキーマとマイグレーションの管理先は一本のままとし、本番に診断機能を含めないことと、環境ごとにDBスキーマを分岐させることは分けて扱います。診断固有のテーブルがあっても、本番の診断データ投入や診断処理の組み込みは行いません。

D1・Workerと本人全体の評価枠は共有するため、完全な障害隔離ではありません。競合・大量投入・破棄を伴う試験は、実行単位で独立させたテスト環境で行います。診断経路の成功だけで正式Queueの接続設定まで検証済みとは扱わず、正式経路は別に確認します。固定版Voidでの複数Queue受信、用途ごとの配送先解決、本番成果物からの除外は実動作で検証します。

#### 検証用APIの契約

HTTP契約は`packages/api-contracts`のTypeSpecを原本とし、ヘッダー・本文・成功応答・エラー応答を定義します。開始と状態取得の応答には`Cache-Control: no-store`を付けます。日時はUTC・ミリ秒付きのRFC 3339形式とします。診断用の固定データとAIスタブを使い、任意の入力や実AI呼び出しはこのAPIの対象にしません。[ADR 0012](../adr/0012-idempotent-diagnostics-api.md)に受付順序とエラー形式の選定理由を記録します。

#### 開始要求と受付結果

`POST /api/diagnostics/check-jobs`は`Content-Type: application/json`と`Idempotency-Key`ヘッダーを必須にします。キーは呼び出し側が生成するUUID v4で、小文字・ハイフンありの36文字です。本文の必須項目は`scenario`のみとし、未知の項目・値を拒否します。型変換や既定値補完は行いません。

```json
{
  "scenario": "retry_then_success"
}
```

| scenario             | 検証する動作                                       |
| -------------------- | -------------------------------------------------- |
| `success`            | 最初の試行で正常に完了する                         |
| `retry_then_success` | 最初のAI呼び出し相当を失敗させ、次の試行で成功する |
| `exhaust_retries`    | 全4回を失敗させ、失敗確定とDLQ受信を確認する       |

受付成功は`202 Accepted`です。`Location`ヘッダーに`/api/diagnostics/check-jobs/{jobId}`を返します。本文の全項目は必須で、受付後に変更しません。

```json
{
  "jobId": "7e318b72-f255-4f17-845b-714d487ae621",
  "scenario": "retry_then_success",
  "acceptedAt": "2026-11-02T03:00:00.000Z"
}
```

`jobId`はサーバーで生成し、呼び出し側からの指定を受け付けません。冪等キーとは別のIDです。`202`は永続化した受付の応答であり、DOへの保存やQueueへの送信、処理完了を意味しません。現在状態はGETで取得します。

#### 開始受付の冪等性と保存順序

キーの有効範囲は環境・サーバーが識別する実行主体・開始操作の組み合わせです。ローカルでは固定の開発用主体を使い、本文の利用者IDを信用しません。入力の同一性は、JSON文字列ではなく検証済みの入力値で比較します。空白やプロパティ順は比較に影響しません。

| 要求                               | 動作                                                              |
| ---------------------------------- | ----------------------------------------------------------------- |
| 初めてのキー                       | 1件のジョブを作成して`202`を返す                                  |
| 同じキー・同じ入力                 | 元と同じ受付本文と`Location`を`202`で返し、新規作成・再実行しない |
| 同じキー・異なる入力               | `409 IDEMPOTENCY_KEY_CONFLICT`を返す                              |
| 同じキーの同時要求                 | D1の一意制約とトランザクションで1件に集約する                     |
| 終端状態になったジョブへの同じ要求 | 元の受付結果を返す。意図的な再実行には新しいキーを使う            |

キーの対応表はジョブと一緒に保持し、最小骨格では自動削除しません。開発・テストDBの明示的なリセットで冪等性の保証も終了します。保存期限や削除機能を追加する際は、対応表だけが先に消えないよう再設計します。

1. 入力とキーを検証します。検証エラーではキーを予約しません。
2. 冪等キーと入力の対応、`pending`ジョブ、後続処理のoutboxをD1の同一トランザクションで保存します。事前の存在確認だけで重複を防ごうとはしません。
3. 保存成功を確認して`202`を返します。応答が失われた場合や、`503`で保存結果が不明な場合、呼び出し側は同じキーで再送します。
4. 永続化した後続処理からDOの初期化・保存確認を行い、その後Queueへ送信します。DO初期化も`jobId`単位で冪等にし、受付直後の停止は既定の定期回復で続行します。

DOには少なくとも`jobId`と初回受信日時を保存し、読み戻して確認します。重複初期化で初回受信日時を書き換えません。D1・DO・Queue間は原子的ではなく、進捗保存前の停止では処理が再実行されます。DO初期化の冪等性とConsumerの実行権管理を維持します。D1の記録を失ったときまで、外部副作用の重複を防ぐ保証はしません。

#### 状態取得

`GET /api/diagnostics/check-jobs/{jobId}`の`jobId`は開始応答と同じUUID形式です。形式不正は`400`、実行主体の参照範囲に対象がなければ`404`を返します。成功は`200 OK`です。

```json
{
  "jobId": "7e318b72-f255-4f17-845b-714d487ae621",
  "scenario": "retry_then_success",
  "status": "completed",
  "attemptCount": 2,
  "acceptedAt": "2026-11-02T03:00:00.000Z",
  "updatedAt": "2026-11-02T03:00:32.000Z",
  "finishedAt": "2026-11-02T03:00:32.000Z",
  "nextAttemptAt": null,
  "lastErrorCode": "SIMULATED_AI_FAILURE",
  "checks": {
    "doPersistence": "passed",
    "consumerCompletion": "passed",
    "dlqReceipt": "not_expected"
  }
}
```

本文と`checks`内の全項目を必須とし、未設定の値は以下の規則で`null`にします。

| 項目                      | 意味                                                                                          |
| ------------------------- | --------------------------------------------------------------------------------------------- |
| `status`                  | `pending / running / retry_wait / completed / failed / cancelled`。既定のジョブ状態遷移に従う |
| `attemptCount`            | AI呼び出し相当の開始回数。初期値0、上限4。Queue配送回数とは区別する                           |
| `acceptedAt`・`updatedAt` | 受付日時と、公開する状態・検証結果の最終更新日時                                              |
| `finishedAt`              | 終端状態へ遷移した日時。それまでは`null`                                                      |
| `nextAttemptAt`           | 次の業務試行の予定日時。予定がなければ`null`                                                  |
| `lastErrorCode`           | 最後に保存したエラーの識別子。エラー未発生は`null`。成功後も履歴として残す                    |
| `checks`                  | 各検証の観測結果。値は`pending / passed / not_expected`                                       |

`doPersistence`はDOに保存した値の読み戻し確認、`consumerCompletion`はConsumerによる結果と完了状態の保存確認、`dlqReceipt`はDLQ Consumerによる受信記録の保存確認です。確認対象は初期値`pending`とし、確認できたら`passed`にします。対象外は`not_expected`です。`pending`は未確認を意味し、終端状態でも確認できなければそのまま残します。

`success`と`retry_then_success`ではDO保存とConsumer完了を確認対象にし、DLQ受信は対象外です。`exhaust_retries`ではDO保存とDLQ受信を確認対象にし、Consumerの正常完了は対象外です。`failed`への遷移だけでDLQ確認を合格にしません。DLQ受信前の`dlqReceipt`は`pending`で、受信後に更新します。実行権トークン、内部例外、秘密情報は返しません。

#### 共通エラー形式

アプリが返すAPIエラーは`error`オブジェクトで包み、`code`・`message`・`requestId`を必須にします。HTTPステータスは本文へ重複させません。Accessなどアプリの手前で返される応答は、このJSON形式の保証対象外です。

```json
{
  "error": {
    "code": "IDEMPOTENCY_KEY_CONFLICT",
    "message": "同じ冪等キーが異なる入力で使用されています。",
    "requestId": "b2144431-e8f4-4d7e-9af4-90db622fde92"
  }
}
```

`code`は機械判定用の安定した文字列、`message`は変更を許容する人向けの説明です。クライアントは文言で分岐しません。`requestId`はサーバーがHTTP要求ごとに生成する追跡IDで、サーバーログと対応させます。再送時は別のIDとなり、冪等キーや`jobId`とは区別します。

入力検証エラーに限り、型付きの`details`配列を付けます。各要素の全項目は必須です。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください。",
    "requestId": "b2144431-e8f4-4d7e-9af4-90db622fde92",
    "details": [
      {
        "location": "header",
        "path": "Idempotency-Key",
        "code": "REQUIRED",
        "message": "冪等キーを指定してください。"
      }
    ]
  }
}
```

`location`は`header / path / query / body`です。本文の`path`は`/scenario`のようなJSON Pointerとし、本文全体は空文字で表します。他の場所ではヘッダー名やパラメーター名を使います。詳細の`code`は`REQUIRED / INVALID_FORMAT / INVALID_VALUE / UNRECOGNIZED_FIELD`とし、構文不正なJSONは本文全体の`INVALID_FORMAT`で表します。受信した値やライブラリ固有の検証エラーをそのまま返しません。

| HTTP  | code                       | 用途                                                            |
| ----- | -------------------------- | --------------------------------------------------------------- |
| `400` | `VALIDATION_ERROR`         | JSON・キー・jobIdの形式不正、必須項目不足、未知の項目やscenario |
| `404` | `JOB_NOT_FOUND`            | 参照できる対象ジョブがない                                      |
| `409` | `IDEMPOTENCY_KEY_CONFLICT` | 同じキーで異なる入力                                            |
| `415` | `UNSUPPORTED_MEDIA_TYPE`   | 開始要求のContent-Typeが未対応                                  |
| `500` | `INTERNAL_ERROR`           | 予期しない内部障害。内部例外は返さない                          |
| `503` | `SERVICE_UNAVAILABLE`      | D1障害などで受付・取得を確定できない                            |

TypeSpecでは共通エラーと入力検証エラーを分け、`details`を自由形式にしません。`type`による大分類や再試行可否の真偽値は追加しません。開始要求で結果が不明な場合の再送は、同じ冪等キーを使う規則に従います。ジョブの失敗はGETの`200`応答内の状態で表し、状態取得自体のHTTPエラーとは区別します。

#### 検証用APIの受入条件

- 通常の初回受付は1件のジョブを作成する。同じキー・同じ入力の逐次再送と同時要求は、同じ受付結果を返す。
- 異なる入力でキーを再利用すると`409`になり、元のジョブや入力が変わらない。検証エラー後は同じキーで修正した要求を受け付けられる。
- 受付応答の消失、受付直後、DO初期化後、Queue送信前後の停止から回復できる。DOの初回受信日時とジョブの同一性を保つ。
- 障害を追加しない通常実行では、`success`は試行1回で完了し、`retry_then_success`は試行2回で完了する。両方ともDO保存とConsumer完了を確認する。
- `exhaust_retries`は試行4回で失敗確定する。DO保存とDLQ受信を確認し、失敗確定とDLQ受信の時間差を表現できる。
- キー・UUID・JSON・scenarioの不正、未知の項目、存在しないジョブが契約どおりのステータスとエラー形式になる。ログを`requestId`で追跡でき、応答に秘密情報が出ない。
- 診断ジョブは専用Queue・DLQを経由し、正式データの一覧・集計や正式DOインスタンスへ混入しない。Queueとジョブの用途不一致では実行しない。定期回復でも診断用の配送先を維持する。
- 終端状態への再送は新規実行せず、新しいキーでは新しいジョブを作る。明示的なDBリセット以外で、既存の開発データを削除しない。

#### 後続の失敗ケース・エッジケース

これは最初の検証範囲であり、失敗ケース・エッジケースの検証を完了したとは扱いません。今後、各機能の実装に合わせて一通りのケースを洗い出し、段階的に追加します。追加予定の主な観点は次のとおりです。

| 観点             | 追加するケースの例                                                                   |
| ---------------- | ------------------------------------------------------------------------------------ |

| 状態・削除       | 不正な状態遷移、削除と評価の競合、遅延ジョブによる削除済み記録の復活防止             |
| 環境・構成変更   | テスト間の干渉、環境切り替え時の誤接続、マイグレーション失敗、旧版・新版Workerの共存 |

各ケースには期待する保存状態・画面表示・再試行可否を定め、実施済みと未実施を区別して記録します。上記は洗い出しの起点であり、網羅済みの一覧ではありません。最小骨格のDB変更・環境分離・サンプル移行は検証済みです。今後も変更時の回帰検査を維持します。

## 対象外

- 業務リポジトリ、非公開GitHub、ローカルコードの取り込み。
- コードと経験Markdownを混ぜた面接、面接中の自由な追加コード取得。
- 実技試験、ライブコーディング、取り込んだコードの実行。
- アプリ側での音声の永続保存。
- 複数利用者、ユーザー登録、履歴共有、大規模な認証基盤。
- 過去の別面接をまたいだ自動の一貫性判定。
- 完了済み評価を別モデル・別採点基準で採点し直す機能。
- ベクトルDB、複雑なRAG、複数AIエージェントの導入。
- 本人が話していない成果の補完、模範解答の生成、採用合否の判定。
