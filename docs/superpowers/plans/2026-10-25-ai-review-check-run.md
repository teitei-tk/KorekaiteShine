# AIレビューのCheck Run実装計画

承認済みのCheck Run方式を実装する。実装と検証はこの作業内で進め、PR #13のマージとResolve操作は行わない。

## 設計

`ai-review.yml`は通常CI完了を受ける既存の権限分離を維持する。実行名に起点CIの実行ID・試行番号とモードを固定形式で記録する。専用の`ai-review-check.yml`がAIレビューの開始・完了イベントを受け、APIで実行元を検証して対象PRのheadに`AI review`チェックを作成・更新する。通知だけに`checks: write`を与える。

通常の終了ジョブだけでは元Workflowのキャンセルに巻き込まれるため、独立したWorkflowを使う。起点CIのリポジトリ・イベント・Workflow・SHAを照合する。新規チェック作成時には既存の本人・同一リポジトリ・main向けPR条件も確認する。完了通知は作成済みの古いSHAのチェックも閉じる。

チェックは実行ID・試行番号で区別する。通知を実行IDごとに直列化し、`queue: max`で待機中の完了通知を新しい開始通知に置き換えさせない。開始通知の遅延で完了状態を戻さない。古い試行の遅延通知は新しいチェックを作らず、既存の古いチェックだけを終了させる。

準備・生成・投稿は対象IDと固定理由コードだけを小さなJSON Artifactへ記録する。通知側は生成元と形式を検証して表示する。外部エラー本文やモデル出力は表示しない。記録前の失敗やArtifact取得失敗にはジョブ情報による固定理由を表示し、成功と推測しない。成功は投稿完了または同一リビジョンの投稿済み確認を必要とし、指摘なしやResolveを意味しない。

## 実装手順

- [x] `check-status.test.ts`にPR headへの登録、失敗・キャンセル・再実行・順序逆転・対象外・不正入力の回帰テストを追加し、失敗を確認する。
- [x] `check-status.ts`でCheck Runの照合と更新、`status-report.ts`で小さな結果の受け渡しを実装する。
- [x] 準備・生成・投稿の結果記録を接続し、実処理の失敗理由が渡る回帰テストを追加する。
- [x] Workflowを接続し、仕様書と運用手順に表示の意味と導入条件を追記する。
- [x] `pnpm check`、Actionsロック生成・検証、差分確認を行う。

## 検証の重点

投稿前のSHA変更、投稿だけの再実行、Artifact欠落、古い試行の通知、完了通知より遅い開始通知を検証する。main反映前のためGitHub実環境でのチェック表示は別途確認が必要である。

## 検証結果

`pnpm check`成功（AIレビュー193件、文書ツール13件、計206テスト）。Actionsロック生成・取得元検証はWorkflow追加時に成功し、その後Workflowは変更していない。差分の空白検査も成功した。

初回レビューの起点CI試行固定・待機通知保持に加え、再レビューの単一Artifact展開先と投稿済み判定の2件を修正した。直下展開の成功・失敗、生成元不一致、展開形式の混在、準備段階の投稿済み確認から成功表示までを回帰テストで確認した。古いhead/base、人間のコメント、対象外PRでは投稿済みとして成功にしない。GitHub上の表示・イベント配送はmain反映後に確認する。
