# AIレビュー修正確認の実装計画

> 実行手順: superpowers:executing-plansに沿って、この作業ツリーで順に実装する。

目的: [追加要件](../../spec/ai-review.md)に従い、PRの指摘履歴と修正確認を残す。

構成: 更新ごとに集約コメントを新規投稿する。過去の指摘をコメントIDと連番で識別し、モデルには固定コミットの資料とともに渡す。確認結果には元コメントへのリンクを付ける。既存形式のコメントも読み取る。

技術: 既存のTypeScript、GitHub API、Responses API、Vitest。依存追加なし。

## 制約と確認観点

本人PRの制限、権限分離、資料を実行しない構成、SHA照合を維持する。修正確認は新規指摘3件の枠とは別に全件を対象にする。指摘履歴は最大30件とし、超過は未完了として停止する。

特に、旧コメントの移行、不正な履歴、確認IDの不足・重複、資料不足、投稿直前の対象更新を検査する。

## 作業

- [x] 履歴の読み取りと投稿の回帰テストを追加し、未実装による失敗を確認する。
- [x] `history.ts`で過去の指摘の識別・検証を行い、`prepare.ts`で資料とmetadataへ追加する。
- [x] Schema・プロンプト・`review.ts`で指摘ごとの判定と根拠を必須にする。
- [x] `publish.ts`で履歴を再照合し、新しい集約コメントへ判定と元指摘のリンクを投稿する。
- [x] SDKから投稿までの接続と境界条件を検査し、文書を更新する。
- [x] `pnpm check`を実行し、差分レビューを行う。

## 実装判断

集約コメントの上書きは廃止する。複数の指摘コメントを個別更新する方式より、1回の投稿で結果が揃い、途中失敗からの再実行を扱いやすいため。投稿数は増えるが、過去の履歴を保持できる。

## 検証記録

履歴読み取り、追記投稿、確認ID不足、重複判定のテストが未実装で失敗することを確認後、実装して成功させた。独立レビューで見つかった影響表現の変更による重複とmetadata容量不足も、失敗する回帰テストを追加して修正した。

履歴を含めたmetadataは400KBへ拡張し、資料全体の400KB上限は維持する。件数内でも容量超過時は停止することを要件へ明記した。意味上の同一性はモデルが判断し、同じファイル・発生条件はコードでも拒否する。
