# AIレビュー分割方式の実装計画

> **実装担当向け:** `superpowers:executing-plans`を使い、このセッションで順番に実装する。チェック欄で進捗を記録する。

**目的:** 関連する変更を容量内で分割し、境界と過去指摘を確認してから一括で投稿に進む。

**構成:** 信頼済みGit読み取りから資料索引・作業台帳を生成する。逐次実行器が各作業の根拠と完了範囲を検証し、固定した成果物を投稿ジョブへ渡す。

**技術:** 既存のTypeScript、Node.js、OpenAI SDK、GitHub Actions、Vitest。静的解析には解析専用のTypeScript 5.9.3を別名で追加し、PRコードを実行しない。型検査は既存の7.0.2を維持する。

**設計:** [承認済み設計](../../spec/ai-review-partitioning.md)。PR #13はマージしない。

## 全体の制約

- 原文300,000バイト、JSON400,000バイト、プロンプト500,000バイトを各呼び出しで維持する。
- 最大12回、入力合計3,000,000バイト、各回出力8,000トークン・150秒、生成ジョブ40分。自動再試行しない。
- 必須作業は最大10回・入力2,000,000バイトとし、整理に2回・1,000,000バイトを予約する。
- 履歴最大30件、新規投稿最大3件。unknown型禁止、外部入力は実行時検証する。
- 新規指摘は行スレッド、修正確認は元スレッド。Resolve・再オープンを操作しない。
- 今回はローカル実装と検査まで。push、マージ、有料の実PR実行は行わない。

## レビュー重点

1. 非変更ファイルの増加や巨大な共通ファイルによって、本文全量送信へ戻らないこと（タスク1）。
2. 削除・改名・循環参照・未解決importが黙って消えないこと（タスク1）。
3. 後半の失敗や不正な根拠で完了成果物を作らないこと（タスク2）。
4. 旧形式履歴を省略せず、別単位の候補や既存指摘との重複を残さないこと（タスク2）。
5. 長時間実行・投稿再試行・Artifact改変で認証や投稿の境界を越えないこと（タスク3）。

## タスク1: 資料選択と作業台帳

対象: `tools/ai-review/material.ts`、新規`source-index.ts`・`partition.ts`と対応テスト。

インターフェース: Git読み取り関数から`SourceIndex`を作る。`planReview(metadata, index, patches)`は`ReviewPlan`を返す。台帳は内容ハッシュ付きの`Source`、確認対象`Obligation`、`ReviewTask`、除外理由を持つ。各作業は資料ID・対象ID・過去指摘IDを参照する。

- [x] 関連資料選択、300KBを超える全体の分割、関係両側の原文、巨大原子単位の拒否、削除と履歴、索引上限の回帰テストを先に追加し、失敗を確認する。
- [x] ASTのトップレベル宣言・Markdownの節を原子単位とする索引を実装する。静的import/export、逆参照、明示的なスクリプト・文書リンクを解析する。未解決参照は関連対象で停止する。
- [x] 変更単位・境界単位・履歴単位を決定的に詰め、原文を共有する作業を優先して容量内にまとめる。資料と対象のハッシュ、全件の割り当てを検証する。
- [x] `pnpm --dir tools/ai-review test`で新旧テスト成功を確認する。

## タスク2: 分割実行と結果統合

対象: 新規`partition-review.ts`・`partition-schema.json`・対応テスト、`review.ts`・`prompt.md`。

インターフェース: `runPartitionReview(plan, invoke)`は検証済み`Review`と実行記録を返す。`invoke(task, prompt)`はSDK応答と使用量を返す。各応答は担当対象ID、候補の資料ID、履歴の根拠を含む。

- [x] 作業漏れ、不正根拠、後半失敗、予算超過、履歴全件、重複候補・統合不一致のテストを追加し、失敗を確認する。
- [x] 作業ごとの限定入力・出力検証・使用量集計を実装する。単位完了後に原文付き横断確認を行い、候補と過去指摘の意味上の対応を確認する。必要な候補整理は予約枠で行う。
- [x] 完了対象が台帳と一致するときだけ最終3件を選定する。部分失敗時は成果物を生成しない。
- [x] `pnpm --dir tools/ai-review test`で新旧テスト成功を確認する。

## タスク3: 認証・成果物・Workflow接続

対象: 新規`orchestrate.ts`・`artifact.ts`と対応テスト、`prepare.ts`・`publish.ts`・Workflow、仕様・運用文書。

インターフェース: 実行器が各呼び出し前にWIF交換し、モデル子プロセスへ許可した環境変数と交換済みトークンのみを渡す。`writePartitionArtifact` / `verifyPartitionArtifact`は固定入力・最終出力と完了台帳のハッシュを照合する。

- [x] 毎回のトークン取得、期限不足、子プロセス環境の隔離、改変Artifact拒否、途中失敗・再投稿の結合テストを追加し、失敗を確認する。
- [x] prepareを分割資料生成へ接続し、旧一括prompt生成を通常経路から外す。投稿は完了Artifactのみ受け付ける。
- [x] Workflowを40分と逐次実行器へ接続する。claims診断は維持する。投稿のみの再実行は生成試行のArtifactを参照する。
- [x] 仕様・運用手順・ADRを更新する。`pnpm check`とActionsロック検査を行う。期待結果: 全検査成功。
- [x] 独立レビューで重要な問題を確認し、必要な回帰テストと修正を加える。

## 実行記録

開始時の土台はPR #12の`1dfa33d`。設計書と文書案内が未コミット。既存の113テストと文書検査は設計作成時に成功している。

実装中の判断: TypeScript 7の従来解析APIが利用できなかったため、解析専用依存を追加した。依存が一つ増える負担を引き受け、PR設定の評価や型検査版の変更を避ける。各作業のテストを失敗から成功へ確認し、全体検査も実行した。コミット・pushは今回の依頼に含まれないため、変更は未コミットで保持する。

独立レビューで指摘されたP2は3件とも修正した。履歴のfixedと再発候補の矛盾、TypeScriptのimport型・import-equals、Workflowの任意script名・動的scriptについて、回帰テストの失敗を確認して修正した。判断を保留した指摘や軽微な先送りはない。

再レビューで指摘された3件も修正した。失敗対象・理由コードの記録、Markdown参照形式リンクの収集、別バッチの相手原文なしでの重複棄却について回帰テストの失敗を確認し、修正した。外部エラー本文を残さず、SDK・子プロセス間でも固定の理由コードだけを伝える。

準備段階で残っていたP2も修正した。実際の収集・分割・事前検証を通す回帰テストで、収集上限、参照未解決、入力予算超過、外部エラーの安全な記録を確認した。CLIの非ゼロ終了と`allowed=false`、正常終了・対象外の動作も検査対象にした。
