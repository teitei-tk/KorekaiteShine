# 通常PR検査の5〜6分化と長時間検査の分離計画

> **実装担当エージェントへ:** `superpowers:executing-plans` または `superpowers:subagent-driven-development` を使い、タスク単位で実装・検証する。チェックボックスは実行時に更新する。

**目的:** 通常のPR向けCIを5〜6分に短縮し、実時間30・120・300秒の再試行とDLQ到着の検査を別ワークフローで維持する。

**構成:** 既存の境界テストを4ジョブ、短い実配送・回復テストを3ジョブへ分割する。長時間検査は夜間・手動・関連変更のPRで実行し、通常CIとAIレビューを待たせない。

**技術:** 現行のGitHub Actions、Node.js、pnpm、TypeScript、Vitest、Void、ローカルD1。依存更新や本番の再試行間隔変更は含めない。

**仕様:** [MVPの設計基準](../../spec/mvp.md#設計基準)、[テスト方針](../../spec/mvp.md#テスト方針)、[ADR 0010](../../adr/0010-queue-contracts-and-job-control.md)、[環境分離のADR](../../adr/0009-explicit-environments.md)。本計画の実行構成は、利用者が選択した「通常PR検査を5〜6分にし、長時間の実時間テストは別枠に残す」方針を具体化した提案である。

## 現状と目標

基準はPR #70、head `507e5d57c4c605fb82834d780710548463d49500` の[CI実行](https://github.com/teitei-tk/KorekaiteShine/actions/runs/41818832055)。実装開始時にこの変更が作業ブランチに含まれることを確認する。

| 検査                  | 現状                      | 変更後の目標                                   |
| --------------------- | ------------------------- | ---------------------------------------------- |
| 通常CI全体            | 12分21秒                  | 開始から完了まで360秒以内、目安300〜360秒      |
| 境界                  | 25ファイル104件、12分17秒 | 4ジョブで分担、最長ジョブ360秒以内             |
| 結合                  | 7ファイル15件、11分38秒   | 通常14件を3ジョブ、長時間1件を別ワークフロー   |
| 全4回失敗の実時間検査 | 待機だけで450秒           | 30・120・300秒を維持、通常CIの時間目標から除外 |

ファイル単体の実測は `check-object.test.ts` 約299秒、`topology.test.ts` 約252秒、`restart.test.ts` 約294秒。単純なファイル数均等分割ではなく、実測時間を用いて割り当てる。runner負荷と待ち行列により変動するため、達成は実装後のCIで判定する。

通常CIの成功は長時間検査の成功を意味しない。関連変更では別検査もPRに表示され、その確認まで含めたマージ判断には6分以上かかり得る。

## 採用方針と制約

- 採用: 通常CIの並列分割と、長時間1ケースの実行頻度分離。既存の時計制御による境界検査を維持する。
- 不採用: 全実時間検査を毎PRの通常CIに含める。450秒の待機だけで目標を超える。
- 不採用: 本番の再試行間隔を縮める、または実配送検査をすべてmockへ置き換える。検証の意味が変わる。
- `execution.test.ts` は既に30・120・300秒の次回時刻、期限1ms前の拒否、全4回失敗を時計制御で検査している。新しい時計注入機構を本番へ追加しない。
- 30秒の一時失敗後成功、実Queueの再配送、60秒周期の停止後回復は通常CIに残す。
- `pnpm test` の境界検査と `pnpm test:integration` の全結合検査というローカルの意味を維持する。通常PR専用の部分集合は別コマンドにする。
- HTTP契約は境界だけに所属する。既存119件の検査を削除せず、通常118件・長時間1件へ対応づける。追加の回帰検査は別集計する。
- 各runner・各ケースは固有のrunIdとD1・Queue・成果物を使う。再起動を検査するケースの環境は共有化しない。
- CI内で同じrunnerのWorker数を無制限に増やさない。境界分割は初期値2 workersとし、実測で調整する。テスト上限を短縮して失敗させることを高速化と扱わない。
- 外部サービス・クラウドリソース・リポジトリ保護設定の変更、マージは本計画の実装に含めない。

## 長時間検査の実行・結果の扱い

新規 `.github/workflows/ci-realtime.yml` の名称を `Worker real-time checks` とする。

- 毎日03:17 JST、cron `17 18 * * *`（UTC、mainの最新版）で実行する。GitHub側の遅延はあり得る。
- `workflow_dispatch` で手動実行できる。任意のSHA入力を実行文字列へ展開せず、選択したrefをcheckoutする。
- PRのopened・synchronize・reopened・ready_for_reviewで軽量な変更判定ジョブを動かす。通常CIと同時に開始し、`needs`で相互依存させない。
- 対象は `apps/**`、`packages/**`、`tools/local-integration/**`、`.github/workflows/**`、ルートと各パッケージの依存宣言・ロック、Node設定、workspace設定。文書だけの変更は除外できる。
- 変更一覧はcheckout後のmerge-baseからNUL区切りのgit diffで取得する。削除・移動を含める。取得不能、比較元不明、未知の非文書パスは実行側に倒す。GitHubのトップレベルpathsフィルターだけに依存しない。
- mainのschedule・手動実行は変更判定なしで実行する。PRは標準のpull_requestイベントを使い、書き込み権限や秘密値を渡さない。
- `Realtime result` 集約ジョブは、対象外・成功・失敗・中断を区別してSummaryへ記録する。対象なのにテストがskipされた場合を成功にしない。対象外なら明示したうえで正常終了する。
- 失敗を `continue-on-error` で隠さない。GitHub標準の実行結果・通知を使い、外部への通知サービスは追加しない。関連変更ではこの結果を確認してから取り込む運用を文書化する。
- 必須チェックの登録は自動変更しない。既存設定を確認し、導入時に必要な設定変更があれば利用者へ別途提示する。
- AIレビューは既存の `CI` 成功を起点とする。長時間検査をworkflow_runの購読対象に加えず、二重レビューを防ぐ。

## レビューで重点的に確認すること

1. 新しいテストファイルが分類から漏れてもCIが緑にならないこと（タスク2）。
2. 削除・移動・多数の変更・比較元不明でも必要な長時間検査を省略しないこと（タスク3）。
3. 分割したシナリオが暗黙に別ケースの環境や結果へ依存していないこと（タスク1・2）。
4. 長時間検査の失敗・中断と通常CI成功を区別し、AIレビューを二重に開始しないこと（タスク3）。
5. runner待ち行列や計測のばらつきを隠して5〜6分達成と報告しないこと（タスク4）。

## タスク1: 長時間シナリオだけを独立させる

対象: end-to-end、realtime-retries、integration-runの検査、package scripts。

- [x] 元の15件のテスト名・assertionと実行ファイルの対応表を保存する。

- [x] end-to-endの共有beforeAllが全3シナリオを直列実行する構造を解消する。正常と30秒後成功は各自の結果を取得し、全4回失敗の既存assertionはrealtime-retriesへ移す。CLIの全シナリオ実行は維持する。
- [x] 通常の境界コマンドから新しい長時間ファイルを除外し、全結合コマンドには追加する。PR用の結合は14件、長時間用は1件とする。
- [x] 正常系・一時失敗・長時間失敗を単独実行して成功を確認する。実時間検査は `clock: real`、間隔30・120・300秒、全4試行、DLQ受信、60秒周期の記録を維持する。
- [ ] 変更前後の15件の対応が一致することを確認し、必須フックを通してコミットする。

## タスク2: 通常CIを時間で均等に分割する

対象: test-suites、run-test-suite、package scripts、ci.yml。

**インターフェース:** `selectTestFiles(suite: 'boundary' | 'integration-pr' | 'realtime' | 'integration-all', shard?: number): readonly string[]`。shardはboundaryで1〜4、integration-prで1〜3。省略時は集合全体。不明な値はエラー。実行CLIは `node tools/local-integration/src/run-test-suite.ts <suite> [shard]`、子プロセスのcwdはlocal-integrationに固定する。

- [x] ファイル集合の交差が空、和集合が全ローカルテスト、全結合が通常結合と長時間の和集合になる検査を書く。存在しない登録・未登録ファイル・範囲外shard・空集合も失敗させる。ルートの `pnpm test` でRedを確認する。
- [x] PR #70の実測で重い順に割り当て、各分割の合計時間を均等化する。初期結合グループは「restart」「cli-recoveryとisolation」「end-to-end・formal-routing・dlq-restart・queue-retry」とする。
- [x] ファイル一覧を一元化し、通常コマンド・全結合・分割ジョブが同じ定義を使う。実際のVitest列挙結果との一致を検査する。自己検査ファイルも一覧へ含める。
- [x] 境界4、結合3のmatrixを作り、`fail-fast: false` とする。既存の型検査・契約生成を維持し、DB保持用の準備を各結合runnerで実行する。各ジョブは他の検査完了を待たない。
- [x] 子テストの非ゼロ終了、signalによる中断、不正な選択を成功へ変換しない回帰検査を追加してGreenを確認する。
- [ ] 7分割それぞれを検査し、ファイルとケースの欠落・重複なしを確認する。全結合コマンドが長時間1件も含むことを確認してコミットする。

## タスク3: 長時間ワークフローとレビューの境界を整える

対象: ci-realtime、ci-selection、AIレビューの回帰検査、関連文書。

**インターフェース:** `requiresRealtimeTests(paths: readonly string[] | null): boolean`。nullは変更一覧の取得不能でtrue。空配列と既知の文書だけはfalse。未知の非文書変更はtrue。

- [x] 文書のみ、各対象ディレクトリ、依存更新、削除・移動の旧新パス、未知の非文書、null、300件以上の変更一覧を検査し、Redを確認する。
- [x] 変更判定を実装し、上記の実行条件を持つ独立ワークフローを追加する。scheduleとdispatchは必ず長時間検査を実行する。
- [x] 対象外・成功・失敗・中断・対象なのにskipの集約結果を検査する。検査対象・head SHA・結果をSummaryへ記録する。
- [x] AIレビューの起点が通常CI成功だけであることを回帰検査する。通常CI失敗時は開始せず、長時間検査完了では追加開始しない。関連PRで長時間検査が未完了でも通常CI成功後のレビューは開始できることを文書化する。
- [x] `gh actions-lock --verify` で検査する。新規ワークフローに必要なロック更新だけを行い、既存Actionの更新を混ぜない。
- [ ] 開発手順・文書検査README・AIレビュー手順・検証記録に実行範囲と失敗対応を反映し、`pnpm check:docs` を通してコミットする。

## タスク4: 5〜6分を実測して調整する

- [x] `pnpm check`、開発DB保持用準備、全結合検査を実行する。119件の既存ケースと追加回帰検査の成功を確認する。

- [ ] 通常CIを同じheadで3回測定する。workflow開始〜完了、runner待ち時間、setup、各テスト、最長ジョブ、合計runner分を記録する。初回のキャッシュ差も残す。

## 完了条件と戻し方

- 通常CIの3回測定、全テストの対応表、長時間検査の実測証拠がそろう。
- 通常CI成功と全実時間検査成功を表示・文書で区別できる。
- 長時間検査の運用開始後に失敗が続く場合は、原因を直すまで関連変更の取り込みを見合わせる。
- 問題があればワークフローと選択コマンドの変更を戻し、PR #70の2ジョブ構成・全結合15件へ復帰できる。業務データの移行はない。
