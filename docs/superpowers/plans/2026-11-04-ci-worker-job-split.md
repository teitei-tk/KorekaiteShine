# Worker境界・結合テストのCI分割と起動負荷削減計画

> 実装担当者へ：`superpowers:executing-plans`を使い、チェック項目ごとに実装・検証する。チェック欄はPR作成前のローカル作業記録。GitHubでの最終検証結果は実装PR本文に記録する。測定結果は[検証記録](../../research/ci-worker-test-performance.md)を参照する。

**目的：** Worker関連CIの検査範囲を維持し、境界テストと実時間の結合テストを並列化し、境界テストの環境準備の重複も減らす。

**構成：** 同じ`CI`ワークフロー内の独立した2ジョブへ分ける。HTTP契約テストは通常の`test`に残し、`test:integration`から除外する。通知時刻の境界8ケースは、計測後にファイル内でWorker環境を再利用する。

**使用技術：** 既存のGitHub Actions、pnpm、Vitest。依存追加・バージョン変更は行わない。

**要件の根拠：** 利用者が指定した「境界テストと結合テストの別ジョブ化」「HTTP契約テストの重複解消」と、追加依頼の「ケースごとの環境準備の負荷削減」。[設計基準](../../spec/mvp.md#設計基準)、[ADR 0010](../../adr/0010-queue-contracts-and-job-control.md)、[現在のCI運用](../../../tools/docs/README.md#ciでの実行)も参照する。

## 現状と選択理由

[PR #68の実行](https://github.com/teitei-tk/KorekaiteShine/actions/runs/41806350844/job/126494226135)は24分9秒。境界テスト96件が12分13秒、結合テスト17件が11分28秒で、同じrunnerで直列実行されている。HTTP契約テスト2件は両方に含まれる。

利用者指定の2ジョブ化を採用する。HTTP契約を境界側に残すのは、日常の`pnpm test`と`pnpm check`で引き続き検査できるため。結合側だけに残す案では通常検査から外れ、HTTP専用の第3ジョブを設ける案では今回の範囲に対して準備処理が増える。

同程度のrunner性能で同時開始できれば、通常CI全体の所要時間は約12〜14分が目安になる。ただし未実測であり、runner待ち時間を含む保証ではない。runnerの合計使用時間は半減せず、準備処理の重複も増える。

## 制約とレビューの観点

- 30・120・300秒の再試行待機、60秒周期の回復、DB保持・環境分離の検証は維持する。本番ロジックは変更せず、境界テストの起動・後処理だけを変更する。既存の業務条件のassertionは維持する。
- 通常テストと結合テストの対象集合は重複せず、変更前の和集合を維持する。HTTP契約は開発・ビルド済みの両方を残す。
- 各ジョブは独自にcheckout・依存インストール・共有契約生成を行う。生成物や`.local`をジョブ間で共有しない。
- ワークフロー名`CI`、起動イベント、権限、Actionsの固定版、インストール時の`--frozen-lockfile --ignore-scripts`を維持する。実AI・クラウド配置は対象外。
- 必須チェック名への依存と、AIレビューがCI全体の成功を待つ動作を確認する。必須チェック設定の変更は本計画のコード変更に含めず、必要なら対象と変更案を提示する。

## タスク2：CIのWorker検査を2ジョブへ分ける

**変更：** `.github/workflows/ci.yml`、必要な場合のみ`.github/workflows/actions.lock`。

**入力：** タスク1の既存コマンド。**出力：** 互いに`needs`を持たない次の2ジョブ。

| ジョブID            | 表示名                     | 検査内容                                                 | 上限 |
| ------------------- | -------------------------- | -------------------------------------------------------- | ---- |
| `local-boundaries`  | `Local Worker boundaries`  | 共有契約生成、local-integrationの型検査、通常`test`      | 25分 |
| `local-integration` | `Local Worker integration` | 共有契約生成、保持確認用データの準備、`test:integration` | 25分 |

上限は初回の分割で縮めず、現在の25分を両方に引き継ぐ。短縮効果は完了時刻で測り、上限の見直しは実測後に判断する。

- [x] GitHubの保護ルール・rulesetの必須チェックを読み取り、旧表示名を要求していないか確認する。取得不能なら未確認事項として残し、保護設定が不要とは断定しない。
- [x] 現在のセットアップを両ジョブへ配置し、境界側で`pnpm --filter @korekaite/local-integration typecheck`と`pnpm --filter @korekaite/local-integration test`を実行する。
- [x] 結合側で`pnpm prepare:integration`の後に`pnpm test:integration`を実行する。保持確認用データは結合側のrunnerで作り、準備失敗時は後続を失敗扱いにする。
- [x] YAML構造と実行対象を確認する。2ジョブ間に順序依存がなく、テストの失敗を隠す`continue-on-error`がなく、既存6ジョブと合わせて8ジョブになることを確認する。
- [x] Actionsロックを検証する。ジョブ内の利用箇所追加により更新が必要な場合だけ既存手順で再生成し、Actionの参照先が意図せず変わらないことを確認する。

## タスク3：環境準備・DB操作・停止の時間を測る

**変更：** `tools/local-integration/tests/helpers/diagnostic-runtime.ts`、`tools/local-integration/tests/dispatch-notifications.test.ts`。必要な内訳の計測箇所は`src/runtime.ts`と`src/database.ts`に限定する。

現ログからは、通知時刻8ケースの合計161.992秒までしか分からない。起動が大半という断定や、短縮目標秒数の設定は計測前に行わない。`runDatabaseCommand`は呼び出しごとに準備用NodeプロセスとVoid CLIを起動するため、DB操作も独立して計測する。

- [x] `performance.now()`で、ケース別の環境起動、DB投入・照合、検査本体、停止、成果物削除の時間と回数を記録する。一時的な計測は`LOCAL_TEST_TIMING=1`でのみ有効にし、SQL・入力値・環境変数は出力しない。
- [x] 起動の内訳はmigration、ソース・設定準備、Workerのready待ちまでとする。親の起動時間とその内訳を二重加算しない。所有プロセスをまたぐ区間は各プロセス内で経過時間を測り、同じケースへ対応付ける。
- [x] 同じマシン・並列度で対象ファイルを3回実行し、各区間の中央値と最大値、起動回数8回を記録する。固定版CLIで確認した方法で対象ファイルだけを実行する。ソケット起動を制限される場合はサンドボックス外で実行する。
- [x] 計測用フックを残す場合は既定無効とし、成功・失敗の両方で記録され、既存の例外を覆い隠さないことをRed/Greenで確認する。短期調査だけに使った計測は改善確認後に削除する。

## タスク4：通知時刻の8ケースで環境起動を共有する

**変更：** `tools/local-integration/tests/dispatch-notifications.test.ts`。
**追加候補：** `tools/local-integration/tests/helpers/notification-runtime.ts`。このファイル専用のライフサイクルをまとめる必要がある場合に追加する。

**境界：** 既存の`withDiagnosticRuntime`は個別起動の意味を保つ。全テスト共通のキャッシュやグローバルなランタイム共有へ変更しない。

8ケースは同じ起動オプションで、`dispatchForTest`が実Queue送信を置き換えて要求を記録している。まずこのファイルだけで`beforeAll`起動・`afterAll`停止を採用し、ケースは直列実行する。新しいrun IDと独立D1はファイル単位で維持する。再起動、停止後回復、DO保存、実Queue配送、migration自体を確認するテストは個別環境を維持する。

- [x] 状態の持ち越しを捕まえる回帰テストを1件追加する。前ケースの未送信outboxと送信失敗を残した状態から、次ケースの通知だけが検査対象となることをassertし、ルートの`pnpm test`でRedを確認する。
- [x] 共通環境を1回起動し、ケース間で当該ケースが作った`job_outbox`と`jobs`を外部キーの依存順に清掃する。IDを記録して対象を限定し、件数ゼロを確認してから次へ進む。UUIDを変えるだけでは未送信通知の走査を防げない。DB全体の`reset-seed`は使わない。
- [x] 既存8ケースの期待値と個別のテスト名を維持して共通環境へ移す。ルートの`pnpm test`でGreenを確認する。ケース内の複数通知と部分失敗・再送のシナリオは分割しない。
- [x] 検査または清掃が失敗した場合はその時点のDB・ログを保持し、汚染された環境で後続を続けない。`afterAll`では失敗時もWorkerを停止する。起動失敗・停止失敗で元のエラーを失わないことも1件ずつRed/Greenで確認する。
- [x] 対象ファイルの正順・逆順・単独ケース実行で同じ結果を確認する。別run IDの同時実行でもDB・ログが交差しないことを確認する。追加テストによる件数増はタスク1の既存111件の保持とは分けて記録する。
- [x] タスク3と同じ条件で3回測り、起動・migrationが各8回から各1回になり、清掃時間を含むファイル全体の中央値が改善したことを確認する。停止後に子プロセス・環境ロックが残らないことを確認する。

DB CLIの起動負荷がなお支配的でも、この変更と同時に任意SQLを実行するHTTP入口は追加しない。まず投入・照合のバッチ化で安全に減らせる呼び出しを計測から特定する。他のファイルへの共有化は、状態の分離と実測効果を確認した後に個別に判断する。

## 完了条件

2ジョブが並列実行され、検査対象の欠落・重複がなく、ローカル検査とCIが成功していること。通知時刻8ケースは起動・migrationが各1回となり、順序依存・状態混入・後処理漏れがないこと。短縮時間はジョブ分割と環境再利用の効果を分けて実測値として報告する。実装PRを扱った場合は[エージェント作業手順](../../runbooks/agent-workflow.md#prを扱った作業の完了条件)に従い、URL・最終head・検査結果・PRの状態を残す。
