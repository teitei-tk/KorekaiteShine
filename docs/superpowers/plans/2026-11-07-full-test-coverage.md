# 行 文 関数 分岐のカバレッジ100%への実装計画

> 実行担当へ：実装時は`superpowers:executing-plans`を使い、チェックボックス単位で進めます。委譲を選ぶ場合は`superpowers:subagent-driven-development`を使用します。実装状況は各タスクのチェックボックスで管理します。クラウド操作はこの計画の対象外です。

**目標：** 生成物・型宣言・テスト専用コードを除いた手書きTypeScript・JavaScriptについて、未計測ファイルを残さず、行・文・関数・分岐をすべて100%にし、CIで維持する。

**構成：** 計測対象を台帳で固定し、通常テスト、ローカルWorker境界テスト、Node.js子プロセスの結果を、同一ソース・同一の計測位置定義に揃えて統合する。計測の正しさを先に確認し、既存テストを再計測してから不足する振る舞いのテストを追加する。

**技術：** Node.js 26.12.1、pnpm 12.15.0、Vitest 5.1.0、TypeScript、既存のVoid・workerd・D1。追加する計測依存の方式と固定版はタスク1の互換性検証で決定する。

**根拠：** [カバレッジ調査](../../research/test-coverage.md)、[MVP仕様書の設計基準](../../spec/mvp.md#設計基準)、[API契約のADR](../../adr/0006-typespec-api-contracts.md)、[ジョブ制御のADR](../../adr/0010-queue-contracts-and-job-control.md)、[診断機能分離のADR](../../adr/0011-access-and-diagnostics-isolation.md)。用語は[GLOSSARY.md](../../../GLOSSARY.md)、レビューは[コードレビュー基準](../../../CODING_STANDARDS.md)に合わせる。

| 行   | 49.66% | 1,748    | covered = total |
| 文   | 49.76% | 1,794    | covered = total |

実行要素のある99ファイルの内訳は、実行記録なし41、部分網羅47、4指標100%が11。未網羅数は追加テスト件数ではない。計測方式の変更で分母も変わるため、タスク2で新しい基準値を確定する。割合の丸めによる100.00%ではなく、各指標の件数が完全に一致することを判定する。

対象はアプリだけでなく、共有パッケージ、開発ツール、生成スクリプト、DBスキーマ、実行設定、今回追加する計測ツール自身も含む。既に100%の11ファイルも回帰検査から外さない。

除外は生成API・生成ルート・ビルド成果物・生成SQL・依存、型宣言・TypeSpec宣言、テスト本体・専用fixture・補助、テストランナー設定とする。除外理由を台帳に残し、生成する処理そのものは除外しない。計測要素0件の6ファイルは、型のみ・空エントリ・再export・実行設定を個別確認する。特にVite・Void設定の実行を「0件だから完了」としない。

シェル2本とWorkflowはV8の4指標で測れない。この計画の100%は上記TS/JS対象集合に対するものと明記し、シェル・Workflowの既存動作検証を維持する。これらにも同じ4指標を適用する要件が追加された場合は、対応する計測方式と分母を別途設計する。

## 共通制約と選定方針

- 既存の単体・HTTP・DO・D1・Queue・本番成果物分離テストを維持する。境界テストをすべてモックに置換しない。
- 負の実行回数が出た`coverage.autoAttachSubprocess`の単純な再有効化は採用しない。異なる変換結果を生のV8オフセットのまま合算しない。
- 計測できないものを除外して100%にしない。`ignore`コメント、分岐の省略、ファイル一覧の固定漏れで数字を上げない。
- 到達不能な実装は根拠を確認する。挙動を保持して整理できる不要コードは回帰テスト付きで削除する。必要な防御分岐はテスト可能な境界へ整理する。どちらもできなければ未達として残す。
- 外部GitHub投稿・実AI呼び出し・クラウド配置を通常のカバレッジ取得条件にしない。外部応答は境界で制御し、ローカルの実プロセス・ファイル・権限検査を組み合わせる。
- パッケージの保護設定を弱めない。固定版で互換性を確認し、追加依存は`pnpm-lock.yaml`に記録する。一時ディレクトリのツールに依存した状態で完了としない。
- 子プロセス回収が必要な環境はテスト実行側で対処する。実装の停止確認やタイムアウトを数字のために弱めない。

採用案は「計測方式の互換性検証 → 計測の接続 → 再集計 → 領域別のテスト追加」である。先に単体テストだけを増やす案は、既存の境界テストとの重複と、Worker実行経路の取りこぼしが残る。Workerや運用ツールを除外する案は、調査と今回の対象範囲を縮めるため採用しない。この選定は計画上の提案であり、未検証の収集APIが使えるとは仮定しない。

## 進め方と作業の分割

依存順は`1 → 2 → 3〜8 → 9`。タスク3〜8は同じ確定済みの計測形式を利用し、共有設定を同時に変更しない単位で分割できる。実施順の推奨は、評価の試行制御、診断API・画面、Worker・DB、生成・文書ツール、ローカル実行ツール、AIレビューである。タスク1の互換性が未確認のため、完了日や追加テスト総数はまだ固定しない。

各領域は一度に一つの振る舞いを追加する。共通のテストサイクルは次のとおり。

1. ケース名、入力、期待する返り値・副作用・呼び出してはいけない処理を決め、テストを1件書く。
2. 追加箇所のテストを実行する。機能追加・修正は意図したRedを確認する。既存動作を補うテストが最初から通る場合は、対象の振る舞いだけを一時的に壊してそのテストが失敗することを確認し、すぐ戻す。失敗を作るための製品仕様変更はしない。
3. 必要な場合だけ最小の実装修正を行い、追加箇所のテストでGreenを確認する。
4. 当該領域の計測で狙った未実行位置が埋まったことを確認する。変更の区切りで関連する実境界テストも実行する。
5. リファクタリング後も同じ検査を通す。各タスク完了時にルートで`pnpm test`を実行する。レビュー可能な単位で差分・根拠・実測値をまとめ、commit前検査後に記録する。

2026年11月7日、利用者が「追加箇所のRed/Green＋タスク完了時に全テスト」への変更を承認したため、この手順をAGENTS.mdのテスト1件ごとの全体実行より優先する。

下記の新規ファイル・コマンドは各タスクで実装する。未完了のコマンドが利用できるとは扱わない。既存の実行手順は[文書検査](../../../tools/docs/README.md)と[ローカル開発手順](../../runbooks/local-development.md)を正とする。
