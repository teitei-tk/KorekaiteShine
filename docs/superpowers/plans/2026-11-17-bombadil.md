# Bombadilによる画面探索の実装計画

> 実装担当エージェントへ：superpowers:executing-plansを使い、各タスクを順に進めてください。チェック欄は実装と検証の完了後に更新します。

**目的：** `/practice`の材料確認と履歴・削除について、既存の固定シナリオにない操作順による不整合を検出する。

**構成：** 既存のPlaywright＋Cucumberを維持し、Bombadilを時間制限付きの補助探索として追加する。`tools/e2e/runtime.mjs`のPR用ランタイムを再利用し、実行ごとに独立したtest環境と模擬AIを起動する。初期導入はローカルと手動CIまでとする。

**使用技術：** Bombadil、TypeScript、既存のVitest・Playwright・ローカル3 Workers。Bombadilとブラウザの採用版はタスク1で互換性と取得条件を検証して固定する。

**設計根拠：** 2026年11月17日の会話で確認した段階導入方針、および[MVPの設計基準](../../spec/mvp.md#設計基準)、[材料取り込み](../../spec/mvp.md#材料の取り込み)、[履歴と保存](../../spec/mvp.md#履歴と保存)、[保持と削除](../../spec/mvp.md#保持と削除)。環境分離は[ADR 0009](../../adr/0009-explicit-environments.md)、削除と評価の責務は[ADR 0010](../../adr/0010-queue-contracts-and-job-control.md)に従う。

2026年11月17日、タスク1の適合性検証を実施した。[検証記録](../../research/bombadil.md)に固定版、成功した範囲、再現の制約を記載する。macOSとLinuxのローカルコンテナでアプリを通す検証を確認した。GitHub runner上での正式ランナーの検証はタスク5で行う。初期導入に成功してから音声操作へ進む。

計画作成時に失敗した既存の`tools/coverage`は、mainの修正`878457d`（PR #120）を取り込んだ後、macOSで96件すべて成功した。タスク1ではBombadilを含む実行経路について、macOSとLinux CIそれぞれの互換性を確認する。

## 範囲と共通制約

- 初期対象は材料の入力・送信確認・テーマ選択と、保存済み面接の履歴・詳細・削除。音声開始、評価再実行、複数タブ、実AI、クラウド環境の検証は含めない。
- 既存の[音声E2E](../../../tools/e2e/README.md)とWorker結合検査を置換しない。Queue配送、実行権、音声停止、採点品質はそれぞれ既存の検査で扱う。
- Node.jsは`.node-version`、pnpmはルートの`packageManager`に従う。`minimumReleaseAge: 1440`、`strictDepBuilds: true`、`blockExoticSubdeps: true`、`trustPolicy: no-downgrade`、`trustLockfile: false`とインストール時の`--ignore-scripts`を維持する。
- `startVoiceRuntime({ profile: 'pr' })`を使い、`E2E_APP_ROOT`は対象チェックアウトの絶対パスに固定する。任意URLやliveプロファイルを受け付けない。開発DBをリセットしない。
- 架空のMarkdown・テーマ・発言だけを使う。ブラウザとBombadil子プロセスへ実AIの資格情報を引き継がない。
- HTTPの型は生成済み契約を利用し、TypeSpecと別の入力・応答Schemaを作らない。DBの初期データは既存スキーマとfixtureの作成手順に従う。
- 通常テストは新しいケースを1件ずつ追加し、ルートの`pnpm test`でRed、最小実装後にGreenを確認する。探索の偶然の失敗をRedの代用にしない。
- 新規文書は日本語で書く。CIの権限、Secrets、必須チェック設定、クラウド資源は変更しない。

## 確認する性質

「画面にそう表示される」と「サーバーでそう処理された」を分けて判定する。DOMだけで送信禁止や保存結果を保証したと記録しない。

| 領域       | 操作の組み合わせ                       | 合格条件と観測先                                                                                                 |
| ---------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 材料確認   | 入力、確認、編集、確認解除、分析       | 未確認・空白のみ・32,768バイト超では分析操作が無効。未確認の内容で分析要求が発生しないことは要求記録でも照合する |
| 材料変更   | 分析、テーマ選択、材料の変更           | 確認が解除され、旧テーマ候補と選択状態が消える。新しい内容を確認してから再分析できる                             |
| 応答待ち   | 分析要求、連打、画面離脱、再表示       | 一つの処理中に分析要求が重複せず、離脱前の結果が別の準備画面を上書きしない                                       |
| 履歴・詳細 | 異なる面接を開く、戻る、再読み込み     | 選んだ面接のテーマ・発言・評価だけを表示し、他の面接の遅い応答が混ざらない                                       |
| 削除       | 対象確認、取消、確定、戻る、再読み込み | 取消では削除要求がなく記録が残る。削除成功後は再取得した一覧から消え、詳細APIでも取得不能である                  |

削除の合格条件は成功応答の確認後に適用する。読み込み中の一瞬の表示や、削除直後の取得不能を一律に不具合としない。遅延・取消・上限など想定内の応答は、対象APIと操作条件を限定して扱う。

## レビューで重点確認する条件

1. 空白、日本語のバイト境界、確認後の編集で、表示上のボタン状態と実際の送信が一致すること。タスク3で固定ケースと探索の両方を検査する。
2. 遅い応答、画面離脱、削除の競合で別の面接を表示しないこと。タスク4で遅延応答を固定して検査する。
3. 起動失敗・時間切れ・SIGINT・SIGTERMで子プロセスとWorkerが残らず、失敗の証拠を失わないこと。タスク2で検査する。
4. 操作生成が停止したり、条件の前提に一度も到達しないまま終了しても、探索成功と判定しないこと。タスク3・4・5で到達状況を判定する。
5. 再現時に初期データ・仕様・ブラウザが変わった場合、再現不能と性質違反を混同しないこと。タスク2・5で検査する。

- [x] 表の合格条件を判定関数とBombadilの性質へ実装する。遷移途中の無効化状態と分析結果の確定を区別し、実装内部のフラグをそのまま正解判定にしない。

## タスク4：履歴・削除の性質と遅延応答を実装する

**入出力：** fixtureの面接IDと固有テーマ・発言を期待値とし、表示中の詳細、削除要求と成功応答、一覧・詳細APIの取得結果を照合する。削除済み集合は成功応答を根拠に更新する。

## 完了条件と後続判断

2026年11月21日、上記の共有検査を確認した。全体計測は1,767件が成功し、実装を変えずに起動中断の固定ケース1件を同じ台帳へ追加計測した。`pnpm check:coverage`は全250対象を照合し、実行要素がある247ファイルすべてで4指標100%となった。要素なしの3ファイルは到達済みと区別する。計測負荷の修正、初回に失敗した既存ケース、GitHub手動CIの未実行は[検証記録](../../research/bombadil.md)に残す。

初期導入の完了条件は、2領域の必須条件への到達、意図的な違反の検出、初期状態からの再現試行、失敗・中断時の停止と証拠保存、既存検査の成功。探索で違反がなかったことを、全操作順の正しさの証明やカバレッジ100%と説明しない。

導入後は手動実行の所要時間、未到達率、誤検知、再現成功率、既存テストになかった不具合を記録する。PR必須化・定期実行・探索時間の拡大は、この記録を見て判断する。

音声操作の探索は別の実装計画とする。既存の模擬AI・音声probeをBombadilから利用できるか、停止表示と実際の送信・再生停止を照合できるかを先に確認する。複数タブ対応が未確認の間は、タブ引き継ぎを既存Cucumberに残す。
