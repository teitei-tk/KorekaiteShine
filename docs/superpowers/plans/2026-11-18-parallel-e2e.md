# E2Eシナリオの並列化

PRの19シナリオを4台のrunnerへ配分する。シナリオ単位の一時ディレクトリ・実行ID・Worker・DB・ブラウザの分離を維持する。同一runnerでWorkerを増やす方式よりリソース競合を抑えられ、既存の時間履歴・欠落検査を再利用できるため、別runnerを選ぶ。

## 実装と検証

- Cucumberの公式検出APIで`@pr`対象をfeatureと行番号で列挙する。Scenario Outlineの各Examples行も独立した対象とする。
- 既存の計画処理へシナリオを登録し、4シャードへ時間重みで配分する。mainの成功履歴がなければ等重みを使う。
- 各対象を完全一致の行指定で実行し、0件・複数件・失敗を拒否する。各シナリオの時間と実行IDを記録する。
- PRの依存判定は従来どおりE2E全体を安全側に選ぶ。実AIを使うlive実行は従来の手動入口を維持する。
- 実際の全シナリオ検出と各行の1件選択、計画した引数の実行、欠落・重複拒否を確認する。通常検査と実runnerの全19件成功・時間を確認する。

長時間カバレッジ検査の未網羅53ファイルは別途残っており、今回も閾値を下げない。

並列化の実CIで、音声入力の待ち行列上限による切断を確認した。ブラウザの20ms入力は維持し、DOで処理待ちになった同じ接続・世代の連続音声だけを、既存の9600バイト上限までまとめる。新たに待ち時間を設けず、操作との順序を維持し、元のメッセージ件数・バイト数を上限判定に使う。失敗時は入力滞留の固定診断名とブラウザの切断元を記録し、ランタイムのログ本文は公開しない。
