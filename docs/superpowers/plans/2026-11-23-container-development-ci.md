# 開発環境とCIの共通コンテナ化計画

## 目的と前提

依存の取得・生成・検査・ローカル起動をコンテナ内で完結させ、開発端末の資格情報とソースを依存コードから隔離する。開発者とCIは同じ固定イメージと実行入口を使う。ホストではGit、Docker Compose、go-task、入力準備用のPython 3を使う。Gitフックの利用時はホストのLefthookとgit-secretsも使う。実AI、認証付き投稿、クラウド配置は既存の専用手順を維持する。

[設計基準](../../spec/mvp.md#設計基準)、[3 Workers](../../adr/0007-three-workers.md)、[環境分離](../../adr/0009-explicit-environments.md)、[依存保護](../../../tools/docs/README.md#依存のサプライチェーン対策)に従う。[通常CI](../../../.github/workflows/ci.yml)のE2Eは既に固定版Playwrightイメージを使っている。

## 1. 依存取得と隔離の成立を先に検証する

- [ ] ルートの compose.yaml と tools/containers/ に共通Dockerfile、起動スクリプト、入力準備処理を置く。Node.jsは .node-version、pnpmはルートのpackageManagerに合わせる。信頼済みの変更からイメージをビルドし、CIはdigestで参照する。開発端末とLinux runner双方でネイティブ依存を確認する。
- [ ] depsだけが許可リスト付きプロキシ経由で配布元へ接続し、専用storeに書く。ターミナルの認証環境、Dockerソケット、ホームは全サービスで渡さない。非root、読み取り専用ルート、追加capabilityなしを共通設定にする。
- [ ] テストには秘密値の代用品、未追跡のソース、削除・改名、入力外を指すシンボリックリンクを用意する。必要な編集中の変更だけを取り込む。depsには依存宣言・lockfile・フック・パッチなどに限定した入力を渡す。準備途中のstoreは再利用せず、成功した世代だけを公開する。
- [ ] 空のstoreとキャッシュ命中時の両方で、固定lockfile、スクリプト無効化、既存の信頼ポリシーとCIのTakumi Guardが実際の取得経路を保護することを確認する。devとcheckは読み取り専用storeの私有コピーからオフライン導入する。保護設定を維持したまま導入できない場合、この段階で方式を見直す。

## 2. 開発用の3 Workersを起動する

- [ ] devは毎回新しい作業コピーで既存のdev:localを呼ぶ。ローカル状態の実パスを確認して開発用volumeに対応させ、生成物とテスト状態を分ける。worktreeごとにComposeプロジェクト名を分ける。
- [ ] tools/local-integration/src/runtime.ts の待受設定はコンテナ起動時だけ変更する。公開はホストの127.0.0.1の63286番だけとし、通常のモック開発は外向き通信を閉じる。
- [ ] ブラウザからWebと音声WebSocketに接続し、モックでDO、Queue、評価、D1まで確認する。停止・再起動後に開発データが残り、ソースの削除・改名が反映されることを確認する。ホストのソースと別worktreeの状態は変更されないことを検査する。

## 3. ローカル検査とGitフックを移す

- [ ] checkは外部ネットワークなし、使い捨ての作業領域で起動する。入力準備とオフライン導入をentrypointに置き、末尾で指定コマンドを実行する。デフォルトの全検査とCI用の個別コマンドの両方で確認する。
- [ ] 文書検査のgit ls-filesやカバレッジのrevision取得など、Gitに依存する入口を棚卸しする。必要なファイル一覧・revisionをホストで渡すか、作業コピー内で検査用のGit状態を再構成する。実際の.gitや認証設定を共有せず、未追跡・削除ファイルを含む既存の判定を保つ。
- [ ] lefthook.ymlに加えフックの登録・起動経路も移す。ホストのpnpmやnode_modulesがない状態でcommit・push時の検査と既存のgit-secretsが動き、失敗がGitに伝わることを確認する。
- [ ] コード変更は失敗するテストを1つ追加し、ルートの通常テストでRedとGreenを確認する。移行後はコンテナで通常検査と結合検査を実行し、失敗時のログ・終了コード・後片付けまで確認する。

## 4. CodexのLocal environmentsを設定する

- [ ] Codexデスクトップの設定でリポジトリルート用のLocal environmentを作り、生成された設定をルートの `.codex/` 配下でGit管理する。Setup scriptには依存準備、Actionsには「開発サーバー起動」と「通常検査」を登録する。各項目は共通のコンテナ起動スクリプトを呼ぶ。[公式のLocal environmentsガイド](https://developers.openai.com/codex/app/local-environments/)
- [ ] この環境を使ってCodexから新規worktreeを作り、自動セットアップの終了を確認する。上部のActionsから開発サーバーを起動して停止し、通常検査の結果を統合ターミナルで確認する。

- [ ] Codexのローカル環境のセットアップから、開発者と同じ依存取得の入口を呼ぶ。Docker Composeとエンジンへの接続を先に確認し、不足時には必要な操作を表示して停止する。セットアップ時にはサーバーを起動しない。
- [ ] 新規worktreeを2つ作り、ホストにプロジェクト依存を導入せず、それぞれでセットアップ、検査、再セットアップが成功することを確認する。片方の停止・再作成が他方の状態に影響しないことを確認する。
- [ ] 動作確認したセットアップ・検査・起動コマンドをルートのAGENTS.mdとローカル開発手順に記載する。エージェントへ渡すDocker操作権限と、アプリのコンテナに渡す権限を区別する。

## 5. CIを並行稼働してから切り替える

- [ ] CI runnerがコンテナを起動し、PRのコードは入力として渡す。外部PRではCompose、entrypoint、イメージ選択、ホストで動く準備処理を信頼済みの版から取得する。PRが起動権限を変更できないよう、呼び出し元を含む信頼境界を確認する。書き込みトークン、OIDC、投稿処理は検査から分ける。
- [ ] lint・整形、型検査、ビルド、単体テストから既存ジョブと並行実行する。依存キャッシュは信頼区分、対象OSとCPU、イメージ、依存入力で分ける。失敗を含む終了コード、テスト計画、成果物をホスト側の既存集約ジョブに引き渡す。
- [ ] 続いて境界・結合検査、実時間検査、カバレッジの分割実行と集約を移す。ブラウザE2Eは現行イメージを基準に、ブラウザ版・OS依存・実行シナリオを維持できる段階で共通化範囲を決める。Dockerを起動するためにE2Eコンテナへソケットを渡す構成は避ける。
- [ ] 同じrevisionで既存CIと成功・失敗判定、実行対象、生成物、カバレッジを比較する。冷・温キャッシュ別にイメージ取得、依存準備、総所要時間、ディスク使用量を記録する。必須チェック名と集約条件を維持し、同等性を確認したジョブから切り替える。

## ローカルで確認済みの範囲

- go-taskから依存を取得し、外部通信を閉じた検査コンテナで通常検査が成功した。依存取得の初回実測は約97秒だった。store再利用時はGuardの拒否とlockfileポリシーを再確認し、28,808ファイルの整合性検証を含めて約79秒だった。
- 3 Workersを起動し、ホストからループバックの面接画面でHTTP 200を確認した。Web公開には固定宛先のTCP転送を使う。診断ジョブ1件がDO・Queue・Consumerを通って完了した。開発コンテナを停止し、ホスト側を63287番に変えて再作成した後も、同じジョブID・受付時刻・完了結果がD1に残った。
- 実時間検査を単独で実行し、30・120・300秒の再試行、定期回復、DLQ受信を約455秒で確認した。
- ホストにプロジェクト依存のない一時リポジトリでGitフックを登録した。検査失敗を返す代役を使い、pre-commitとpre-pushの両方が失敗を伝え、pre-commitが秘密値検査も呼ぶことを確認した。

## 完了条件と切り戻し

ホストのNode.js依存や資格情報なしで日常開発・Gitフック・結合検査が通り、通常CIと長時間検査が従来と同じ対象を判定すること。許可外通信、ホストへの書き込み、開発状態や信頼済みキャッシュの共有が起きないことを実測する。開発手順とCIの障害調査方法を既存のrunbookに追記する。

移行中は既存CIを必須のまま残す。問題のあるジョブは従来の入口へ戻し、開発用データvolumeは保持する。イメージの公開、必須チェックの設定変更、クラウド操作は本計画作成には含まない。
