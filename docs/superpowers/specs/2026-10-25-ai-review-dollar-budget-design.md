# AIレビューを実行ごとに1ドル以内へ制御する設計

2026年10月25日作成。利用者が指定した「実行ごとに$1」「予算超過はCIエラーではなくPRコメント」「Resolveを操作しない」を具体化する設計案。利用者の実装指示に基づき、実装と回帰テストを追加した。mainへの反映と実API検証は未実施。

## 目的と変更する判断

関連単位のレビューと横断確認を維持し、根拠のない入力合計3MBではなく、トークン数とモデル単価で費用を制御する。PR #25は必須作業の入力約1.83MBに横断確認の予約0.90MBを加え、2MBの事前上限で停止した。このバイト数は実料金を表していない。

[既存の分割設計](../../spec/ai-review-partitioning.md)の3MB、必須作業2MB、候補整理1MB、横断確認ごとの150KBの費用予約を置き換える。[ADR 0005](../../adr/0005-partitioned-ai-review.md)の関連資料選択、横断確認、全必須作業完了後の投稿は維持する。[MVPの設計基準](../../spec/mvp.md#設計基準)に沿い、費用と失敗時の責務を明確にする。

## 合意した範囲

- 1回の生成実行のAPI利用料を最大$1.00とする。分割レビュー、横断確認、履歴確認、候補整理の全呼び出しを含む。
- 生成実行を識別するキーはGitHub Actionsのrun IDとrun attempt。同じhead/baseでも生成を再実行した場合は新たに$1。以前の生成費用は繰り越さない。
- 投稿だけの再試行は既存Artifactを使い、モデルを再実行しない。追加の生成予算を使わない。
- 予算不足はレビュー未完了として停止し、PRの会話欄へ固定文のコメントを投稿する。該当行への指摘とは別に扱う。
- 予算不足だけではCIを失敗させず、エラーアノテーションも出さない。コメント投稿などの障害は従来どおり失敗として扱う。
- Resolve・再オープンは一切操作しない。PR #13のマージや別チャット担当のPR #19は対象外。

予算はUSD建てのモデルAPI利用料を対象とし、GitHub Actions料金、税金、為替換算は含めない。プロジェクト全体の日額・月額制限ではない。

## 検討した方式

| 方式                                           | 利点                                               | 問題・判断                                                         |
| ---------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------ |
| 応答の使用量だけで累計し、$1超過後に停止       | 実測だけで判定できる                               | 最後の呼び出しで既に超過分を使ってしまうため不採用                 |
| 開始前に全作業の最大費用を確保                 | 途中の予算不足を避けやすい                         | 後続候補が未確定で、最大値の過大予約による停止を繰り返すため不採用 |
| 各呼び出し前に費用を確保し、応答後に実測で精算 | 実測を次の判断へ反映し、超過する要求を送らずに済む | 途中停止までの費用は発生する。利用者が選択した方針として採用       |

## 費用計算と料金設定

mainの信頼済み設定に、モデル、処理方式、入力長の料金区分、通常入力・キャッシュ読み取り・キャッシュ書き込み・出力の単価、確認日、出典、料金設定の版を保持する。PR内の設定でモデル、単価、$1上限を変更できない。サービス階層とキャッシュ保持設定を明示し、アカウントの暗黙設定に依存しない。

2026年10月25日に確認した[GPT-6 Lunaの公式仕様](https://developers.openai.com/api/docs/models/gpt-6-luna)では、Standardの短文区分で100万トークン当たり通常入力$0.10、キャッシュ入力$0.01、キャッシュ書き込み$0.125、出力$0.50。長文入力やキャッシュ保持時間などによる区分があるため、これらを単一単価にまとめない。実装時に[料金表](https://developers.openai.com/api/docs/pricing)と利用する設定を再確認する。

実測費用は、互いに重複しない入力の各課金区分のトークン数に単価を掛け、出力費用を足す。推論トークンは出力の内数であり二重計上しない。APIの入力合計からキャッシュ分を差し引く方法は、SDKの使用量フィールドの意味を公式仕様と照合して決める。

計算は整数の最小金額単位で行い、必要な丸めは安全側へ切り上げる。表示の小数桁への丸めと予算判定を分離する。ちょうど$1なら許可し、超える場合だけ拒否する。

料金表を実行ごとにWebから解析しない。モデル・料金区分・返却された処理方式が設定と一致しなければ追加生成を停止する。単価変更は設定更新とテストで扱う。ここで算出する費用は公表単価に基づく利用料であり、請求書の確定額ではない。

## 実行前の計数と呼び出し後の精算

1. 完成した要求を作る。指示、資料、履歴、候補、構造化出力のSchemaなど、入力に影響する要素を固定する。
2. [公式のトークン計数機能](https://developers.openai.com/api/docs/guides/token-counting)で、そのモデルと要求に対応する入力数を求める。文字数・バイト数をトークンへ定率換算しない。計数した要求と送信する要求の一致をハッシュで検証する。
3. 入力数から該当する料金区分を選ぶ。事前にはキャッシュ割引を期待せず、選択した設定で発生し得る最大の入力単価（書き込み料金を含む）を用いる。出力は推論を含む`max_output_tokens`分を確保する。
4. `使用済み費用 + 今回の最大費用 <= $1`なら呼び出す。満たさなければ`COST_BUDGET_EXCEEDED`で停止する。入力が確定した作業のみを判定し、未生成の候補に固定容量の予約を積まない。
5. 応答のusageを、JSON解析・指摘検証より先に回収して費用台帳へ記録する。不正JSON、拒否、未完了でもusageがあれば課金分を集計する。
6. 有効なusageが返れば確保額を実測費用へ置き換え、余った予算を次の呼び出しに使う。失敗やタイムアウトでusage不明なら確保額を解放せず、費用を「不明」として追加生成を止める。SDKの自動再試行は無効のままにする。

呼び出しは逐次実行とし、並列の予算取り合いを発生させない。途中で予算が足りなくなった場合、既に使用した費用は戻らず、部分的な指摘・修正確認は投稿しない。予算のために必要資料を削ったり、出力上限を極端に下げたりして完了扱いにしない。

実測額が確保額を超えた場合は計数・料金設定の不整合として停止する。実測合計が$1を超えた場合も予算超過コメントを投稿し、不整合の固定理由を記録する。超過済みの費用を取り消せるとは扱わない。

### 実装開始時に確認する接続条件

現在のWIFトークンと固定SDKで、計数APIの利用、モデルの対応、Schema等を含めた計数対象を確認する。計数API自体の課金有無・料金も確認し、有料ならその最大費用を事前確保して合算する。無料とは仮定しない。

完全な要求の計数または安全な課金上限を確認できない場合は、固定倍率へ戻さず設計上の未解決事項として止める。計数失敗・未知のusage・料金不明は「予算超過」と偽らず通常の技術的失敗にする。実装検証で実際のusageと計数値の整合を確認するまでは、厳密な$1制御を検証済みと報告しない。

### 計数APIの料金調査結果

2026年10月25日、次の公式資料を確認したが、`POST /v1/responses/input_tokens`自体の無料・有料、課金単位・単価を明示する記載は確認できなかった。

- [Counting tokens](https://developers.openai.com/api/docs/guides/token-counting)：要求の入力トークン数を生成前に取得する機能と、Schema等も計数対象であることを説明している。
- [Input Tokens APIリファレンス](https://developers.openai.com/api/reference/typescript/resources/responses/subresources/input_tokens)：返却項目は`input_tokens`と`object`。返却されたトークン数が計数要求の課金使用量だとは記載されていない。
- [Pricing](https://developers.openai.com/api/docs/pricing)：モデル料金等は掲載されているが、計数APIの料金を特定できなかった。
- [Changelog](https://developers.openai.com/api/docs/changelog)：計数APIの課金条件を確定できる記載は確認できなかった。

料金表に掲載がないことや、API応答に料金項目がないことを、無料の根拠とはしない。現在の実装は生成費用のみを集計しており、計数費用の無料確認・有料対応は未完了である。未確認の単価を仮に設定したり、計数されたトークンを生成料金で課金扱いしたりしない。

有効化前にOpenAIの公式な料金説明またはサポート回答で確定する。無料なら出典と確認日を記録する。有料なら計数前の最大費用の確保、生成と合算した$1判定、計数失敗時の費用不明の扱いを追加し、計数だけで上限へ達する場合・生成と合わせて超過する場合の回帰テストを追加する。今回の調査だけでは有料条件が確定しないため、費用計算と回帰テストの動作変更は行っていない。

## 費用記録の状態管理

DBは追加しない。親プロセスが実行中の累計と各要求の予約・実測をメモリで管理し、予約時と応答受信時に一時ディレクトリの`budget.json`へ一時ファイル経由のrenameで保存する。子プロセスは入力計数とusageを親へ送り、親の保存完了通知を受けてから生成・結果検証へ進む。JSONには生成run/attempt、対象SHA、料金版、要求ハッシュ、トークン数、金額、未精算状態だけを残す。

終了時には成功・失敗を問わず可能な範囲で費用記録をArtifactへ保存する。強制終了などで保存できない場合は費用不明とし、ゼロと推定しない。新しい生成run/attemptは空の台帳から始め、前の生成から累計を復元しない。投稿のみの再試行は保存済みArtifactを利用する。これは実行内の予算制御用の記録で、永続的な請求履歴ではない。

## 既存の容量・時間制限との区別

費用の根拠としての合計バイト制限を取り除く。1回の資料容量、索引・Artifact・応答サイズ、タイムアウトは、メモリ・処理時間・モデル制約を守る別の制限として維持する。必須10回・合計12回・候補整理2回の上限は廃止する。生成処理は認証・計数・モデル呼び出し・統合を含め30分で打ち切る。期限後は次の要求を開始せず、実行中の認証要求と子プロセスを中断する。未精算の費用予約は保持し、部分結果は投稿しない。時間切れは固定理由 `TIME_BUDGET_EXCEEDED` でCIに記録する。費用超過時のPR通知とは区別する。

横断確認の150KB予約は事前の費用合算から除く。1回の要求へ候補を収めるための分割上の余地とは区別し、完成した要求を容量・コンテキスト上限と費用で再検査する。容量制限や回数制限を超えた場合に「$1超過」と表示しない。

## PRコメントとCIの状態

予算不足の通知はモデルに生成させず、固定テンプレートを使う。

> 予算上限（$1）を超える見込みのため、AIレビューを中止しました。PRを分割してください。
>
> AIレビューは未完了です。

利用済み費用、次の呼び出しの最大費用、対象SHA、実行へのリンクを検証済みの値から補足する。実測で既に超過した異常の場合は「予算上限（$1）を超過したため、AIレビューを中止しました」と区別する。usage不明を$0と表示しない。モデル生出力・プロンプト・認証値は含めない。

投稿処理にはリポジトリ・PR・head/base・生成run/attempt・料金設定版・予算・費用内訳・固定理由を含む、サイズ制限付きの予算結果Artifactを渡す。通常の完了Artifactと判別可能にし、未完了の結果を指摘投稿へ流さない。取得元Workflow、対象SHA、試行、スキーマと数値の整合を検証し、投稿直前にPRが同じ対象か再確認する。古い対象なら投稿を省略し、対象変更として終了する。

重複防止はbotの投稿者IDと固定マーカーで行う。マーカーには生成run/attemptとPR・head/baseを含める。同じ生成の投稿再試行は既存コメントを確認して成功扱いとし、本文不一致は停止する。別の生成実行は別予算・別コメントで、過去の実行履歴を上書きしない。

| 結果                                 | 投稿                       | CIの扱い                             |
| ------------------------------------ | -------------------------- | ------------------------------------ |
| レビュー完了                         | 既存の指摘・修正確認       | 成功                                 |
| 予算不足、通知成功／既に同じ通知あり | 予算コメント               | 通知処理の成功。レビュー結果は未完了 |
| 予算不足、通知失敗                   | 投稿成功まで未通知         | 技術的失敗                           |
| 対象SHA変更                          | 古い結果を投稿しない       | 対象外として正常終了                 |
| 計数・認証・資料・モデル等の障害     | 予算コメントを誤投稿しない | 技術的失敗                           |

現在の独立した`AI review / Review result`はネイティブActionsジョブなので、予算コメントの投稿確認後に終了コード0で終える。緑のチェックは通知処理の成功を示し、レビュー完了とは区別する。Actions概要にも「予算不足・レビュー未完了・PR通知済み」とコメントリンクを記載する。独自Check Runのneutral化や書き込み権限の追加は今回行わない。

## 権限分離と引き渡し

生成ジョブは予算結果を通常の終了結果として返し、予算不足では非ゼロ終了や`::error::`を出さない。投稿ジョブの起動条件を「レビュー完了Artifactまたは予算結果Artifactが検証済み」へ広げる。予算通知の後に通常の指摘投稿を実行しない。

生成側にGitHub書き込み権限を与えず、投稿側にOpenAI認証・OIDC権限を与えない。表示ジョブは読み取り専用のまま、投稿済み報告と対象実行の整合を確認して終了する。生成側の「予算不足」報告だけでは通知成功とみなさない。コメントAPIのみを使い、レビュースレッドのResolve APIは呼ばない。

## 実装対象と移行

- 費用計算・料金設定・台帳を専用モジュールへまとめ、分割計画から分離する。
- `review.ts`とworkerの境界で計数・usage・費用を保持し、結果検証の失敗でも使用量を失わないようにする。
- `partition-review.ts`と`orchestrate.ts`から固定の合計入力予算を除き、各要求前の予算判定と専用の予算不足結果を導入する。
- `publish.ts`、status report、check status、`wait-review.ts`、Workflowに予算通知と投稿確認の経路を追加する。従来Artifactの読取り互換を維持する。
- 実装時に分割仕様、コメント要件、運用手順とADRを同期し、容量制約・技術的失敗・費用超過の用語を分ける。実装仕様と運用手順にも本設計を反映する。
- main上の信頼済みコードで動くため、PRだけでは新しい予算処理は有効にならない。main反映と有料の実PR検証は、それぞれ承認範囲を確認して実施する。

## 受け入れ条件

1. $1未満・ちょうど$1は許可し、最小金額単位でも超える次の要求は送信しない。表示丸めに判定が左右されない。
2. 通常入力、キャッシュ読み取り・書き込み、長文料金区分、推論を含む出力を正しく集計し、二重計上しない。
3. 事前確保後の精算で次の要求の可否が変わる。失敗応答のusageも計上し、不明なusageや料金では追加生成しない。
4. 同じhead/baseの別run/attemptは新しい$1予算となる。投稿だけの再試行ではモデルを呼ばない。
5. 3MB超でも費用と別の安全制限に収まる入力を、合計バイト数だけで拒否しない。逆に小さな入力でも費用超過なら止める。
6. 初回・途中の予算不足とも固定PRコメントを投稿し、通常の指摘・修正確認や完了表示を出さない。同じ生成の通知を重複投稿しない。
7. 改ざんArtifact、古いSHA、別run/attempt、通知失敗を成功扱いしない。予算不足を認証障害等と混同しない。
8. 予算通知済みのCIはエラーにならず、Actions概要とPRコメントから未完了だと分かる。Resolve APIは呼ばれない。
9. テストはAPI・価格・usageを差し替えて行い、$1を実際に消費して境界を検証しない。有料の実PR検証では少額の通常経路と、信頼済みの検証設定による低予算の停止経路を確認する。PR内設定から予算を変更させない。
