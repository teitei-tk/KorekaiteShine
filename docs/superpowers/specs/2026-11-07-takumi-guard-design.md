# Takumi Guardの匿名導入と将来の組織連携

2026年11月7日作成。利用者の方針は「今は匿名モードで利用し、将来はShisho Cloudへ連携する」です。本書に沿ってCI設定と遮断確認を実装し、ローカルでGuard経由の取得・拒否を確認しました。PRの通常CI・実時間検査と、手動の隔離受入検査も成功しました。証拠と未検証のイベントは[検証記録](../../research/takumi-guard.md)に記載しています。

## 目的と範囲

CIでnpm依存を取得するとき、Takumi Guardが悪性と判定したパッケージをダウンロード前に拒否します。既存のpnpm保護設定とActionsロックを維持して追加します。

対象は通常CI、Workerの実時間検査、AIレビューと隔離受入検査です。pnpm本体の導入、シェル内のインストール、公式Action内のnpm取得も確認します。GitHub Releases・apt・Actions本体の取得はnpmレジストリの保護範囲外です。未知の悪性依存や、すべてのサプライチェーン攻撃の防止を保証するものではありません。

## 採用方式と代替案

| 方式                           | 判断と負担                                                                                              |
| ------------------------------ | ------------------------------------------------------------------------------------------------------- |
| 匿名モード                     | 今回採用。アカウント・トークン・Guard用OIDC権限なしで遮断を利用できる。取得履歴と事後通知は利用できない |
| Shisho CloudとのOIDC連携       | 将来移行する。Botと信頼条件の設定、ジョブ権限と資格情報の管理が必要になる                               |
| CIのregistry環境変数だけで設定 | 設定量は少ないが、将来の認証追加を考え、今回は公式Actionに統一する                                      |

公式Actionを依存取得前に配置し、ジョブ内のregistry設定をGuardへ向けます。ローカルのregistry設定は変更しません。拒否・通信障害時はCIを失敗させ、npm公式レジストリへ自動的に切り替えません。

初期導入ではpnpm storeのキャッシュ復元を無効にします。取得済みパッケージの再利用は、その時点のGuard判定を受けないためです。増える取得時間と匿名利用のレート制限を実runnerで確認します。性能のために保護を緩めず、必要なら組織連携または別の検査方式を再検討します。

## 制約と受入条件

- pnpm 12.15.0と既存の共有ロックファイルを使用する。ロックファイルを削除・再生成しない。
- 公開後24時間の待機、信頼情報の検査、依存ビルドの制限、`--frozen-lockfile --ignore-scripts`を維持する。
- Guardの設定は最初のnpm系取得より前に適用し、scope別registryや直接tarball URLによる対象外の取得がないか確認する。
- 正常な依存取得と公式の遮断確認用パッケージの拒否を確認する。DNS障害、タイムアウト、認証失敗は遮断確認の成功と区別する。
- AIレビューの専用UID、read-only sandbox、rootのWIFプロキシと既存の通信制限を維持する。
- 将来の連携を見越した空のBot ID変数や、Guard用の`id-token: write`は今回追加しない。既存AIレビューのOIDC権限は別用途として維持する。

## 将来のShisho Cloud連携

Shisho Cloudに組織とGuard用Botを作成し、対象リポジトリを信頼条件へ登録します。その時点で公式仕様を再確認し、対象ジョブに`bot-id`と必要な`id-token: write`・`contents: read`を設定します。長期トークンをGitHub Secretsへ登録する方式は採用しません。

認証を要求するジョブではBot IDの未設定を失敗として扱い、匿名モードへの意図しない移行を防ぎます。fork PR・Dependabotでの権限と実行条件を確認し、意図した匿名利用が必要な場合は条件を明示します。AIレビューへ新しいトークンや設定ファイルが持ち込まれるため、専用UIDからの非可視性、環境変数、後続Actionへの継承と有効期限を再検証します。組織作成・Bot作成・外部通知の設定は将来の別作業です。
